# C.A.W — Code Auditioning Workspace

An experimental, code-driven sound-design and music workspace. The current Flutter app ships Android and Windows builds; the portable C++20 engine and CLI are also built/tested on Linux and Windows CI targets. The app opens straight into your last project, takes a typed or tapped tempo in its transport, undoes and redoes project edits from it, pauses and resumes with Space, lets you choose what each key does, and has three sections, Build, Files and Arrange (docked panels, compact on phones), for C++ sound creation, pattern editing (a piano roll whose notes stretch from either end and whose notes and curves snap to a time and value grid, and that sound while you place, move or bend them), arrangement (songs of any length; the 64-bar limit went in Foundation F7.2, and the engine takes more than 64 layers within its memory budget since F7.3), mixing (Reaper-style channel strips with chain slots and dB peak meters per track, folder and master, on Arrange's mixer card), automation, file management and export (a page from the project menu). Audio runs locally; offline exports install the complete project synchronously without relying on an audio callback, and WAV and MIDI exports support handoff to other music tools.

Project automation supports song-time lanes for module parameters and shared globals, with any number of lanes and points; track volume and pan keep their existing lanes.

**Current status:** Android and Windows app builds are produced by CI. The app has three sections (Build, Files, Arrange), but not every planned capability is implemented. See [App](docs/app.md) for shipped behavior, [Engine status](docs/engine-build-status.md) for native implementation boundaries, the [engine blueprint](docs/engine-next.md) for the target engine design, and the [permanent roadmap](docs/roadmap.md) for planned work and sequencing: the C++ creation-platform foundation first (ordinary C++, the C.A.W. Library/SDK and shared component model), then the engine graph/N-channel Foundation, then the unified C++ editor, visual composition and generated/custom performance interfaces, followed by Stages 0–7 and the first release. The .caw language and VM are gone (#160): sound is C++; old projects are not kept. The target architecture also requires native per-note, per-voice and per-channel processing, genuinely native stereo synthesis with resource-scalable N-channel routing, and MIDISketch-inspired pitch curves that edit smoothly on the note itself; these are requirements, not claims of shipped implementation. The UI redesign (the arrangement as home, docking panels, a Unity-like code workspace) is specified in the [UI plan](docs/ui-plan.md); its first step (shared motion rules and settings, a glass look, design tokens, a shared toolbar, screenshot tests) is built, and so is the docking shell: the three sections are docking panels, on phones too ([app](docs/app.md)).

## Where things are

| Path | What it is |
| --- | --- |
| `engine/` | The C++20 native sound engine, public C++ component SDK (`CAW::SDK`: one component descriptor for ports, parameters, role and timing), built-in instruments and effects, mixer, note patterns, WAV exports, C API, the `caw` CLI and tests ([reference](docs/engine.md)) |
| `app/` | Flutter app for Android and Windows: Build, Files and Arrange ([app](docs/app.md)) |
| `examples/` | The C++ starters (`examples/cpp/`) and two example patterns the app bundles (`acid-line.caw`, `chords.caw`) |
| `docs/` | Project documentation: current app/engine facts, decisions, architecture, the C++ creation-platform and visual-routing designs and the permanent roadmap ([index](docs/index.md)) |
| `scripts/` | Repository tooling. `node scripts/docs-test.js` checks that the docs match the repository; `agent-run.js` runs a chat agent's requested commands and writes its report, `agent-context.js` its start file |
| `.github/` | Issue and PR templates, CODEOWNERS, Dependabot, and the workflows below |
| `.claude/` | Setup for Claude Code sessions: rules, skills, review agents, and hooks that make Graphify and Serena the default way to navigate code ([.claude/README.md](.claude/README.md)) |
| `CLAUDE.md` | Instructions every AI session follows |

Workflows:
- `.github/workflows/docs.yml`: runs the docs guard and repo hygiene checks on Main and every pull request (or on demand); superseded runs are cancelled per branch/PR.
- `.github/workflows/app.yml`: runs Dart analysis and Dart tests on every pull request that changes the app or the engine code it embeds, and on Main (or on demand with Run workflow) also builds the Android APK and Windows app, as independent jobs. A branch's own pushes run only through its pull request, so nothing runs twice. Run workflow can skip the installables for a quick test-only run, and when the Compiler workflow finishes on Main the APK is rebuilt so it carries the compiler. Flutter SDK, Dart packages, Gradle, the Android SDK's CMake and NDK, the engine's native objects (ccache) and the packaged compiler are cached; native test builds use ccache; Dart tests run with bounded parallelism. The APK carries the on-device C++ compiler once the Compiler workflow has cached its LLVM build (a warning says when it doesn't). The APK (`caw-android-apk`) and Windows app (`caw-windows`, also zipped as `caw-windows-zip`) are downloadable artifacts; superseded runs are cancelled. Both builds get the telemetry channel, relay URL and app key through `--dart-define` (none is a secret; repository variables override them). A version tag (`v0.9.0-beta.2`), or Run workflow with **release** ticked, publishes both as a GitHub Release tagged from `app/pubspec.yaml`'s version (a pre-release while the version has a suffix such as `-alpha.N` or `-beta.N`); it refuses a tag that doesn't match the version or a release that already exists. Pushes to Main never make a stable release: the owner promotes a build by tagging it. Each push to Main that builds also replaces the rolling **Every change** pre-release (tag `latest-main`, never the repository's latest release; its notes carry `Version:` and `Build:` lines the app's update check reads), one run at a time. Every build carries the first 12 characters of its commit (`--dart-define=CAW_BUILD`), for the update check and telemetry.
- `.github/workflows/engine.yml`: on Main and every pull request that changes engine code or examples (or on demand), builds and tests Linux x64, Linux Arm64, Windows x64 and Linux sanitizers in a four-job matrix. Linux native builds cache compiler outputs; CTest runs the native suite in four deterministic parallel shards, sound checked against reference renders within a perceptual tolerance (`engine/tests/references/`). The Linux x64 job also checks generated function docs and renders each example except patterns (they need a sound to play); superseded runs are cancelled.
- `.github/workflows/bench.yml`: on Main and every pull request that changes engine code (or on demand, with seconds and runs as inputs), builds Release `caw_bench` and runs its suite (`caw_bench SECONDS 500`, three runs) on Linux x64, Linux Arm64 and an Android arm64 binary (NDK, static, run on the Arm64 runner); each job prints a markdown table to its summary and uploads JSON and markdown (`bench-linux-x64`, `bench-linux-arm64`, `bench-android-arm64`), and a summary job puts all targets in one table ([engine performance](docs/engine-performance.md)).
- `.github/workflows/compiler.yml`: builds the on-device C++ compiler (`engine/compiler/`: Clang and LLD 23.1.5 as one library, LLVM cached per version) for Android ARM64 and Linux, assembles its offline data bundle, and on Linux compiles test components for Android ARM64 with it; publishes the Android library and the bundle.
- `.github/workflows/cpp-components.yml`: builds the installed `CAW::SDK` package, a manifest-driven example component and the example instrument (`examples/cpp/poly-synth/`) on Linux x64, Windows x64 and Android ARM64 (NDK r30); desktop jobs run their contract tests (through each component's C interface, `caw_get_component_v3`) and every target publishes its component artifact; a CLAP job builds the example as a `.clap` plug-in for Linux x64 and Windows x64 (artifacts `caw-minimal-clap-*`) and runs the CLAP test host on Linux.
- `.github/workflows/quick-check.yml`: the chat-agent route. Pushes to `gpt/**` branches run the commands named by `run:` lines in the commit message (targeted tests, sanitizer runs, builds, renders, widget-test screenshots, git diff/log/show/blame, search and Graphify; `scripts/agent-run.js`) or, with none, the docs guard, a Linux x64 engine build and tests, the example checks and (when `app/` changed) Dart analysis and tests. No app builds. It writes one short report per branch to `quick-check/<branch with / as -->.md` on the `agent-results` branch (RUNNING as soon as a run starts, with `quick-check/INDEX.md` listing every branch; screenshots under `screens/`) ([AGENTS.md](AGENTS.md)). Full CI runs once the branch opens a pull request.
- `.github/workflows/agent-context.yml`: on pushes to `Main` that change `AGENTS.md`, `CLAUDE.md`, `docs/vision.md` or a rule, rebuilds `START.md` on `agent-results`: one file bundling everything a chat agent reads first (`scripts/agent-context.js`).
- `.github/workflows/publish-agent-results.yml`: reusable step the two workflows above use to commit their file to `agent-results`; it is the only job with write access and never runs branch code.
- `.github/workflows/clear-status-on-close.yml`: removes `status:` labels when an issue closes.
