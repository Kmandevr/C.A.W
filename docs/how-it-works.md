# How it works

The map for an agent new to the repo. It shows how the parts connect; the details live in [engine](engine.md) (patterns, playback, C API), [app](app.md) (screens) and [native module SDK](native-module-sdk.md) (writing components). Every source file starts with a one-line comment saying what it is for, and `.claude/tools/tree.sh <dir>` lists them. The app has three sections, Build, Files and Arrange (`app/lib/ui/cpp/build_section.dart`, `file_manager_screen.dart`, `arranger_screen.dart`): Build edits C++ components and patterns (a pattern's tab is `pattern_screen.dart`), and Export is a page from the project menu (`export_page.dart`). Sound is C++: built-in components and the user's own; the .caw language is gone (#160), and what stays of its text is the note pattern.

## From a keystroke to sound

1. **Text.** A project module is a pattern: plain text, a header, then one line per note ([engine](engine.md#patterns)). In the app it is `ModuleDoc.source` (`app/lib/model/project.dart`); the piano roll edits it through `app/lib/model/pattern_doc.dart`. A track is a C++ instrument and its effects (`LayerDoc.instrument`, `LayerDoc.components`). What only the screen uses (a track's own row height and collapse state, `LayerDoc.height` and `collapse`, its spacer and open lanes) is saved with the project but never sent to the engine (`AppState._changed(engine: false)`).
2. **Edit to project JSON.** `AppState.editSource` (`app/lib/model/app_state.dart`) stores the text. On Run, or auto-update after a pause, the text becomes the module's `run_source`. `_syncNow` turns the whole project into the engine's project JSON (`Project.toEngineJson`) and sends it. Edits the engine never sees, such as an arrangement spacer (`AppState.setSpaceBelow`) or the music video's shots (`AppState.setMusicVideo`), save and redraw without a sync.
3. **Off the UI thread.** Project updates and offline WAV renders are native jobs submitted to the bounded C++ `AdaptiveWorkerPool`. The app owns each opaque job handle, polls its versioned status/progress and retrieves its result/error; no native worker calls Dart. Project jobs retain the engine handle until completion, so disposal waits safely for accepted work. Jobs use foreground or offline priority, and the app starts with an interactive-preview concurrency budget. Live auto-update uses the result of its one project update. The native pool never touches the audio callback.
4. **C API.** `caw_engine_set_project` (`engine/src/capi.cpp`) hands the JSON to `Engine::setProjectJson` (`engine/src/engine.h`). `engine/include/caw.h` is the only door into the engine, for the app, the CLI's tests and any future plugin.
5. **Parse and diff.** `parseProject` (`engine/src/project.cpp`) validates and normalizes project data. Modules, clips, automation lanes and points are unbounded (the app keeps them all too since F7.1); song positions run to the 32-bit step count and out-of-range ones are refused (F7.2); layers have no fixed limit: the Engine grows its slots and mix graph within its memory budget (F7.3) (owner, 2026-11-04). The full list is the caps audit in [engine status](engine-build-status.md).
6. **Build.** Each pattern goes to `parsePattern` (`engine/src/pattern.cpp`); an error comes back with its line and column, and the last good version keeps playing. Arrangement clips become one sorted event list (`compileArrangement`). Each track's instrument and effects are built and activated as `ComponentChain`s (`engine/src/component_chain.*`) on the control thread; a chain with the same components keeps playing and only takes new values.
7. **Hand-over.** The current Engine sends per-layer commands through a bounded SPSC queue in `engine/src/spsc.h`. `send` retries for about two seconds and can drop an install/pattern command without propagating failure. Replaced chains, patterns and tables return through a bounded queue plus a fixed pending list; overflow can leak. This is a known correctness gap. The target is one prepared project snapshot published transactionally and reclaimed off the audio thread.
8. **Audio callback.** miniaudio (`engine/platform/audio_miniaudio.cpp`) calls `Engine::process`, which runs the mix graph: each track's node (`Engine::runTrackNode`) turns its pattern's notes into note events on their frames, runs its instrument and inserts, then volume, pan, sends and latency delay; each folder bus after what feeds it; then the master's effects, gain, the DC blocker and the limiter.
9. **Built-ins.** Every built-in instrument and effect is a C++ component registered in `registerBuiltinComponents` (`engine/src/builtin_components.cpp`), built on the Library headers (`engine/include/caw/library/`), as a user's component is.
10. **Back to the screen.** The app reads meters and scopes through `caw_engine_meters`, `caw_engine_layer_meters` (every track in one call) and `caw_engine_scope`, polled by `app/lib/model/poller.dart` only while something can change. Between those 30 reads a second the playhead runs on at the tempo (`app/lib/model/playhead_clock.dart`, drawn every frame by `app/lib/ui/live_playhead.dart`) and peak meters fall per frame, so both move at the screen's rate.

Space pauses: `AppState.togglePlay` keeps the playhead as a step and resumes there through `Engine.playAt` (`caw_engine_play_at` in `engine/src/capi.cpp`, which `Engine::play` in `engine/src/engine.h` converts with the tempo then in effect). Every project edit saves, and every save feeds the undo history (`ProjectHistory`, `app/lib/model/history.dart`): whole-project snapshots, one per burst of edits; undo restores one and re-syncs the engine. On launch, `AppState.openStorage` opens the last project, or a copy of the bundled default project (`app/lib/model/default_project.dart`) on a first run. `AppState` also owns transport timing, including latency compensation (`app/lib/model/latency_comp.dart`): `playheadStep` is the render position less the output latency and the meters are read from a short timeline at the time they are heard; the transport's ⏮ (`AppState.backToStart`) seeks to the loop or project start and asks the views to come back through `revealStartRequests` (`requestRevealStart`). Tap Tempo keeps up to five increasing tap timestamps, starts a new measurement after a pause longer than two seconds, averages the intervals and clamps the resulting project tempo to 20–400 BPM. The project update then follows the normal sync and save path. The Arranger's project settings sheet (`app/lib/ui/arranger_screen.dart`) still keeps its own copy of this logic; issue #19 moves it onto `AppState.tapTempo`.

## Modular engine foundation (PR #25)

The modular foundation is real native C++ code, but it is not yet the active playback path for ordinary projects. Its implementation status and remaining integration work are tracked in [engine build status](engine-build-status.md); the intended ecosystem contract is in [engine integration](engine-integration.md).

| Area | Implementation | What is true today |
| --- | --- | --- |
| Module contract | `engine/include/caw/module.hpp`, `engine/src/module.cpp` | Public canonical C++ contract for typed audio, control, modulation and event ports; the `Event` record (note id, raw UMP); the component's identity, role, latency, tail and state size; parameter metadata with choices and modulation/automation/MIDI flags (the graph executor enforces them); generated/custom UI metadata; descriptor validation; and the processor interface (`process`, `processPorts`, and `quiet()`, which lets the host skip a component that has fallen silent). Internal `engine/src/module.h` forwards to this header. |
| C++ SDK build target | `engine/CMakeLists.txt`, `engine/cmake/`, `app/lib/platform/cpp_build.dart` | `CAW::SDK` is installable; the `caw.component` helper creates shared libraries and emits a configuration-specific artifact path; the engine's own link-time optimisation (`CAW_LTO`) does not reach components built against it. The app persists source/dependency pins, invokes local CMake in a private workspace and returns the verified artifact. GitHub Actions is repository CI only, not the user's build service. |
| CLAP export | `engine/plugin/clap/caw_clap_entry.cpp`, `engine/cmake/CAWClap.cmake` | `caw_add_clap_plugin` compiles a component library's sources with the wrapper into a `.clap`: the wrapper reads the components through the C interface (`caw_get_component_v3`) and exports `clap_entry`, mapping ports, notes and MIDI, parameters, state, latency, tail and transport. `caw_clap_tests` (`-DCAW_CLAP=ON`) checks it against `ModuleRegistry` ([native module SDK](native-module-sdk.md#export-as-a-clap-plug-in)). |
| VST3 export | `engine/plugin/vst3/caw_vst3_entry.cpp`, `engine/cmake/CAWVst3.cmake` | `caw_add_vst3_plugin` compiles a component library's sources with a second wrapper into a `.vst3` bundle; the wrapper reads the component through `caw_get_component_v3`, as the CLAP one does, and saves the same state blob |
| Parameter resolver | `engine/src/params.h`, `params.cpp` | One parameter's value per block from its manual/MIDI base (smoothed), automation (unless touched) and modulation links in id order, on the descriptor's curve, then clamped and stepped (F6.1). The graph executor resolves every node's parameters each block, with modulation links from other nodes' modulation outputs (F6.3), automation lanes at the transport position (F6.4) and MIDI CC mappings from host events (F6.5), and passes them to processors (F6.2). The Engine's component chains resolve their parameters the same way (F6.6). |
| Module registry | `engine/src/module_registry.h`, `module_registry.cpp`, `engine/src/capi.cpp` | Static and dynamic registry. Windows uses `LoadLibraryW`; POSIX uses `dlopen`. Explicit trust is mandatory: Blocked refuses, Isolated is rejected until process isolation exists, Trusted loads in-process. Components load only through the C interface v3 (`engine/include/caw_component.h`, `caw_get_component_v3(index)`; a library may be a bundle): the registry copies and validates the descriptor, wraps each instance in an allocation-free adapter, and keeps the library loaded while instances live. `caw_engine_components` lists the loaded descriptors as JSON, which `app/lib/engine/component_info.dart` parses. |
| Native effects | `LayerDoc.components`, `ProjectDoc.masterComponents`, `ComponentChain` (`engine/src/component_chain.h`), `Engine::runTrackNode`, `Engine::runMasterNode` | Stereo effects with parameters: a track's run after its instrument and before volume and pan; the master's before the safety limiter. Values ramp through the F6 resolver; `caw_engine_set_component_param` changes one while playing. An update with the same components keeps the chain and its state. Output is sanitized; old chains retire off the callback. |
| Native instruments | `LayerDoc.instrument`, `ComponentChain::buildInstrument`, `engine/src/note_events.h`, `Engine::runInstrument` / `instrumentNotes` / `instrumentMotion`, `engine/include/caw/instrument.hpp` | A one-component chain on the track's slot plays its notes: the track node turns pattern and clip notes, previews and Stop into UMP note events (fixed storage, frame-accurate) and runs it into the slot's stereo buffer, which goes stereo into the inserts. The component owns its voices (`caw::InstrumentProcessor`, `caw::VoicePool`, whose list holds only the voices sounding at a period's end). |
| Component testing | `engine/src/component_test.*`, `engine/src/analysis.*`, `caw_component_test` in `engine/src/capi.cpp`, `caw test-component` in `engine/cli/main.cpp` | Renders one stereo effect offline (its own `ModuleRegistry`: the built-ins plus a library loaded with an explicit trust choice) with a generated or WAV test signal, and returns levels, THD+N, IR length, frequency response, spectrum, latency and tail against the declared values, null tests, parameter sweeps and CPU per block as JSON ([engine](engine.md#component-testing)). Not on the audio thread; not used by the app yet. |
| Processing graph | `engine/src/graph.h`, `graph.cpp` | Typed graph validation and deterministic topological ordering. The compiler has no former fixed node/connection count caps; node indices remain `uint32_t`. Compile/prepare require `GraphResourceBudget.maxWorkingBytes`, with optional count ceilings defaulting to unlimited; internal working-set estimates are checked before allocation. The executor accepts caller-selected block sizes without the former 8,192-frame cap, is planar N-channel with summing inputs, and can be re-routed on the audio thread (`setRouting`). The Engine owns one such graph for its mix (F4.3). |
| Graph publication | `GraphRuntime` in `graph.*` | A control-thread publication helper lets the audio thread adopt a prepared graph and defers reclamation to the control thread. It is not connected to `Engine`. |
| Workload policy | `engine/src/execution.*`, `execution_capi.cpp`, `app/lib/engine/execution.dart` | A deterministic native policy maps task class and host-supplied pressure to a bounded worker budget. The app applies an interactive-preview budget to its native pool. Android thermal/battery-saver events and app foreground/audio transitions update the active plan; other platform pressure adapters remain unknown/unimplemented. |
| Hardware profile | `engine/src/hardware.*`, `app/lib/engine/execution.dart` | Best-effort active/online logical-core probe, process affinity on supported hosts, Linux/Android cgroup CPU and memory limits, conservative available-memory budget and CPU-SIMD probe; Linux/Android account for cgroup headroom, including exhausted limits. macOS/iOS use a physical-memory fallback. Missing signals remain unknown and policy falls back conservatively. Android `PowerManager` thermal (Android 10+) and battery-saver signals feed the scheduler through event-driven channels; app foreground/audio transitions also refresh policy. Unsupported platforms remain `Unknown`, not normal. GPU compute is unavailable in this build. |
| Worker pool | `engine/src/scheduler.*`, `engine/src/worker_api.cpp`, `app/lib/engine/execution.dart` | The C++ pool is a bounded non-real-time queue (256 jobs), up to 16 workers, with priorities and an adaptive wrapper. It creates workers only for demand, sleeps on a condition variable, and retires idle workers after 30 seconds by default; completed slots are joined and reused. The public C API exposes job handles/status/progress/results/cancellation. The app submits project compilation, module checks and offline WAV renders to it; generation and analysis jobs remain to be routed. |
| Dependencies | `engine/src/dependency.*`, `engine/src/project.*` | Exact scope-aware resolution by stable ID, pinned version, optional hash and interface version. Project JSON parses and stores references; installed-library matching, project writing/round-tripping and repair UI are not complete. |
| MIDI devices | `engine/src/midi2.*`, `engine/src/midi_device.*`, `app/lib/platform/midi_input*.dart`, `app/lib/model/live_midi.dart`, `MidiInput.kt`, `BluetoothMidi.kt` | The platform reads a device (Android MIDI with its `System.nanoTime` stamps, Windows WinMM); `LiveMidi` routes each message to a track and hands it to `caw_engine_midi_bytes`/`_ump`; the engine converts MIDI 1.0 to UMP at the edge, queues it in `Midi2InputQueue` and the audio thread places it at its frame in the instrument's note events (`DeviceNotes`). Controller learn maps CCs to knobs in the app. |

**Important boundary:** since F4.3 live playback and offline render run through the Engine's mix graph, with one node per track (its instrument and inserts), folder bus nodes and a master node (F4.4; one node per track since #160). The graph compiler cap-removal and low-level budget slices passed CI at checkpoint 1269019; follow-up commit e815b495 adds direct compiler-budget rejection coverage and awaits CI. The prepared executor is planar N-channel since F3 (any layout) and runs audio, modulation and control ports since F5.1 and event ports since F5.2. Native-pool routing is implemented for project updates and offline WAV renders; generation/analysis routing remains incomplete. Android live thermal/battery-saver and lifecycle pressure feeds are connected; other platform adapters remain incomplete. Do not describe graph hot-swap integration, universal native-module execution, dynamic add-on loading or app-side custom UI rendering as complete.

## Export

`caw_render` (`engine/src/render.cpp`) drives the same `Engine` offline, so a file sounds the same as what was heard (timing exact, sound within the perceptual tolerance of `docs/decisions.md`, 2026-11-12), and writes it with `engine/src/wav.cpp`. The app submits it as an offline-priority native job with progress and cancellation (the Export area). The CLI (`engine/cli/main.cpp`) uses the same native render call.

## Checks

- Engine: build with CMake and run `caw_tests` ([engine](engine.md#tests)); `caw render PROJECT.json` and `caw test-component` check a sound without listening.
- App: `flutter analyze` and `flutter test` in `app/`; `CAW_LIB=<built libcaw.so>` adds the tests that need the engine.
- Docs: `node scripts/docs-test.js`.
