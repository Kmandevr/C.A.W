# Engine reference

The engine in `engine/` as built. The reasons behind it are in [architecture](architecture.md), and the version plan is in [roadmap](roadmap.md). All of it is **[Fact]**: it is checked by `engine/tests/`.

Every file path the engine takes or returns (C API, project JSON, requests) is UTF-8 text. The engine opens, creates, renames and deletes files through `src/utf8_path.h` (a `std::filesystem::path` built from the UTF-8 bytes, and `_wfopen` on Windows), so names outside ASCII work on Windows too, where a narrow `fopen` or `std::filesystem::path(std::string)` would read them in the ANSI code page; file system errors there are returned, never thrown. Returned paths use `/` on every platform. **[Assumption]** The `caw` CLI is the exception on Windows: it passes `argv` on as given, which there is in the ANSI code page, so CLI paths outside ASCII are not expected to work on Windows (untested).

Build and test (Linux or macOS, CMake 3.22+ and a C++20 compiler):

```
cmake -S engine -B engine/build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build engine/build && ctest --test-dir engine/build --output-on-failure
```

Optimised builds (Release, RelWithDebInfo, which Android Gradle's release uses, and MinSizeRel) are link-time optimised by default with Clang (the Android NDK's included) and MSVC, when CMake's `CheckIPOSupported` finds it works; not by default with GCC or MinGW, where it measured slower; never in Debug or `-DCAW_SANITIZE=ON` builds. `-DCAW_LTO=ON|OFF` overrides the default (speed phase 1, [engine performance](engine-performance.md#1-free-wins)).

`-DCAW_CLAP=ON` (off by default; it fetches the CLAP headers from GitHub) also builds the CLAP export tests: the minimal example and a test bundle as `.clap` plug-ins, and `caw_clap_tests`, a small CLAP host CTest runs ([native module SDK](native-module-sdk.md#export-as-a-clap-plug-in)). `-DCAW_VST3=ON` does the same for VST3 (it fetches the VST3 interface headers): `.vst3` bundles and `caw_vst3_tests` ([native module SDK](native-module-sdk.md#export-as-a-vst3-plug-in)).

## Patterns

The .caw module language, its compiler and VM were removed (#160, owner 2026-11-10): sound is C++ (built-in components and the user's own, [native module SDK](native-module-sdk.md)). What stays of the text format is the note pattern, the note-clip format the app edits (#158).

A project module holds a pattern (`kind: pattern`): notes, not code. A track picks one as its pattern (or plays several as clips), and the track's instrument plays its notes. Patterns are plain text, so a person or an AI agent can write one:

```
---
kind: pattern
name: Acid line
length: 16          # in 16ths, or `length: 2 bars`; without it, the whole bars its notes need
---
// at   note(s)    len   vel   extras
0       A1         2     1
3       A1         1     0.8   slide
13/3    E2         1     0.6   prob 0.5
4.5     C3,E3,G3   1/2   0.9   ratchet 2
```

- **Columns:** `at` and `len` are in 16ths and may be decimals or fractions (`13/3` lands exactly on a triplet). Notes are names (`A1`, `F#3`) or MIDI numbers, with fractions for microtones; commas make a chord. `vel` is 0–1 and optional (default 1).
- **Extras:**
  - `prob P`: the note plays with chance P. The choice comes from the project seed, the note and which repeat of the pattern this is, so every project loop plays the same way and exports match playback.
  - `ratchet N`: the note is split into N equal repeats (2–8).
  - `slide`: the next note starting exactly where this one ends takes over the held note: no new note-on, the pitch glides over half a step. In a chord, sliding notes pair with the next chord's notes in written order.
  - `bend`: per-note pitch curve in semitones, written as time/value points; optional segment bend handles use `~`.
  - `vib`: vibrato depth, rate in Hz and optional fade-in.
  - `press`: per-note pressure/volume curve; `timbre`: per-note timbre curve. These are preserved in the pattern model and emitted as MPE expression on MIDI export.
- **Playback:**
  - The pattern sets the track's loop length; a note running past the end is released there.
  - Notes reach the instrument as note events on their exact frames; how many sound at once, and how a stolen or released note ends, is the instrument's own (each built-in's, or the user's component).
  - A tempo change releases held notes.
  - Notes that start at or after the pattern's length never play, and the project result warns about them.
  - **A pattern edit while a note sounds** (owner, 2026-11-10, #170): pattern text has no note ids, so `setProject` matches the old pattern's notes to the new one's on the control thread (`matchPatternNotes`, `engine/src/pattern.cpp`): first notes with the same start, length, pitch and ratchets, in order (a curve, velocity or chance edit keeps the note); then each changed note takes the edited note that overlaps it in time, nearest in pitch, then start, then length (a move, stretch or transpose that still overlaps its old place). Past 2^24 pairs of changed notes that second pass is skipped. The map goes to the audio thread with the pattern (and is retired with it). On the track's next run, a held note whose matched note still covers the playhead keeps sounding, with no new trig or note-on, and takes the new note's curve from the playhead, gliding from the pitch heard to where the new curve is over 5 ms; it then ends where the edited note ends. A note the edit deletes, or moves off the playhead, is released (its release, not a cut); a note the edit adds starts at its next start. A note's 16-frame control grid keeps its phase across the edit. Two notes at the same pitch overlapping the same place are told apart only by start and length, so a drag that swaps their order can hand a sounding note to the other one. With no edit nothing changes, so playback and export match (their renders unchanged).
- **Limits:** note collections grow dynamically; there is no fixed 4096-note parser cap. Pattern step indices use the signed 32-bit representation boundary rather than a fixed 4096-step product cap; note-expression curves are dynamically sized. Ratchets remain limited to 8. Errors give a line and column. Kit rows (`[kick]` lines) are reserved for kit patterns and are an error for now.

### MIDI files

A pattern can be imported from, and exported to, MIDI files for use in Reaper and other DAWs (code in `engine/src/midifile.cpp`).

- **Import:** `caw midi import IN.mid -o OUT.caw [--track N] [--channel C] [--name NAME] [--no-bend] [--no-slides]`, or `caw_pattern_from_midi(data, size)`, which returns `{"ok","error","pattern"}`.
  - It reads Standard MIDI Files (format 0 and 1) and MIDI 2.0 Clip Files (`.midi2`). All tracks and channels are merged unless one is chosen.
  - Times come from ticks, so tempo changes don't move notes. Whole steps are written as numbers, small fractions exactly (`13/3`), and anything else to 1/1000 step.
  - Notes with the same start, length and velocity become one chord line. Velocity is vel/127, or vel/65535 for a clip file.
  - The pattern is the whole bars of the file's first time signature (4/4 without one).
  - A pitch bend sounding at a note's start becomes a microtonal pitch, assuming ±2 semitones.
  - A note that overlaps the next one by at most 1/8 step becomes a `slide`, so ordinary legato playing comes in as slides. `--no-slides` turns that off.
  - Limits: 16 MB and 65536 events; notes and steps are bounded only by the signed 32-bit step representation (a caller may pass a lower note allowance). Format 2, SMPTE-timed and malformed files give an error.
- **Export:** `caw midi export PATTERN.caw -o OUT.mid|OUT.midi2 [--bpm B] [--beats N] [--clip]`, or `caw_pattern_export(source, bpm, beats_per_bar, CAW_MIDI_SMF|CAW_MIDI_CLIP, path, error, len)`.
  - Both formats use 960 ticks per quarter and carry the tempo, the meter and the pattern's name.
  - Ratchets are written as their repeats, every note is written whatever its `prob`, and a slide is a legato overlap of 1/16 step. Notes are cut at the pattern's length, as in playback.
  - `.mid` is a format 1 file. Microtonal notes round to the nearest note and play on a channel of their own (2–9, 11–16) with a pitch bend; RPN 0 sets the bend range to ±2 semitones. If the pattern has note expressions (bend, vibrato, pressure or timbre), export uses an MPE lower zone with per-note pitch bend, channel pressure and CC74 timbre.
  - `.midi2` follows the MIDI Clip File specification (M2-116-U, read 2026-10-28): MIDI 2.0 notes with 16-bit velocity, and microtones through the Note On Pitch 7.9 attribute.
    - **[Assumption]** Some layout choices aren't fixed by the spec. Everything is on group 0, channel 1. Tempo, time signature and clip name sit right after Start of Clip. Note Off has velocity 0x8000.
    - **[Assumption]** Which DAWs read clip files is unverified ([architecture](architecture.md#variables-and-patterns-proposal)).

## Playback

- **Project:** BPM, beats per bar, loop length in bars, seed and master volume. The project loop is `round(steps × 60 × sr / (bpm × 4))` samples, and every layer restarts when it wraps.
- **Loop range** (REAPER's loop points, 2026-11-10): with `loop_range` on, playback that reaches `loop_end_steps` goes back to `loop_start_steps` (both rounded to samples like the loop), every layer restarting there as at the song's end. Played from after the range, the song plays to its end and then goes back to the range's start. Off (the default, and every older project), the whole song loops.
- **Tracks:** any number, up to what the Engine's memory budget allows (`maxLayers()`). A track is a native C++ instrument (`instrument`) playing its pattern or clips, then its native effects (`components`); a layer without an instrument plays nothing and takes no slot. A track loops at its pattern's length in 16ths, or its own `length_steps`; 0 means it follows the project loop. Each loop start falls at `round(k × length)`, so a 3-bar pattern against a 4-bar loop stays in time.
- **Notes:** notes start and end on the exact sample (`round(at × samples per 16th)`). At a pattern restart, held notes are released, but the instrument and its effects carry on, so tails ring across it. Editing a pattern swaps it in at the next block without rebuilding the sound. A note that is already sounding follows the edit from the playhead, gliding onto its new curve, or is released if the edit deleted it or moved it off the playhead ([Patterns](#patterns)).
- **Chain changes:** a new instrument, or a changed list of effects, is built and activated on the control thread, then crossfaded in over 20 ms while playing (held notes move to a new instrument); new values for the same components ramp over each parameter's smoothing, without a rebuild.
- **Play costs about one callback (A3, 2026-11-13):** a chain's first-time work happens when it is built, on the control thread: an instrument of built-ins is reset there (one with a loaded component is still reset on the audio thread, since the native ABI does not say reset may run on another thread) and its components' values are resolved there, a reset with nothing run since is a no-op (`ComponentChain::reset`), and a block where only the play state changed keeps the values of a component no lane drives (a Play still ends knob overrides). So the first callback after Play no longer clears every drum voice twice or resolves every parameter ([engine performance](engine-performance.md#a3-the-first-callback-after-play)); `startPlay` and the stopped monitoring scan visit only the slots in use (A4, #133).
- **One node per track:** the mix graph runs each track as one node (its instrument, inserts, volume, pan, sends and latency delay), each folder bus after what feeds it, then the master: two nodes per slot. A send or key is pulled (speed phase 5a, 2026-11-12): the source writes each route into a buffer of its own route table, and the destination sums its routes when it runs (`pullRoutes`), in a fixed order (its sources in the order they run, each one's routes by index), so the float sums keep their bits. Each node has its own scratch, the project modulation's per-chain output is per slot, and what a node hands back waits in its own list until the graph has run (`flushRetires`). The executor sorts the order into dependency levels (each send and key a dependency, the master alone and last; phase 5b) and runs them level by level. Since phase 5c the nodes of a level can run at once on the mix pool (`src/mix_pool.*`, worker threads with the callback thread joining in; the output is the same bits as on one thread): the platform starts it with the device (`startLiveMixPool`; `MixPool::defaultWorkers()`: the fast cores less the callback's, at most cores − 2 on 4 or fewer cores, at most 4; used once the measured load stays above 0.4, with fewer workers or none while the callback waits on them more than they work), offline renders use it unless a device runs (checked every callback), and a node holding a third-party native component stays on the callback thread. Since phase 5d the live pool's workers tune themselves to the callback thread (`src/thread_tuning.h`: priority never above the callback's, the fast cores of a hybrid CPU, MMCSS on Windows, an Android performance hint; see "Audio threads" below and [engine performance](engine-performance.md#5-parallel-mixer)).
- **Mix:** each layer has volume, constant-power pan, mute and solo, smoothed over 5 ms. Track and master volume are linear gains from 0 to +12 dB (3.981, `kMaxMixGain`; owner, 2026-11-10: faders like REAPER's), in the project JSON (`volume`, `master`) and the live controls alike; more is held at +12 dB. Volume automation lanes reach the same +12 dB (API version 7; before it they stopped at 0 dB), so a lane written from a fader keeps its level. The master chain is master volume, then a 5 Hz DC blocker, then a safety limiter with a ceiling of −0.2 dBFS, always last.
- **Overload, and coming back (shedding recovers on its own since 2026-11-12, the owner's Bluetooth report):** the host reports how much of each audio callback was used, how many frames it covered and how many the engine rendered for it (`reportLoad(load, frames, rendered)`, `engine.cpp`; through the device FIFO a callback renders more or fewer frames than it plays, so the load counts per frame rendered and the FIFO's alternating render sizes are not taken for overload). Everything goes by time, so every callback size behaves the same. The CPU meter is an average that keeps 0.9 of itself per 10.7 ms. **Shedding:** the share of the last ~0.25 s spent in callbacks over 85% of their budget (an average with a 0.25 s time constant, weighted by each callback's length) passing 70%, about 0.3 s of nearly all-over callbacks, mutes the newest audible layer (faded as a mute is), flags it in the meters, and starts 1.07 s before another could go. One late callback, however late (the first after Play, a device restart or reroute, a background burst), counts only its own length, so a single spike sheds nothing; before, a stall could push the average over 85% for 0.21 s by itself. **Coming back:** with the meter under 60% for 2 s, the newest shed layer returns (fading in), if the meter now plus what that layer was seen to cost (the meter's drop in the 1.07 s after it was shed, at most an equal share of the load then, so a load that fell for another reason doesn't make it look too costly ever to return) stays under 75%, or else on trial after 8 s more of quiet (a cost seen while the device was throttled reads high, and a song shed to silence must not stay silent); then another 2 s for the next. The hysteresis (shed over 85%, back only under 60% and only to under 75%) keeps a returning layer from crossing 85% again, and a layer shed again within 10 s of coming back waits twice as long each time (2, 4 ... 32 s, plus 8 s on trial), so a layer the device can only just not carry comes back on trial a few times a minute at first and then about every 40 s, not every 2.3 s. **Reset:** Unmute (`caw_engine_clear_overload`), the app going to or coming back from the background (`AppState.lifecycle`), and every device open (`requestSheddingReset`, an atomic the next callback reads) bring every shed layer back and forget the load history (every per-callback average, the CPU meter included), so a throttled stretch never thins the song for good. An engine that has rendered offline (`setProjectOffline`) never sheds. A removed layer, track or folder bus, stops counting as shed when its slot frees. **With the mix pool** (speed phase 5, merged 2026-11-13): `reportLoad` takes the pool's times first, before every early return (no frames, an offline engine, a shed), so the pool sees every callback: the callback's wait for workers and the workers' task time (`MixPool::takeTimes`), and the callback's real time against the frames it played for the performance hint (`reportWork`: the device's deadline). Auto's decision follows, on the load per frame rendered, as the meter is, so the FIFO's alternating render sizes don't swing it. While Auto turns the pool on, its first callbacks' cost is the pool starting, not the song: for `kMixSettleSeconds` (0.25 s) they don't count toward the over-budget share and nothing is shed, and a load still over after that sheds as before (`mix_pool_auto_turning_on_holds_shedding_off_while_it_settles`). A shedding reset also clears Auto's wait and work averages and its over and under times (whether it is on, its workers and its retry wait stay). `caw_engine_shedding_stats` (API 27) counts the layers shed (the telemetry's `dropouts`), those that came back on their own, and those shed now (`CawMeters.overloaded`, which now falls as layers return). The per-callback cost outside the layers is small at the smallest periods ([Fact, measured 2026-11-11, x86-64 Release]: 0.011 µs a callback stopped, 0.175 µs with one layer playing at 16 frames against 4.3 µs at 512). Tests: `overload_shedding_goes_by_time_not_callbacks`, `shed_layers_come_back_on_their_own_once_the_load_drops`, `a_layer_the_device_can_only_just_not_carry_does_not_come_and_go`, `a_single_late_callback_sheds_nothing`, `an_offline_render_never_sheds_and_a_shedding_reset_brings_everything_back`, `odd_callback_sizes_through_the_device_fifo_shed_nothing_under_the_threshold`, `a_shed_folder_bus_that_is_removed_is_no_longer_counted_shed`, `shedding_and_its_recovery_never_allocate_on_the_audio_thread`.
- **Threads:** the control thread parses patterns, builds chains and sends messages to the audio thread through a lock-free queue. The audio thread hands what it replaced back the same way, so it never allocates, locks or frees. Parameter and mix values are atomics.
- **Determinism:** output must be perceptually identical, not bit-identical, across platforms, live against export and runs; timing, seeded choices and discrete behaviour stay exact (owner, 2026-11-12, [decisions](decisions.md)).
  - The output doesn't depend on the device's buffer size, and a second engine in the same process gives the same bits (both tested under the build's flags).
  - **Sample positions are strict:** every step or second the engine turns into a sample index goes through `src/sample_time.h` (samples per step, ratchet repeat steps, `floor(x × scale + 0.5)`, layer passes, clip shifts, the metronome's beat offset), and `src/sample_time.cpp` is built with the strict flags in every build, its functions out of line (`noinline`), so neither inlining nor link-time optimisation merges them into fast code. Without it Arm64 fused `at + part × sub` into one rounding and put a ratchet repeat on a half sample one sample away from x86-64 and MSVC (44.1 kHz, 60 BPM, a note at step 2, length 1, ratchet 6: repeat 5 at 31237 strict, 31238 fused). The callers: Engine timing, loop range, play-from, layer passes, note spans and event lookup, pattern ratchet events, arrangement clips, audio clips (start, end, source offset), punch in/out, render and stem ranges and tails (one `stepFrame`, `render.h`), MIDI export's ratchet ticks, the creative effects' song-beat frame (`StepClock`), the note-FX fades, the preview glide, the play tail, the dynamics look-ahead and the test signal's period. Tests: `sample_timing_test.cpp` (ratchets at awkward rates and tempos against a strict oracle, `tests/timing_oracle.cpp`; fails on an Arm64 FMA build without the helper), a sweep of the helpers, MIDI export's note-on ticks against the strict step and the song-beat frame against the strict formula.
  - **Floating-point flags (speed phase 2, 2026-11-12):** the engine's own targets (`caw_core`, `caw_engine`, the CLI, tests, bench) build with `CAW_FP_FLAGS` = `-ffp-contract=fast -fno-math-errno -fno-trapping-math -fno-signed-zeros -fassociative-math` on GCC and Clang (the Android NDK's); `-DCAW_FP_FLAGS=...` overrides it. Never `-ffinite-math-only`: the mix's NaN/Inf guards (`route_math.h`, `finiteOr0`, the limiter) stay, and `fp_mode_test.cpp` feeds NaN and ±Inf from a track (the test bundle's `poison` component) and checks the mix stays finite and audible; a full `-ffast-math` build fails it. `-freciprocal-math` is left out (no gain). Fused multiply-adds happen on Arm64 only: the x86-64 baseline (SSE2) has no FMA and is not raised, and there is no runtime dispatch: x86-64-v3 measured 15–29% faster with GCC but no faster with MSVC, the compiler of the shipped x86-64 build (A5, [engine performance](engine-performance.md#a5-cpu-features)). MSVC keeps `/fp:precise` (clang-cl also `/clang:-ffp-contract=off`): Windows is not the speed target, and `/fp:fast`'s NaN handling is unchecked. Measured gains are in [engine performance](engine-performance.md#2-floating-point).
  - **`CAW::SDK` stays strict:** a component built against it gets `-ffp-contract=off -fno-fast-math -fno-trapping-math` (`/fp:precise`), so the Library gives the same bits in a component on every platform. The SDK's interface flags skip targets with the `CAW_ENGINE_FP_FLAGS` property (otherwise, coming last on the command line, they would override `CAW_FP_FLAGS`). The Library's exact bits and signed zeros, as components get them, are tested in their own executable, `caw_exact_tests` (`library_kernels_test.cpp`, `library_exact_test.cpp`): it builds with `CAW::SDK`'s strict flags and links nothing of `caw_core`, so `caw_tests`, `caw_rt_tests` and the CLAP and VST3 host tests (`caw_clap_tests`, `caw_vst3_tests`) hold only code built with the engine's flags (an inline function compiled both ways in one program leaves the linker one copy for every caller). Their one strict file, `tests/timing_oracle.cpp`, includes no engine or SDK header. Fast-built tests read sign bits from the bits (GCC folds `std::signbit(x)` to `x < 0` under `-fno-signed-zeros`) and keep expected sums in order through a `volatile` (Clang vectorized a 8192-term one in another order).
  - **Code the flags would break:** `detmath.hpp`'s Cody-Waite range reduction (`detail::reduce`, in `detSin` and `detExp`) is kept as written: `#pragma clang fp reassociate(off)` for Clang, an empty asm holding the partial result for GCC; reassociated, it doubled the sine's error at every |x| and put `detExp` 1e-13 off (`fp_mode_test.cpp` checks both under the build's flags). With FMA (Arm64) the reduction is exact. `positiveZero` (`detmath.hpp`) turns −0 into +0 in its bits, as `lib::wrap01` needs, where `x + 0.0` would be folded away.
  - **Flush-to-zero:** every `Engine::process` call (live callbacks, every export and render, the bench, the C API), every sample-pack render and the stem render's loop (its stems' master chains and loudness meters) holds `ScopedFlushDenormals` (`src/fp_mode.h`): x86 MXCSR FTZ and DAZ (FTZ only on 32-bit x86), Arm64 FPCR.FZ (float and double); it clears only the bits it set when it ends, so a host's thread keeps its mode and its exception flags. **[Assumption]** every x86-64 CPU supports DAZ. Each control-register access is a volatile asm with a memory clobber (MSVC: the intrinsics between compiler barriers), so work on values loaded after the guard starts and stored before it ends runs flushed; a value kept in a register across either end needs `ScopedFlushDenormals::fence(v)` (GCC otherwise moved a register-only multiply before `msr fpcr`). Other targets (32-bit Arm, MSVC on Arm64) keep their mode. The component test suite (`caw test-component`) renders without it on purpose, so its "denormals" warning still shows a component's own subnormals (what a CLAP or VST3 host that doesn't flush would get). The kernels' own denormal guards stay: they settle state at exact 0 far above 1e-38 (which lets silent nodes sleep), and they protect components and plug-in exports outside the engine.
  - The built-ins use the Library's own `sin`, `exp` and `log` (`caw/detmath.hpp`); per-sample tanh curves (saturator, delay feedback, drum drives, filter drives, distortion) use `lib::tanhApprox` and Flagship's voice filters `setApprox` (speed phase 3, 2026-11-12, [engine-performance](engine-performance.md)), and control-rate exps, pows and sin/cos are worked out again only when their inputs move. Block-split bit tests (`note_fx_test.cpp`) hold the modulation path to `denormalizeParameter`'s bits, so `denormalizeOffsets` hoists the curve's log but keeps `detExp`.
  - Tolerance tests against reference renders hold the sound, not the bits ([Tests](#tests), "Reference renders"); every reference passes unchanged with the flags above on x86-64 GCC 13 and Clang 18 and on Arm64 GCC 13 (FMA; run under qemu, 2026-11-12). **[Fact, 2026-11-12, x86-64 GCC 13 Release]** the earlier probes (`-mfma -ffp-contract=fast`; `-ffast-math -fno-finite-math-only -mfma`) also null below −129.7 dBFS.

## Project file (JSON)

The app, the CLI and exports share one format:

```json
{ "caw_project": 1, "name": "Night Glitch", "bpm": 140, "beats_per_bar": 4, "loop_bars": 4,
  "seed": 7, "master": 0.7,
  "automation": [
    { "target_type": "instrument", "layer": "l1", "target": "flt1_cutoff",
      "points": [ { "step": 0, "value": 900 }, { "step": 64, "value": 2400 } ] }
  ],
  "modules": [ { "id": "p1", "name": "Riff", "source": "---\nkind: pattern\n---\n0 A2 2 1\n" } ],
  "layers": [
    { "id": "g1", "name": "Group", "folder": true, "bus": true,
      "volume": 0.9, "pan": 0, "mute": false, "solo": false },
    { "id": "l1", "name": "Lead", "parent": "g1",

```

- Optional project-level `automation` lanes target a component's or instrument's parameter: `target_type` `"component"` (with the `layer`, empty for the master chain, and the chain `component` index) or `"instrument"` (with the `layer`), and the parameter `target`. Each lane has song-time `points` with `step` and `value`, linearly interpolated, holding its first and last value outside its range; the project loop extends far enough to include the latest arrangement or automation point. Lanes of other types (the old `param` and `global`) are read but drive nothing.
- `modules` are patterns: `{"id", "name", "source"}`. The result has one entry per module: `ok`, `kind` (`pattern`), `error`, `line` and `col` when it doesn't parse (it keeps its last good version playing), the pattern's `name`, `summary`, `notes`, `length_steps`, `length_bars`, `last_end` and `warnings`. A module that isn't a pattern (an old .caw sound module) fails there with line 1.
- A layer's `pattern` names one pattern module; its notes play the instrument, and its length replaces `length_steps`.
- A layer's `instrument` (a component entry, as in `components`) is the native C++ instrument that plays its notes (see the C API's native components, below). Old keys the engine no longer reads: a layer's `chain`, the project's `globals`, `voices`, `swap`, `seam_crossfade`, `key_root` and `key_scale`.
- An arrangement layer can instead contain \`clips\`. Each clip references a reusable pattern source and has \`start_steps\`, \`length_steps\`, \`source_offset_steps\`, \`loop\`, an optional \`loop_steps\` and an optional \`mute\` (a muted clip plays nothing, while its layer still follows the arrangement instead of running free). \`loop_steps\` is the clip's own loop point (owner, 2026-11-11, REAPER-like): the clip repeats its source from the offset every \`loop_steps\` steps, so notes past it never play and a loop past the pattern's end plays silence up to it; 0 or absent loops at the pattern's length, as before (\`compileArrangement\`, off the audio thread; \`arrangement_clip_loop_steps_repeat_the_source_at_the_clip_loop_point\`). The engine has no clip automation: the app unrolls a clip's lanes into the layer's and the project's lanes (see [App](app.md)). Clip instances may overlap; all of their notes play the track's one instrument and chain.
- The control thread compiles clips into a sorted absolute-time event stream when the project changes. The audio callback does no pattern parsing or timeline allocation: it splits its current block at note boundaries and renders the events at their sample positions. The scheduler follows project transport and loop boundaries; it does not depend on Flutter timers.
- Folder layers may set `folder: true`, `bus: true|false` and `parent`. A parent must be an existing folder; cycles and invalid parents are rejected. Bus folders sum their descendants' stereo output once, then apply the folder's volume and pan before routing to an ancestor bus or master. Organization-only folders do not process audio. A bus folder runs its own `components` (a reverb bus) on that sum, before its volume and pan; an organization-only folder takes none.
- **Sends (#175, API 9):** a layer's `sends` is a list of at most 8 `{"to": bus folder id, "level": linear gain 0..+12 dB, "pre": bool, "mute": bool}`, a copy of the layer's sound into a bus folder's input beside its normal route. Post-fader (the default) taps after volume and pan, pre-fader after the layer's effects and before them; a muted or soloed-out layer sends nothing either way. A bus folder can send too. `caw_engine_set_send(engine, layer, index, level, pre, mute)` changes send `index` while it plays (ramped, no project update); a switch between pre and post fades the send to silence, changes tap and fades back (5 ms each way), and a send pointed at a different bus starts there from silence, with none of the old bus's audio still in its delay line. Soloing a layer keeps open every bus it is heard through: its sends' buses and theirs, and the buses above them.
- **Samples (API 11):** a component entry may name `"samples"`: at most 256 `{"slot": n, "path": file}` or `{"slot": n, "builtin": name}`. The engine decodes them when it builds or updates the chain (the control thread; the audio thread only takes the new buffer), and keeps a slot whose source didn't change. Only a component with sample slots takes them (`org.caw.drums`: slot n is pad n, A1 = 0); a file that fails to load empties its slot and the project still loads. Limits and the decoder: [Drums, samples](#samples).
- **Sidechain keys (#175, API 9):** a component entry may name `"key": {"layer": id, "tap": "pre" | "post", "level": gain}`: that layer's sound (after its effects, before or after its fader) feeds the component's sidechain input (a post key is the pre tap times the fader's own volume and pan, automated ones included, whether the layer is muted, soloed out or its fader still ramping, so muting or unmuting a kick never drops or doubles a duck), and the notes it plays feed the component's key-notes input (the ducker's Notes mode). Only a component whose descriptor has a stereo `"sidechain"` audio input takes one (the ducker, the compressor and the gate; `keyedEffectDescriptor`); a key on any other is ignored with a warning. A layer keying a component keeps running while muted or soloed out, so its key still arrives (a muted kick can drive a ducker). Keys are not delayed by latency compensation: they arrive as early as they can, and the ducker's look-ahead covers a late one.
- **Routing loops are refused:** the project is a graph of routes (a layer to its nearest bus folder, each send, each key from its source to the keyed layer), and an update whose routes make a loop is refused, naming it ("routing makes a loop: 'Verb' -> 'Group' -> 'Verb' (a layer can't hear itself)", `validateRouting` in `project.cpp`); so is a send to a missing layer, to a layer that isn't a bus folder, or from a folder without a bus, and a key from the component's own layer or a bus-less folder. The app never sends one: it leaves such routes out of the engine's copy (`RoutingPlan`, [app](app.md)).
- **Latency compensation across the routing:** a layer's own latency is its instrument's and inserts'; a bus's input arrives at the latest of what feeds it (its children and the sends into it), and every route into a bus or the master is delayed by how much earlier it arrives, so everything that meets is in time, through any depth of buses and sends (`Engine::updateCompensation`). A parameter that changes a component's latency (the ducker's look-ahead turned on or off) recomputes it at once.
- A layer's `automation` array supports `volume` and `pan` lanes, each with any number of ordered `{step, value}` points. The audio callback linearly interpolates these points against absolute song position; no UI timer or per-block parsing is involved. Volume values are gains from 0 to +12 dB (`kMaxMixGain`, more is held there); pan values are -1–1.
- If a clip references a missing or broken pattern, that clip contributes no notes; legacy broken patterns keep their last good version playing.
- `audition` is the Builder's preview, with an optional pattern: a C++ `instrument` and native `components` written as a layer's (API 17). With `audition_only` (it needs an instrument), only the preview is heard. The app's Solo preview of a pattern used by a C++ instrument track plays it through that track's instrument and effects.
- Values outside their range are clamped:
  - BPM 20–400
- Any number of layers: the Engine grows to fit, up to what its memory budget allows (`maxLayers()`), and refuses a project with more by name (F7.3).
- `loop_range` (default false) with `loop_start_steps` and `loop_end_steps` turns the loop range on (see Playback); while it is on, both must be whole steps with the end after the start, and the song lengthens to reach the end. Off, the two are not read.
- Song positions are refused with a message naming the field, never moved or shortened (F7.2): `loop_bars`, layer `length_steps`, clip `start_steps`/`length_steps`/`source_offset_steps`, automation point steps and the audition length must be whole numbers (points may be fractional) that fit the 32-bit step count, so a song holds whole bars up to 2^31 − 1 steps (`maxLoopBars`/`maxArrangementSteps` in `engine/src/project.h`). Project automation lengthens the loop to reach its last point.
- Clips are expanded off the audio thread. A layer whose clips would expand past the project-state budget left (an upper bound, checked before expanding) is not installed, with a warning. Building takes about three times the result, so that peak must fit the budget left after the project so far.
- **Audio tracks (API 18):** a layer's `audio_clips` and `input`, and the project's `assets`: see [Audio clips](#audio-clips).
- **Per-note FX (#127, API 22):** a layer's `noteComponents` (component entries; stereo effects that declare the per-note domain, at most one event input each, no sidechain key) run once per note between its instrument's voices and the instrument's own effects, in `noteVoices` slots (1–16, default 8); the instrument must have a voice bus. Automation lanes and modulation links name them with the kind `noteComponent` (`layer`, `component`/`index`, `target`/`param`). See [Per-note FX host](#per-note-fx-host-127-steps-46).
- Fields the app adds for itself, such as colours, are ignored.

### Song renders

The Export sheet's renders (`engine/src/render_stems.*`, API version 15, roadmap 0.3, 6.4 and 6.5): the mix and stems over a range, in one engine pass per range.

- **Request** (`caw_render_song(project_json, request_json, progress, cancel)`, or as a worker-pool job with `caw_worker_pool_submit_song`; unknown keys are refused): `out_dir` (an existing folder; every file goes straight into it), `project` (the `{project}` name), `pattern` (default `{project}_{region}_{stem}`; also `{kind}` and `{index}`; characters other than letters, digits and `. _ - # +` become `_`, the separators an empty token leaves collapse, a repeated name gets `_2`, `_3`), `mix` (default true), `tracks`, `buses` (a stem per track that plays and per folder bus) or `layers` (these ids instead), `bounds` (`song`, `loop` (the loop range, else the song), `selection` with `start_steps`/`end_steps`, or `regions`: `[{"name", "start_steps", "end_steps"}]`, up to 1,024, a set of files each), `sample_rate` (8,000..192,000), `bit_depth` (16, 24 or 32 for float), `dither` (TPDF, default on, used at 16-bit only), `normalize` (`none`, `peak` with `target` dBFS, default −1, or `lufs` with `target` LUFS, default −14, and `ceiling` dBTP, default −1, above 0 off), `normalize_each` (stems each to the target instead of by the mix's gain), `tail` (`none`, `seconds` with `tail_seconds`, or `silence`: until every file has been below `silence_db`, default −90, for half a second, plus 10 ms, at most `tail_seconds`, default 30, up to 600) and `stems_through_master` (default true).
- **Result:** `{"ok", "error", "files": [{"path", "name", "kind" (mix, track or bus), "layer", "region", "frames", "gain_db", "peak_db", "lufs"}]}`; peak and loudness are as written, −200 for silence or not measured. On failure or cancel no file of the request is left.
- **One pass:** the range plays once, straight through (the loop range is turned off for it), started with `Engine::play(start)` as Play from that step is. `Engine::setOutputTap` copies each stem's layer output into a buffer as it plays: a track's or bus's signal after its effects, volume, pan and latency compensation, where it meets the others. So every file of a range starts on the same frame and has the same length. The song is lengthened past the range and its tail when they reach beyond it, so playback never goes back to the start inside them; clips and patterns end where they end, so a tail is the notes' releases and the effects ringing out. Each file streams to a `.raw.part` float file beside it and is then encoded with its gain (`WavFileWriter`, through `.part`), so memory doesn't grow with the length and normalising needs no second render.
- **Stems through the master:** each stem then gets the master's linear stage as `runMasterNode` applies it to the mix (its volume, the 5 Hz DC filter and the 10 ms fade in when playback starts after the song's first frame), not the master's effects or the limiter. The mix's gain goes on every file unless `normalize_each`.
- **Parity [Fact, tests in `engine/tests/render_stems_test.cpp`, 2026-11-11]:** the mix is bit for bit what playback from the range's start plays, at any device buffer size (callbacks of 441, 64, 37, 512, 1 and 192 frames): the song, a selection, the loop range and a region. A tail leaves the range's own frames unchanged. The stems that reach the master (top-level tracks and buses; a bus carries its children and the sends into it) add up to the mix within 1e-5 when the master has no effects and its limiter is idle; a soloed track's mix equals its stem within 1e-6; a stem without the master stage equals that track's output at the master's input bit for bit. **Exceptions:** master effects and the safety limiter act on the mix only, so stems don't add up to a mix they change; a track inside a bus is in that bus's stem as well as its own, and a send's return is in the bus's stem, not the sender's, so add only the stems that reach the master; an instrument that sounds without notes (the test signal's Free mode) keeps sounding through a tail, and with Until silent it runs to the cap.
- **Fixed with this (2026-11-11):** the master's 10 ms fade in when playback starts mid-song left the rest of the chunk it ended in at 1 − 1/480 of full level, so playback from a step depended on the device's buffer size (`runMasterNode`'s `finishSample`).
- **Dither and 16-bit:** `WavSpec.pcmBits` 16 or 24 and `dither`: ±1 LSB triangular noise from a seeded xorshift32 added before rounding, as the sample-pack maker's (Lipshitz, Wannamaker and Vanderkooy, JAES 40(5), 1992), so the same request gives the same bytes; exact silence stays silent.
- **Loudness:** the integrated loudness and true peak come from `LoudnessMeter` (BS.1770-5) run on the file's samples as they render.
- **[Assumption]** Serum may want an extra `clm ` chunk to recognise 2048-sample frames. This isn't written yet; check before relying on Serum.

## Hardware profile and execution policy

The native hardware probe is a one-time, non-real-time snapshot. It uses active/online logical CPUs, process affinity where exposed, and Linux/Android cgroup CPU and memory limits where readable. Windows uses available physical memory; Linux/Android read system-available memory as `MemAvailable` from `/proc/meminfo` (free memory plus reclaimable cache; Android keeps `MemFree` low on purpose, and budgeting from free pages alone refused First loop on a Galaxy S22+, 2026-11-11), falling back to free pages, and combine it with a finite cgroup limit minus current usage. An exhausted finite cgroup limit is represented by a 1 MiB scheduler budget; a zero field means the signal is unavailable. Positive measurements are budgeted at one quarter, capped at 8192 MiB. macOS/iOS currently use half of reported physical memory as a conservative fallback, not live available memory. The scheduler falls back to one worker for unknown or very low memory. On Android, the host reads thermal status (Android 10+) and battery-saver state once, then listens for changes through event-driven platform channels; foreground/background and audio-playing transitions also refresh the worker budget. Unsupported platforms retain an explicit `Unknown` pressure state; background/offline work reserves one host core where possible and GPU work is disabled. Physical-device behavior still requires validation.

## C API (`engine/include/caw.h`)

- **Engine:** `caw_engine_create(sample_rate)` creates one.
  - `caw_engine_set_project(json)` returns `{"ok", "modules": {id: entry}, "warnings": {"project": [...]}}`, one entry per pattern module ([Project file](#project-file-json)).
  - Live controls: `caw_engine_set_layer_mix`, `caw_engine_set_master` (a 5 ms audio-thread gain ramp), `caw_engine_play`, `caw_engine_play_at` (play from a position in sixteenth steps, converted with the tempo in effect when the play arrives, so a pause resumes on the same beat; it fades in over 10 ms, as does a play that interrupts a stop's fade; outside the loop it starts at 0; notes that began before it are not heard), `caw_engine_stop`, `caw_engine_clear_overload`. API version 7 (2026-11-10, REAPER flow gaps 3 and 4): `caw_engine_play_count_in(engine, step, beats)` clicks `beats` (0..64) beats at the tempo, accented on each bar, then plays from `step` as `play_at` does, on the sample after the last beat (previews play over it; a Stop cancels it; while playing it is `play_at`); `caw_engine_set_metronome(engine, on)` clicks every beat while the song plays, accented on the bar. The click is built in (`Engine::startClick`): 30 ms of a decaying sine, 1760 Hz at 0.5 on the bar and 1320 Hz at 0.32 on other beats, mixed into the master before the safety limiter while playing; the count-in, which runs with the song stopped, adds it to the output directly, held to ±1 (its peak is under the limiter's ceiling). Off by default; offline renders never click. It was chosen over a hidden click track as simpler and real-time safe: no allocation, a few floats of state. `caw_engine_release_touches(engine)` ends every knob touch as a Play does, without moving the transport, so lanes rule again at once (the app's automation Touch mode). Tests: `count_in_clicks_each_beat_then_plays_on_the_sample_after_the_last`, `metronome_clicks_on_every_beat_while_playing_and_not_when_off`, `released_touches_let_the_lanes_rule_again_while_playing`, and `count_in_metronome_and_released_touches_never_allocate_on_the_audio_thread`.
  - Note previews (#103): `caw_engine_note_on(layer_id, id, pitch, velocity)`, `caw_engine_note_pitch`, `caw_engine_note_off`, `caw_engine_notes_off`; heard through the layer's effects and mix while playing or stopped, without moving the transport (detail: [engine build status](engine-build-status.md)). The on-screen keys and pads play through these; MIDI devices through the device input below.
  - **MIDI devices (API 15, `engine/src/midi_device.*`):** `caw_engine_midi_bytes(layer_id, bytes, count, time_ns)` takes a MIDI 1.0 stream (running status within a call; real-time, system and SysEx bytes skipped) and converts each Channel Voice message to a MIDI 2.0 UMP at the edge with the UMP specification's min-centre-max upscaling; `caw_engine_midi_ump(layer_id, words, count, time_ns)` takes UMP words (type 2 upscaled, type 4 as is; utility such as JR timestamps, system, SysEx and data packets skipped by their length). Both push into the engine's `Midi2InputQueue` (1,024 messages between callbacks; more are dropped and counted by `caw_engine_midi_dropped`) from any thread but the audio callback's. `time_ns` is on `caw_midi_clock_ns()` (steady_clock: CLOCK_MONOTONIC, Android's `System.nanoTime`, so `MidiReceiver` timestamps go in unchanged; 0: now). At each callback the audio thread works out every message's frame: a callback stands for the frames just before it started, so a message plays one callback (plus `caw_engine_set_midi_options`' delay, 0–200 ms) after it was played, with the spacing kept; one later than that plays at frame 0; one for a later callback waits. Nothing on that path allocates (`engine_rt_test`). On a native instrument a Note On holds a device note (a preview with its own id range, the device's key and channel; Stop's fade and mute end it, `caw_engine_notes_off` does not); Note Off ends it unless the channel's sustain pedal (CC 64) holds it; Poly Pressure and MIDI 2.0 per-note pitch reach that note (the drums' pad pressure and note learn read them); Pitch Bend repitches the channel's notes over the bend range, Channel Pressure sets their pressure; CC 120 and 123 end them; every CC, Program Change and Channel Pressure also reaches the instrument as its own MIDI event (MIDI 2.0 words, note id 0). With `CAW_MIDI_MPE` channel 1 is the master and channels 2–16 one note each (their bend over the per-note range, 48 by default, and their CC 74 the note's timbre). A `.caw` voice chain takes only the notes, at the block's start. `caw_engine_midi_release(layer_id or NULL)` ends a track's (or every track's) device notes at the next callback; `caw_engine_position_at(time_ns)` is the transport position (samples, unwrapped) the audio thread rendered at that time, -1 while stopped, which recording uses.
- **Meters:** `caw_engine_meters` (master sample peaks since the last read, left and right), `caw_engine_layer_meter` (a track's or folder's sample peak since the last read, after volume and pan; `caw_engine_layer_meter_stereo`, API version 5, also gives each side's peak, and either call resets both; `caw_engine_layer_meters`, API version 25, reads every project layer's stereo meter under one lock into a caller's `CawLayerMeterStereo` array, the first min(count, capacity), resets them the same way, allocates nothing and returns the layer count, `all_track_meters_read_in_one_call`) and `caw_engine_scope` (1024 samples of a track's signal before pan, per layer, or for the master and the audition by `CAW_SCOPE_MASTER`/`CAW_SCOPE_AUDITION`). Loudness and correlation (API version 12, `engine/src/meters.*`): `caw_engine_loudness` fills a `CawLoudness` with the master's momentary (400 ms), short-term (3 s) and integrated loudness in LUFS, their maxima, each side's true peak since the last read and the maximum since the reset (dBTP), the master's stereo correlation and the seconds the integrated value has measured; `caw_engine_loudness_reset` restarts the integrated value and maxima (Play does too); `caw_engine_layer_correlation` gives a track's or folder's correlation (of what it sends on, about 300 ms). A value with no reading yet is `CAW_METER_NONE` (-200). **[Fact]** The definitions follow ITU-R BS.1770-5 (11/2023: K-weighting, the 400 ms gated blocks with 75 % overlap, the -70 LUFS absolute and -10 LU relative gates, Annex 2's 4x true-peak filter) and EBU Tech 3341 V4 (11/2023: the momentary, short-term and integrated windows); `meters_test.cpp` checks the filter against BS.1770-5's printed 48 kHz coefficients and the meter against Tech 3341's minimum test signals. The audio thread K-weights and squares each sample and publishes at each 100 ms sub-block; the integrated value is gated from a fixed 0.01 LU histogram when read, so memory stays fixed however long it plays. The meter measures what the device plays, after the safety limiter, while something reads it: from the engine's start until 30 s pass with no `caw_engine_loudness` read, and again from the next read, which starts it over as a reset does (nothing in the app reads it yet; it cost about 6 % of a three-track project's audio work, [performance](performance.md)). **[Assumption]** the 300 ms correlation window is a usual meter's, not a standard.
- **Hosts and devices:** `caw_engine_process(left, right, frames)` lets hosts such as a plugin drive the audio. `caw_audio_start` and `caw_audio_stop` open the device through miniaudio: AAudio or OpenSL ES on Android, WASAPI on Windows, Core Audio, and ALSA or PulseAudio.
- **Exports:** `caw_render(project_json, options, path, progress, cancel, …)` writes a WAV. Progress counts 0–1000, and a non-zero cancel stops it. `caw_render_song` and `caw_worker_pool_submit_song` (API 15) make [song renders](#song-renders): the mix and stems.
- **MIDI files:** `caw_pattern_from_midi` and `caw_pattern_export` (see [MIDI files](#midi-files)).
- **Function library:** `caw_library()` returns JSON: `functions` (name, category, signature, doc, example and args with name, doc and optional) and `constants`. The app's Library sheet reads it.
- **Native C++ components:** `caw_engine_load_component(engine, library_path, expected_component_id, trust_level)` loads a built shared library into the Engine's `ModuleRegistry` and returns JSON with `ok`, component ID, error text and error code. The caller must pass `CAW_NATIVE_TRUST_BLOCKED`, `CAW_NATIVE_TRUST_ISOLATED` or `CAW_NATIVE_TRUST_TRUSTED`; there is no default. Blocked refuses before opening the library, Isolated is rejected until a separate-process host exists, and Trusted loads in-process. `caw_engine_unload_component` returns 1 only when the library can be unloaded (no live processor wrapper retains it). A build does not call either API. The component exports one C symbol, `caw_get_component_v3` (`engine/include/caw_component.h`); the Engine activates each master-chain instance (`activate(sample rate, kBlock)`) before it plays, and creation, destruction and memory stay inside the component. `caw_engine_components` returns every loaded component's descriptor as JSON (identity, role, timing, ports with layout and channel count, parameters with choices and capability flags, UI controls). The Dart FFI wrapper calls load, unload and the listing on a background isolate. Components see the song's transport in each block (`CawProcessBlock.transport`, `caw::Transport`): the tempo and beats per bar always, and the position in beats with `playing` set while the song plays. A project places loaded stereo effects (one stereo audio input, one stereo audio output, any parameters; a built-in may add a stereo `sidechain` input and a key-notes event input, fed by its `key`) in a layer's `components` (after its .caw chain, before volume and pan) and in `master_components` (before the safety limiter); each entry is an id or `{"id": ..., "params": {name: value}, "bypass": bool, "state": base64, "state_version": n}`. A bypassed component crossfades to its input over 5 ms and is then not run. A component that says it has fallen silent (`ModuleProcessor::quiet()`, the C interface's `caw.quiet.v1` extension) sleeps (is not run, and its output is silence) until an event or input that is not silent arrives. A declared tail alone never puts one to sleep: it would fall asleep on a block boundary with its timed state frozen, so the output would depend on the device's buffer size (second audio review, 2026-11-10; test `a_sleeping_component_renders_the_same_at_any_block_size`). The built-in drums and Flagship say when they are quiet (Flagship once no voice sounds and its effects have fallen below −94 dB), as do the effects suite's effects after silence; the others keep running. A saved state loads when the chain is built (a component may refuse it, which refuses the update), or while playing through `caw_engine_set_component_state` (API 14; the fx-space bullet below). Project automation lanes reach component parameters with `{"target_type": "component", "layer": id (absent: the master), "component": index, "target": param}`: a lane rules while playing, a knob move overrides it until the next Play, and parameters the descriptor marks not automatable ignore lanes. A component that is not loaded, has other ports or names an unknown parameter refuses the whole update. An update with the same components in the same order keeps each chain's running state. `caw_engine_set_component_param(engine, layer_id, index, param_id, value)` changes a value while playing (NULL or empty layer id: the master), ramping over the parameter's smoothing. `caw_engine_set_component_bypass` bypasses one while playing, and `caw_engine_component_states` returns each component's state as JSON (base64) for the project; the app stores it on every save (`ProjectDoc.storeComponentStates`). API version 4 (instruments, below). After Stop, effects that declare a tail (`tail_frames`) ring out on silence until their output stays below −80 dB for 0.25 s (at most the declared tail, and 30 s); effects without one stop with the transport and start the next play from silence. Tracks, buses and sends are kept in time across the whole routing (each layer's latency is the sum of its components' `latency_frames`, up to 32,768 frames; see Latency compensation under [Project file](#project-file-json)). Every Engine also has the Library's built-in stereo tools, which need no trust choice and can't be unloaded. `org.caw.stereo.balance` (`pan` −1..1: the side being turned down falls linearly, the other stays at unity) and `org.caw.stereo.width` (`width` 0..2, mid/side: 0 is mono, 1 unchanged; a mono signal is unchanged at every width) both live in `engine/src/builtin_components.cpp`, with kernels in `caw/library/stereo.hpp`. `org.caw.distortion` (`shape`: Drive, Hard clip, Fold or Crush; `drive` 1..20, `bits` 1..24, `mix`, `output` 0..2) distorts each channel separately. Its kernels in `caw/library/distortion.hpp` are the same code the .caw `fx.drive`, `fx.crush` and `fx.fold` call, so both sound the same (their renders unchanged). `org.caw.delay.pingpong` (`sync`: Free or a note division from 1/16 to a bar, `time` in ms when free, `feedback` 0..0.95, `cross` 0..1 for ping-pong: toward 1 the left line takes the mono average of both inputs and the right line none, so even a centred sound bounces left, right, left, its first echo at the dry level (before the second audio review, 2026-11-10, the left line took the sum, 6 dB over); `mix`) has up to 4 s of delay, set aside at activate (a longer division is held at 4 s), and glides to a new time; it syncs to the song's tempo and rings out after Stop. `org.caw.chorus` (`rate` 0.05..5 Hz, `depth`, `mix`) sweeps each side a quarter cycle apart, so a mono signal comes out wide. `caw_engine_components` lists them first, with `"builtin": true`. `caw_engine_reload_component` loads a rebuild (a new file) of a loaded component: every chain using it switches to the new build, keeping each instance's values, bypass and (if the new build accepts it) state, and a chain swap of any kind (a rebuild, an effect added or removed) crossfades over 20 ms while it sounds. The per-component trust store remains outstanding.
- **Native instruments (#156, API version 4):** a component with one event input and one stereo audio output (no other ports; `ComponentChain::isInstrument`) can be a layer's `instrument`; an instrument in `components`, or an effect as `instrument`, refuses the update. It is a one-component `ComponentChain` (`buildInstrument`) on the track's slot, so values, bypass (a crossfade to silence), state, automation, transport, latency (added to the track's), rebuilds and the project-component cap work as for effects; `CAW_INSTRUMENT_INDEX` (0xFFFFFFFF) addresses it in `caw_engine_set_component_param`, `_bypass` and `_component_states`, and lanes use `{"target_type": "instrument", "layer": id, "target": param}`. The engine sends it the track's notes as MIDI 2.0 UMP note events with host note ids (the encoding in [the SDK](native-module-sdk.md#writing-an-instrument)), queued per block in a `NoteEvents` list set aside when the instrument's chain is built (4,096 events a block and 1,024 held notes, 360 KB per instrument track, about 23 MB at 64 tracks, counted in the project memory budget; the host sets no practical polyphony cap, owner 2026-11-10). A thousand notes at once is far past what a track plays, and 4,096 events leave room for every held note to end and start again in one block; the earlier 16,384 events and 4,096 notes took 1.5 MB a track, about 94 MB at 64 tracks and twice that for a track during a rebuild (second audio review, 2026-11-10). Room for every held note's off is kept back from note-ons and per-note motion, so a full block drops a pitch or pressure update, never an off; drops are counted (`overflow()`), and a 1,025th note ends the oldest. The block's events are put in frame order by a natural merge sort of the runs they arrive in, frame-accurate in every block: pattern and clip notes with the same rules .caw voices follow (chance per repeat, ratchets, clip loops, loop restarts ending held notes, a slide as a pitch glide on the held note without a new on, the note's bend, vibrato, pressure and timbre every 16 frames, and held notes following a pattern edit, below in [Patterns](#patterns)), note previews (`caw_engine_note_on/_pitch/_off/_notes_off`: piano roll and MIDI keyboards), and offs for every held note at Stop, at a tempo change and at Play. After Stop it rings out (its release, then the track's effects) until the track is quiet for 0.25 s, at most 30 s; at Play it is reset unless a preview is held, so an export (the same path, `setProjectOffline`) starts from silence; one still ringing out after Stop first fades out over the new pass's first 5 ms, rendered at Play inside that callback, so the instruments ringing share a budget of 480 frames of that work (`Engine::kPlayTailBudgetFrames`: two fade over 5 ms, 16 over 0.6 ms each), and Play never costs more than about two 5 ms tails (second audio review, 2026-11-10). A track muted long enough to stop is reset before it plays again. A new or rebuilt instrument takes over the held notes (a new on for each, same ids) while the old one releases them and crossfades out over 20 ms. The track then runs its .caw effects (they are mono: they take the instrument's mid, and without any the instrument stays stereo), its native inserts, volume and pan.

    - **`osc1_`..`osc3_` (three wavetable oscillators):** `on` (osc 1 on by default), `table` (Basic: sine, saw, square, 25 % pulse; Analog: triangle, warm saw, shark fin, soft square, soft pulse; Vocal: A, E, I, O, U formants; Harmonic: a band of harmonics sweeping up over 16 frames; Classic: sine, triangle, saw and square, the retired Morph synth's shapes and phases, so its frame is that synth's `shape`; generated by code at the first activate, 1,024-sample mip-mapped frames shared by every instance; User: the imported table, below, or a sine with none), `frame` 0..1 (between frames, linearly), `level`, `pan`, `octave` ±4, `semi` ±12, `fine` ±100 ct, `phase`, `phase_rand` (0 every copy starts at `phase`, 1 at random), `warp` (None, Bend, Sync up to 8×, Mirror, Quantize 256..2 steps, FM: phase modulation by a sine at `fm_ratio` 1..16 times the note, up to 0.75 cycles deep, Fold: a wavefolder on the table's value, drive 1..8, blended in over the first quarter, Osc FM: phase modulation by the oscillator before it round the ring (osc 1 hears osc 3, 2 hears 1, 3 hears 2), its mono output before its level, so a modulator at level 0 is heard only as FM, up to one cycle per unit, held to ±2 units; osc 1 hears osc 3 one 16-frame control period late, the same at any block size; #171). [Fact, `flagship_tables_test.cpp`, 2026-11-11: a sine at A6 (1760 Hz) leaves its aliases about 80 dB down with FM at full depth and ratio 2, 63 dB down with Fold at full drive (the same fold drawn naively at the base rate: 33 dB), and 51 dB down with Osc FM from a sine an octave up] and `warp_amt`, `unison` 1..16 (osc 1 seven), `detune` 0..100 ct (where the outermost copies sit), `detune_power` −1..1 (0 even spacing, +1 gathers copies near the note as \|x\|⁴, −1 pushes them out as \|x\|^0.25), `spread` (pan of each copy: \|x\| × spread, mirror pairs on opposite sides alternating pair by pair, so spread 0 is exactly mono), `blend` (0 only the centre copy or two, 0.5 all equal, 1 only the others; levels power-normalised), `stack` (Off, Octave, 2 octaves, Fifth, Major chord, Minor chord, Harmonics: intervals cycled across the copies in pitch order), `dest` (Filter 1, Filter 2, Both, Bypass). The layout is `caw/library/unison.hpp`.
    - **`flt1_`, `flt2_` (two filters per voice):** `on`, `type` (Ladder LP/HP/BP 24/12 dB, SVF LP/HP/BP/notch, Comb: peaks at the cutoff and its multiples, Formant: `morph` sweeps A, E, I, O, U and the cutoff over 1 kHz shifts the formants), `cutoff` 20..20000 Hz, `resonance`, `drive` 1..10 (a level-matched tanh before the filter), `keytrack` (0..1 of an octave per octave from C4), `morph` (formant vowel, comb damping), `mix`. `flt_routing`: Series (filter 1 into filter 2; Both feeds filter 1) or Parallel (summed).

    - **`mod1_`..`mod16_` (the mod matrix; edited in the flagship's device editor, [app](app.md)):** `src` (None, Env 1..3, LFO 1..3, Random, Velocity, Note, Pitch bend (the note's per-note pitch from where it started, over `bend_range`), Pressure, Timbre, Mod wheel (controller 1 when the host sends it), Accent (a 303's: 0 up to velocity 0.7, 1 at velocity 1)), `via` (a second source the slot's amount is multiplied by, 0..1; None: 1, so "env 2 by accent" opens the filter further only on accented notes), `dst` (None or any parameter before the slots: value k + 1 is parameter k, labelled by name), `amt` −1..1 and `bipolar` (a source is 0..1; bipolar makes it −1..1). A slot adds amount × source in the destination's knob travel (its curve: an exponential knob moves in octaves), slots on one destination add up, and the result is clamped to the range. Applied every 16 frames per voice; a voice source moves an instrument-wide parameter (below) from the newest voice. Slot 1 starts as env 2 opening filter 1 by 1.5 octaves.
    - **Voice mode:** `voice_mode` Poly (a voice per note), Mono (one voice, last-note priority: releasing the newest note returns to the one held before; every note restarts the envelopes) or Legato (one voice; a note played while another is held glides there without restarting them, as a 303's slide; a pattern `slide` arrives as the host's pitch glide). `glide` 0.001..2 s: how long a mono or legato voice takes to reach a new note (to 40 dB of the way), from the pitch it is sounding, even when it is only releasing.

An effect switched on starts from silence.
    - **User wavetable (the component state, #171):** `caw_engine_set_component_state` with the instrument index, state version 1, in one of two forms: an import, `CWTI` + a little-endian u32 split (0: the file is 2048-sample frames, the usual single-cycle table export, and a file shorter than 2048 samples is one cycle; 1..256: that many equal frames, each resampled linearly to 2048) + a WAV file's bytes (PCM 8/16/24/32-bit or float, any channels, mixed to mono, at its own rate; at most 8 MiB); or the saved form `saveState` writes, `CWT1` + u32 frame count (1..256) + u32 frame size (2048) + every frame's samples as 16-bit little-endian PCM, the table normalised to a peak of full scale. Anything else is refused whole and the table playing is kept: another version, a short or unknown header, a size that does not match, 0 or more than 256 frames, another frame size, a split over 256, frames under 16 samples, a WAV the decoder refuses, a silent table. An empty state is no table. Each frame is measured with a 2,048-point FFT, its first 512 harmonics (DC dropped) become a 1,024-sample mip-mapped frame like the built-in tables', and the table is scaled so its loudest frame has a full-scale saw's RMS. Building runs on the control thread when the chain is built (a state change rebuilds the chain and crossfades it in): about 2 ms a frame on a desktop core (256 frames: about 0.55 s; the same bytes again: 6 ms, since instances holding the same table share one copy) [Fact: measured 2026-11-11, Release, x86-64]. Poly voices whose filter 1 is set alike (a linear SVF without drive that no slot moves for that voice, no key tracking, filter 2 off) share one filter with their level before it, as the Morph synth did; a voice whose filter is moved apart takes its own to the note's end. Voices whose own filters are set to the same ladder or SVF low-pass run them side by side (four voices at a time on x86-64, two on Arm64; two centred voices share a two-wide vector), each voice's output summed in the voices' order, so the output is the same as one voice at a time within the tolerance tests and bit-identical on the builds checked (the engine's fast floating-point flags may fuse the paired and single paths differently, about 1 ulp; [engine performance](engine-performance.md#a2-flagship-voices-side-by-side)). - **The built-in effects suite (#173, `engine/src/builtin_effects*.cpp`, and the ducker, #175):** thirteen stereo effects in original code on the Library's kernels (plus the Dynamics and Drive group's five, `engine/src/builtin_fx_*.cpp`, below), listed with the other built-ins. The shape: `attack` 0.1..500 ms down to full depth (a fixed concave bend), `hold` 0..1000 ms, `release` 1..4000 ms back up, bent by `tension` −1..1 (0 straight; > 0 stays low longer and swells back, the classic pump; < 0 springs back and settles), the bend (e^(6·tension·x) − 1)/(e^(6·tension) − 1). A retrigger starts the attack from wherever the duck is, so it never jumps; a new depth from `velocity` jumps only while nothing is ducked, and during a duck glides in over the attack. `lookahead` (Off, 1, 3, 5, 10 ms; Audio only) delays the main signal so the duck leads the key; its latency is reported only while it is on (`VariableLatency`, so the chain's latency follows the knob). `mode` and `lookahead` are not automatable or modulatable, since the reported latency reads their held values; a live change of either crossfades the old read point to the new one over 5 ms. `bands` (Full, Lows, Highs) ducks only below or above `crossover` 40..2000 Hz, split by a Linkwitz-Riley crossover (two Butterworth sections a side, so the bands sum flat in magnitude; Linkwitz, JAES 24(1), 1976); the split always runs, so a change of `bands` crossfades the two paths over 5 ms from current filter state. The key and split filters settle at 0 instead of decaying through denormals. `listen` plays the filtered key. Built-in presets (shapes; the trigger is left alone): Pump, Quick, Smooth, Gate.   - `org.caw.tapestop` ("Tape stop", Pitch & Time): `stop` 0..1 (the trigger: at or above 0.5 the tape stops, below it plays; a knob so a lane or modulation can trigger it; the UI's hold-to-stop pad sets it while held), `stop_time` 20..8000 ms or `stop_sync` (Free, 1/32 .. 2 bars), `start_time` 1..8000 ms or `start_sync`, `curve` −1..1, `mix`. A recording buffer (8 s plus room, set aside at activate) read at a speed v: stopping, v = (1 − x)^p over the stop, p = 4^curve (0 a straight ramp, > 0 drops fast and drags, < 0 holds and falls late); the last 5 % of the speed fades the level out; stopped, silence; on release the motor starts on the tape under the head, v = 1 − (1 − x)^p, and once at speed the lagging tape crossfades back to the live input over 12 ms. Playing, it passes its input bit for bit. *Kilohearts' Tape Stop:* Play (the motor state), Stop Time, Start Time, Curve; what makes it good is the one big switch with musical curves. Technique: varispeed playback, a read pointer moving at speed v through a delay line (DAFX, 2nd ed., Zölzer (ed.), Wiley 2011, time-segment processing), cubic between samples (Niemitalo, "Polynomial Interpolators for High-Quality Resampling of Oversampled Audio", 2001).

Each backwards read is a grain with equal-power fades in and out (sin and cos) over the crossfade, the old one fading out past its chunk's start as the new one fades in. *Kilohearts' Reverser:* Delay time with Sync, Crossfade (in percent of the section) and Mix; good because one knob gives the swell-into-the-beat sound. Two read taps sweep a grain-long delay at speed 1 − ratio, half a grain apart, each faded by sin² so the two always sum to one; with no shift and no jitter it settles on one tap half a grain back (no comb). **Latency:** half a grain plus one frame (60 ms: 1441 frames at 48 kHz), reported per instance (`VariableLatency`), and the dry signal is delayed the same so the mix doesn't comb; a new grain size fades out and in over 5 ms. Clearly different from the saturator's Crush mode (a plain bits-and-rate stage after drive): it models a converter pair; quality does not change it (the aliasing is the sound). *Kilohearts' Bitcrush:* Rate (down to 200 Hz), Bits, ADC Q and DAC Q (the conversion quality: low ADC Q gives aliasing in the lows, low DAC Q in the highs), Dither, Mix; good because the two Qs choose which grit you keep.

Square and saw are band-limited by PolyBLEP (Välimäki and Huovilainen, IEEE Signal Processing Magazine 24(2), 2007). Sidechain multiplies by the key another track sends (silence without one); in the app a key turns `source` to Sidechain, and removing it back to Sine. At High quality the product runs at twice the rate (the Library's half-band, no latency), so sums above Nyquist fold back far less (tested). *Kilohearts' Ring Mod:* Bias, Rectify, Mix, Frequency, Spread and an internal oscillator or noise generator, or its sidechain input; good for metallic, robotic and tremolo sounds from one device.

  - `org.caw.ladder` ("Ladder filter"). *Kilohearts' Ladder Filter:* cutoff, resonance ("high values will make the filter resonate at the cutoff frequency"), topology (transistor or diode ladder; the diode rolls off more gently), Saturate with Drive and Bias; its appeal is vintage warmth and self-oscillation. *Ours:* `mode` (Low-pass, Band-pass, High-pass), `slope` (12 dB, 24 dB), `cutoff` 20..20000 Hz, `resonance` 0..1 (feedback 0..4.4; it self-oscillates from about 0.91 and stays bounded), `drive` 0..36 dB, `bias` −1..1 (tilts the saturation: even harmonics), `comp` "Bass comp" 0..1 (makes up the passband the feedback takes away, as the input gain 1 + comp·k), `mix`, `output`. *Technique:* Zavalishin's zero-delay-feedback (TPT) ladder ([The Art of VA Filter Design, rev. 2.1.0, ch. 5](https://www.native-instruments.com/fileadmin/ni_media/downloads/pdf/VAFilterDesign_2.1.0.pdf), checked 2026-11-11): four one-pole TPT stages, the feedback loop solved for the current sample. The first stage's input is w = T(a − k·y4) with T a tanh shifted by the bias; since y4 is linear in w, the equation is solved each sample by the linear answer and two Newton steps (the slope is ≥ 1, so it converges), with filter.hpp's rational `softClip` standing in for tanh (no exp per sample). Outputs by pole mixing (12 dB: y2, 2w·H(1−H), w(1−H)²; 24 dB: y4, 4w·H²(1−H)², w(1−H)⁴), each unity mid-passband; the feedback always comes from y4, so every mode peaks at the cutoff. A mode or slope change crossfades between the two taps over 5 ms (both come from the same state). High quality runs it 2x oversampled (the Library's half-band). Distinct from `org.caw.filter`'s ladder types (input-stage soft clip only, no drive into the loop, no 12 dB or bias, no oversampling). Tests: −60..−80 dB three octaves above at 24 dB, −30..−45 at 12 dB; a tap at full resonance rings on at 220, 1000 and 3000 Hz within 4 % and under 4.0, and dies away at 0.85; drive 24 dB adds over 10 % distortion where 0 dB adds under 5 %. Display (9): see the table. Presets: Acid squelch, Warm low-pass, Self-oscillation, Fat drive, Thin band, Airy high-pass. Cost 22.5 M (Normal), 60.4 M (High, 2x).
  - `org.caw.nlfilter` ("Nonlinear filter"). *Kilohearts' Nonlinear Filter:* type (all-pass, low-, band-, high-pass, notch), cutoff, Q, drive ("overdrives the filter, which makes the effect of the nonlinear behaviour more prominent"), mode (clean "does not color the signal"; the others' names are not given on the page) [Fact, read 2026-11-11]. *Ours:* `type` (Low-pass, Band-pass, High-pass, Notch, All-pass), `cutoff`, `q` 0.5..25, `drive` 0..36 dB, `shape` (Clean, Warm: tanh, Diode: soft one way and saturating at 0.6 the other, Hard: clip, Fold: a sine fold, Rectify: a lopsided bent curve), `mix`, `output`. *Technique:* a TPT state-variable filter (Zavalishin, ch. 4) whose band-pass integrator output passes the shape before it updates its state and feeds the low-pass, the place an OTA integrator saturates; the band is shaped at √k times its level (k = 1/Q), so a high Q saturates sooner but not Q times sooner. Every shape has slope 1 at 0, so quiet signals hear the clean filter. With a shape the driven input meets a soft ceiling at 4 and half the drive's dB is taken back (Clean takes it all back, being linear). A type or shape change fades to a freshly cleared second filter over 5 ms. High quality oversamples 2x. Tests: Clean is the analog SVF (−3 dB at the cutoff with Q 0.707, the all-pass flat within 0.2 dB); every shape stays bounded and differs from Clean at drive 30 dB and Q 20. Presets: Analog warmth, Screaming band, Diode growl, Folded metal, Hard notch, Clean all-pass. Cost 23.1 M, 53.9 M at High.
  - `org.caw.comb` ("Comb filter"). *Kilohearts' Comb Filter:* cutoff (the peaks' spacing), polarity Plus (a peak at 0 Hz) or Minus (a trough), Stereo (the right side's polarity flipped: wide yet it folds back to the original in mono), mix; feed-forward, "hollow out the sound". *Ours* adds the feedback comb: `tune` (Hz, Note), `freq` 20..5000 Hz or `note` 12..108 with `fine` ±100 ct, `feedback` −0.99..0.99 (negative: peaks at the odd multiples of f/2, hollow, an octave down), `damping` (a one-pole low-pass in the loop), `polarity` (Plus, Minus: flips the delayed path and the loop together, so peaks and troughs trade places), `stereo` (Same, Flip right), `spread` (the right side up to 30 ct sharper), `mix`, `output`. *Technique:* the textbook comb (Smith, [Physical Audio Signal Processing, "Feedback Comb Filters"](https://ccrma.stanford.edu/~jos/pasp/Feedback_Comb_Filters.html), CCRMA; Zölzer, DAFX, ch. 3): out = ½(x + p·d), d the line one period back, the line fed x + p·fb·LP(d); a 4-point Hermite fractional read, the delay gliding over about 20 ms (a retune sweeps, never clicks), the loop low-pass's own lag ((1 − a)/a samples) taken off the line so it stays in tune, and the output scaled by peak^−0.7 with peak = (2 − |fb|)/(2(1 − |fb|)) (high feedback rings about 4.5 dB over the dry level at 0.9). Tests: the first echo one period on (in Hz and by note), Plus/Minus swapping peaks and troughs by more than 15 dB, negative feedback ringing at f/2, the damped comb's period exact to a sample. Presets: Metallic, Hollow, Flange static, Tuned A, Wide comb. Cost 15.8 M.
  - `org.caw.resonator` ("Resonator"). *Kilohearts' Resonator:* pitch, decay, intensity, timbre (all harmonics like a saw, or odd like a square), mix. *Ours:* `mode` (String: harmonics 1..16; Odd string; Modal: a struck free-free bar's modes, ratios (x_n/x_1)² from the roots of cos x·cosh x = 1, 1, 2.756, 5.404, 8.933…; Chord: four chord tones with four harmonics each; Scale: sixteen notes of a scale), `chord` (Major, Minor, Sus4, Major 7, Minor 7, Power, Octaves), `scale` (Major, Minor, Major penta, Minor penta, Dorian, Harmonic minor), `note` 24..96, `fine`, `decay` 0.05..10 s (T60 at the root), `brightness` (higher modes ring as long and as loud at 1; at 0 they fall off as rank^−1.4 and decay as (f1/f)^0.9), `spread` (odd and even modes panned apart, the right bank up to 8 ct sharp), `mix`, `output`. *Technique:* modal synthesis (Smith, PASP, ["Modal Synthesis"](https://ccrma.stanford.edu/~jos/pasp/Modal_Representation.html)): sixteen TPT band-passes in parallel per side, Q = π·f·T60/ln 1000 (a two-pole resonance's envelope falls 60 dB in T60), each mode's band output × √k so a broad input gives each about the same power whatever its decay; the pitch glides over 30 ms; a safety ceiling on the bank (instant down, 150 ms back) keeps a held note at a resonance under 0 dBFS. Both sides run as one two-wide vector (`Pair`, `src/stereo_pair.h`). [Assumption] the bar ratios are beam theory, computed here, not checked against Fletcher & Rossing's table. Tests: modal at A3 rings at 220 Hz and falls 17..32 dB in 0.4 s at a 1 s decay; every mode stays under the ceiling on a full-scale tone at its root. Presets: Plucked string, Hollow square, Glass bell, Minor chord, Pentatonic wash, Short body. Cost 58.3 M.
  - `org.caw.formant` ("Formant filter"). *Kilohearts' Formant Filter:* a vowel selector pane (an XY pane of vowel symbols whose axes take modulation), Q, Lows and Highs (let the lows or highs through); "boost two frequencies to mimic the sounds of different vowels". *Ours:* `vowel_x`, `vowel_y` (the pad: A at 0.5/0.85, E 0.15/0.55, I 0.1/0.1, O 0.85/0.55, U 0.9/0.1, front to the left as on the IPA chart), `shift` "Gender / shift" ±12 st (all formants), `q` 1..30, `lows`, `highs` (the dry signal low-passed under F1 or high-passed over F3), `mix`, `output`. *Technique:* the source-filter model (Fant, Acoustic Theory of Speech Production, 1960): three band-passes in parallel at the first three formants (the Library's `kVowelFormantsHz`, [Assumption] rounded textbook values), levels 2, 1.4 and 0.9 (F1 +6 dB, so a vowel keeps about the level that went in); the pad morphs by inverse-distance weights (1/(d² + 10⁻⁵)²) averaged in log frequency, landing exactly on a vowel at its point. Tests: A peaks at F1 and is 10 dB over at 2290 Hz, I the other way round; +12 st moves the peak an octave; Lows adds 10 dB at 80 Hz. Presets: Ahh, Ooh, Eee, Deep voice, Small voice, Talk box. Cost 24.9 M.
  - `org.caw.disperser` ("Disperser"). *Kilohearts' Disperser:* "magic all-pass filter": frequency, amount ("increasing the order of the all-pass filter"), pinch ("the Q… concentrating the delay around the cutoff"); spreads transients over time without changing the gain. *Ours:* `amount` 0..1 (0..64 second-order all-pass stages, fractional amounts a blend of the chain's outputs either side, so it glides), `freq`, `pinch` (Q 0.3..9), `spread` (the right side's frequency up to an octave higher), `mix` (against the dry: notches). *Technique:* a cascade of TPT all-passes (x − 2k·band; Smith, [Introduction to Digital Filters, "Allpass Filters"](https://ccrma.stanford.edu/~jos/filters/Allpass_Filters.html)); stages leaving the chain are cleared, so they come back clean; both sides as one vector. Cost 77.5 M at 45 stages (about 1.7 M a stage).
  - `org.caw.eq.dj` ("3-band EQ"). *Kilohearts' 3-Band EQ:* splits (two crossovers) and the low, mid and high gains. *Ours* adds DJ kills: `low`, `mid`, `high` −24..+12 dB, `kill_low`, `kill_mid`, `kill_high`, `low_x` 40..1000 Hz, `high_x` 1..12 kHz (held at least 1.5× the low split), `output`. *Technique:* Linkwitz-Riley 4th-order crossovers (two Butterworth TPT stages each; Linkwitz, "Active crossover networks for noncoincident drivers", JAES 24(1), 1976 [Assumption: citation details not re-checked]), the low band through the high split's all-pass (the LR4 sum is a 2nd-order all-pass, Q 0.707), so with every gain at 0 dB the bands sum flat; gains and kills glide over about 4 ms. The saved state is the decoded response (16-byte header and floats); the state also takes the WAV's own bytes. *Technique:* partitioned FFT convolution in two sizes (the non-uniform partitioning of W. G. A new response is built in slices on the audio thread's spare budget (about a quarter of a second for 5 s) and crossfaded in over one partition, so a knob never clicks or blocks; the response is up to 5 s at High, 3.5 s at Normal, 2 s at Eco. Beside `org.caw.utility` (gain, width, pan) and `org.caw.stereo.width`, which stay. Display (265). Presets: Master widen, Mono bass, Narrow, Air, Sides only.
  - `org.caw.channelmixer` ("Channel mixer", Utility). *Kilohearts' Channel Mixer:* Left to Left, Right to Left, Left to Right, Right to Right, each −1 (inverted) .. 0 .. 1. *Ours is the same matrix* (`left_to_left`, `right_to_left`, `left_to_right`, `right_to_right`), smoothed, with a correlation and balance meter. Display (4). Presets: Swap, Mono, Left only, Invert right, Side to mono.
- **Display data (#173, API version 6):** `caw_engine_component_display(engine, layer_id, index, out, max)` copies the latest floats a playing component published for its UI (addressed as in `caw_engine_set_component_param`; NULL or empty layer id: the master; `CAW_INSTRUMENT_INDEX`: the instrument) and returns the count: 0 when it publishes nothing yet or the engine is busy with a project update (it never waits for the control lock: `try_lock`), −1 when there is no such component. Components publish about 60 times a second through a lock-free double buffer (`caw/display.hpp`, [SDK](native-module-sdk.md#display-data)); reading allocates nothing and never blocks the audio thread (tests `display_test.cpp`, `publishing_and_reading_display_data_never_allocates`). Dart: `Engine.componentDisplay(layerId, index, Float32List)`. Each built-in's layout is under [Display data](#display-data).
- **Component testing:** `caw_component_test(request_json, trust_level, output_dir, input_dir)` renders one C++ effect (a test signal) or instrument (notes) offline and returns its measurements as JSON (see [Component testing](#component-testing)). The host gives a library's trust (the user's own choice for it); a request naming a `trust` is refused. Written WAVs are plain file names inside `output_dir` and a WAV test signal a plain name inside `input_dir` (NULL: none), so a request handed on from project data can't load code or touch files on its own. A test WAV is read only from a regular file of at most 200 MB. The CLI keeps `--trust` and paths, since its user types them. It blocks while it renders, so hosts call it from a worker, never the UI or audio thread.

It blocks while it renders, so hosts call it from a worker, never the UI or audio thread.

### Racks (containers, fx-racks)

Two built-ins hold other built-in effects inside one device (`engine/src/builtin_fx_racks*.cpp`): `org.caw.rack.fx` (a serial chain of up to 8 effects with its own modulators, after Kilohearts' Snap Heap) and `org.caw.rack.multiband` (up to 5 bands split by Linkwitz-Riley crossovers, each band a chain of up to 4 effects, after Multipass). **[Fact]** for what is below once the rack tests pass; the design was written first (2026-11-11).

- **Children live in the rack's own parameters.** Each slot has `<slot>_fx`, the child's identity: 0 for an empty slot, else the FNV-1a hash of the child's component id held to 24 bits (`rackChildHash`; exact as a double, never 0), and `<slot>_on` (Off/On, a 5 ms crossfade to the slot's input). Slots are `s1`..`s8` on the FX rack and `b1s1`..`b5s4` (band, slot) on the multiband rack. A child's parameters follow the rack's own as `<slot>.<param>` (`s2.cutoff`, `b3s1.threshold`), in slot order, each as its child declares it. So the project JSON needs nothing new: a rack is an ordinary component entry, `{"id": "org.caw.rack.fx", "params": {"s1_fx": 1234567, "s1.cutoff": 800, ...}}`, and presets (engine and user), undo, A/B compare and the app's value model carry the whole rack as one set of values. A hash rather than an index into a list means any built-in added later can go in a rack without a shared table; a test checks no two built-ins collide.
- **Per-instance descriptor.** The registry's descriptor of a rack lists only its own parameters (empty slots). `ComponentChain` builds a rack (an engine-internal `fx::RackContainer`) by calling `configure(registry, params)` right after `create`, before reading `descriptor()`: the rack creates its children from the `_fx` values and returns a descriptor with their parameters appended. Every value, ramp, automation lane (`"target": "s2.cutoff"` on the rack's component index), knob move (`caw_engine_set_component_param(..., "s2.cutoff", v)`) and MIDI mapping then works as for any parameter; the rack hands each child its slice of the resolved values. A slot naming an effect that isn't a built-in stereo effect, or a rack, refuses the update (a rebuild drops it instead). A change of any `_fx` value is a structural change: `sameComponents` compares the slots, so the chain is rebuilt (and crossfaded) like an effect added or removed; every other value keeps the running chain.
- **Modulation (FX rack).** The rack's modulators are 4 LFOs, 2 envelope followers, 2 ADSR envelopes, a random source and 8 macros. Its 16 routes use the Flagship's layout, `modN_src`, `modN_dst` (parameter index + 1 among every parameter before `mod1_src`: the rack's own and its children's), `modN_amt` (−1..1 of the knob's normalized travel) and `modN_bipolar`, so several routes may reach one knob and the app's mod matrix widgets work unchanged. The routes come after the children's parameters, so a structural change can move a destination's index: the app re-points routes by parameter id when it changes a slot. Modulation is worked out every 16 frames on the rack's grid and moves a child's value only between that child's own control points, never the base value the host holds.
- **Envelopes from notes.** The FX rack is a keyed effect (a `sidechain` input and a `key_notes` input): its ADSR envelopes are gated by the notes of the layer named as its key, and a follower may follow the key's audio instead of the rack's input. A child that is itself keyed (the compressor, the gate, the ducker) hears the rack's key.
- **Latency.** The FX rack reports the sum of its switched-on children's latency (`VariableLatency`, so a child's own variable latency counts). The multiband rack delays every band to the longest band's latency and reports that; its crossovers are minimum-phase IIR and add none. The dry path of `mix` is delayed by the same amount, so dry and wet stay aligned.
- **Display data.** The rack publishes its own block (below). A child's block is read through `caw_engine_component_display` with `index` = the rack's index + (child + 1) × 65536, child counting the slots from 0 in the order above (the FX rack's `s1` is 0; the multiband rack's `b2s1` is 4). No new C function.
- **Nesting.** A rack never holds a rack (refused at configure): no depth to bound, and each rack's cost stays one level of children.
- **Real time.** Children are created, activated and their buffers set aside on the control thread when the chain is built; a rack change is a new chain swapped in lock-free like any other. The audio thread never allocates (tested in `caw_rt_tests`).
- **The modulation model is device-neutral (the base for #161).** A device that offers modulation declares, as ordinary parameters after the knobs it lets be modulated, N route slots of four values: `modN_src` (a choice; its *labels* name the sources, e.g. "LFO 1", "Macro 3"), `modN_dst` (0 none, else parameter index + 1 among the parameters before `mod1_src`), `modN_amt` (−1..1 of the target's normalized travel) and `modN_bipolar` (Unipolar/Bipolar: a source's 0..1 becomes −1..1). The device evaluates its sources on its control grid, sums every route's offset per target (several routes reach one knob), and applies `base normalized + offset`, clamped, to the processor's own copy of that knob's value; the host's base value, automation and undo never see modulation. The Flagship and the FX rack share this contract; the app's `ModMatrix` (`app/lib/model/mod_matrix.dart`) reads any device that declares it, mapping sources by their labels (so a device lists only the sources it has, in its own order) and, with `prefix`, presents a rack child's knobs (`s2.`) as the child's own. The project-level version of the same record is built (#161): see [Modulation](#modulation-project-modulators-and-links-161) below. The rack keeps its own modulators and evaluates its routes inline (`FxRack::control`); the arithmetic both use (`modRouteOffset`, `modulatedValue`, the shared LFO shapes and random hash) is one header, `engine/src/mod_route.h`, so the rules cannot drift.
- **CPU** (callgrind instructions in `ComponentChain::process` per second of stereo noise at 48 kHz, 64-frame blocks, x86-64 GCC `-O2`, 2026-11-11; scratch bench, the chain's own small cost included): an empty FX rack 26 M (the modulators and the dry path); FX rack with a filter and a delay and one LFO route 78 M, against 16 M + 29 M for those two effects alone (so the container's cost is about 33 M with children); the multiband rack with 3 empty bands 47 M, with 5 empty bands 87 M (crossovers, all-pass compensation and band delays); 3 bands each with a compressor 104 M, against 17 M for one compressor alone. [Assumption] a phone core retires a few billion instructions a second, so a 5-band rack is a few percent of one core.

#### Research (Kilohearts, read 2026-11-11)

- **Multipass** ([kilohearts.com/docs/multipass](https://kilohearts.com/docs/multipass)): a band splitter into "up to five different frequency bands", Linkwitz–Riley filters so "a flat frequency response is achieved when the bands are mixed back together", split bars dragged on the display; per lane enable, mute ("the band splitter will still send audio to the lane, but it will simply be discarded"), solo, gain, pan and a per-lane mix; Pre FX and Post FX lanes around the split; eight macros; a modulation lane. **Ours:** the same split and per-band mute, solo, gain and pan, a bypass per band instead of the per-lane mix, an overall mix and output. Not covered: the Pre/Post FX lanes (a chain before or after the rack does that), per-lane mix, the auxiliary outputs, and modulators inside the multiband rack (its knobs take automation; a rack can't go inside the FX rack, so modulating them waits for #161).
- **Snap Heap** ([kilohearts.com/docs/snap_heap](https://kilohearts.com/docs/snap_heap)): "seven lanes" of snapins run left to right, adjacent lanes linked to run in parallel, each with enable, mute, solo, gain, pan and mix; eight macros routed to "several parameters"; a modulation lane; presets with a browser. **Ours:** one serial lane of up to 8 effects, each with its own on switch, 8 macros, and fixed modulators. Not covered: parallel lanes (the multiband rack with one band is not a substitute; a follow-up if wanted).
- **Modulators** ([kilohearts.com/docs/modulation](https://kilohearts.com/docs/modulation)): a lane of up to 32 modulators, among them Envelope (with a "Seamless" restart), LFO with custom shapes, LFO Table, Curve, Random (frequency, jitter, smooth, chaos), Audio Follower (gain, attack, release), Pitch Tracker, Note, Velocity, MIDI CC, Remap, limits, Scale and Sample & Hold; outputs unipolar, bipolar or inverted; several modulations per knob, each with its amount. **Ours:** a fixed set (4 LFOs with 8 shapes including a drawn one, sync, phase and free/retrigger/song modes; 2 followers on the input or the key; 2 ADSR envelopes from the key's notes, restarting from where they are as Seamless does; random with smoothing and S&H; 8 macros) and 16 routes with amount and polarity. Not covered: pitch tracker, curve, LFO table, remap and the modulator-of-modulator tools.
- **Technique.** Linkwitz–Riley 4th-order crossovers whose low and high outputs sum to an all-pass (S. Linkwitz, "Active Crossover Networks for Noncoincident Drivers", JAES 24(1), 1976); for more than two bands, each band passes the other splits' all-passes so all bands share one phase response and sum flat (the standard compensation, e.g. Zölzer (ed.), *DAFX*, 2nd ed., Wiley 2011, ch. 2 on filters and crossovers). LFOs are phase accumulators read through shape functions; the follower is a one-pole attack/release envelope on the rectified signal (*DAFX* ch. 4).

### Modulation (project modulators and links, #161)

Any modulator output can move any parameter of any instrument or component on any track, bus or the master, another modulator's parameter, and a track's or bus's volume, pan and send levels. **[Fact]** for what is below: built and tested 2026-11-11 (`engine/src/modulation_links.*`, `builtin_modulators.*`, `mod_route.h`; tests `engine/tests/modulation_test.cpp`, `modulation_rt_test.cpp`).

- **One model.** A link is the racks' and Flagship's route record at project level: `amount` (−1..1 of the target's normalized travel), `bipolar` (a source's 0..1 becomes −1..1) and a `curve` (−1..1, 0 straight: `u^(1+3c)` above 0, `1 − (1−u)^(1+3|c|)` below; `detPow`). Links into one target add up (in link-id order), the sum moves the resolved base value's normalized position, clamped, and the base value (what the project stores, automation writes and undo restores) never changes. A device's own matrix (`modN_*`) keeps working inside it; a knob can have both.
- **Project JSON.** `"modulators": [{"id", "name", "layer" (where the app shows it), "input" (the layer it hears), "hears": "notes" | "audio" | "both", "tap": "pre" | "post", "component": {component entry}}]` and `"modulation": [{"id" (whole number ≥ 1), "source" (a modulator id), "output" (0..7), "target": {"type", "layer", "index", "param"}, "amount", "bipolar", "curve"}]`. Target types: `component` (`layer` absent or "" is the master chain; `index` the component; `param`), `instrument` (`layer`, `param`), `modulator` (`layer` is the modulator's id; `param`), `volume`, `pan` and `send` (`layer`; a send's `index`). A parameter whose descriptor says `modulatable: false`, or a choice in the app, takes none. Volume and send links move the fader's travel (the app's taper: 0 dB three quarters up, +12 dB at the top), pan links pan's −1..1 travel; a muted or soloed-out track (fader gain 0) stays silent whatever its links do.
- **Modulators** are components whose outputs are `CAW_PORT_MODULATION` ports (one float per frame), with at most one event input (the notes of `input`) and one audio input (its audio after its effects, or with `tap: post` after its volume and pan): `ComponentChain::isModulator`. A track's chain refuses one ("add it to the project's modulators"). Outputs are held to 0..1 (NaN → 0). They run as one `ComponentChain` built with `buildModulators`, so their knobs ramp, take values and keep state as any component's (`caw_engine_set_modulator_param`).
- **Built-ins** (`org.caw.mod.*`, written on the public `caw/modulator.hpp`): `lfo` (Sine, Triangle, Saw up, Saw down, Square, Sample & hold, Smooth random, Custom: 16 drawn points `p1..p16`; `rate` 0.01..40 Hz or `sync` (Free, 1/32 .. 2 bars); `phase`; `mode` Free, Retrigger (on each note of its input), Song (synced: locked to the song position)); `envelope` (ADSR `attack`, `decay`, `sustain`, `release` from its input's notes; `mode` Retrigger or Legato); `follower` (stereo audio input; `attack` 0.1..500 ms, `release` 5..5000 ms, `gain` ±24 dB); `steps` (16 steps `s1..s16`, `steps` 1..16 long, `sync` (default 1/16) or `rate`, `glide`; locked to the song while it plays); `random` (`rate`/`sync`, `smooth`, `seed`); `macros` (`macro1..8`, eight outputs `m1..m8`); `midi` (MIDI to CV: outputs `pitch` (`low`..`high` note to 0..1, `glide`), `velocity`, `gate`, `pressure` (channel or poly); `priority` Last, Highest, Lowest). The LFO shapes and the random hash are the FX rack's (`mod_route.h`).
- **User modulators**: `caw/modulator.hpp` gives port helpers (`mod::output`, `mod::notesInput`, `mod::audioInput`), a `mod::Modulator` base with `render(const mod::Block&)`, `mod::decode` for MIDI 2.0 note, pressure, controller and bend messages, `mod::HeldNotes` (last, highest, lowest) and `mod::Ramp` (control-rate output drawn straight between blocks). `examples/cpp/modulator` is a Euclidean gate (outputs `gate` and `ramp`); the engine tests load it as a trusted native component and route it to a track.
- **Timing.** Modulators run in blocks of 16 frames on a grid counted from Play, each block hearing what its input played in those 16 frames, and its output applies 96 frames (2 ms at 48 kHz) later, given the transport of the time it applies. So every input is known whatever order the mix graph runs tracks in, and the result is the same for every device buffer size and for an export (tested: one render in 64-frame blocks and one in blocks of 1..512 frames give the same bits). At each Play every modulator restarts from 0 (state reset, grid at 0), as an export starts. A target's offset is worked out on the same grid and drawn straight between grid points (control rate with smoothing); a component sees per-frame values only while the offset moves. While stopped the modulators run on (free LFOs move, previews are modulated).
- **Loops.** Notes never make one (a track's notes don't depend on its sound), so an envelope from a track's notes may move that track. A modulator that hears audio makes its input layer feed every layer its links reach (also through modulators it moves): `modulationEdges` adds those edges to `validateRouting`, which refuses a loop through folder buses, sends, keys and modulation alike ("a layer can't hear itself"). Modulators moving each other in a loop are refused too ("modulation makes a loop"); otherwise each runs after the modulators that move it, whatever their order in the list.
- **Budgets.** 64 modulators, 256 links, 32 links per target, 8 outputs per modulator (`modulation_links.h`). The resolver's own 8 links (F6.3) don't apply: the host sums the links. A component with more than 8192 parameters, or more than 32 parameters with per-frame values in one block, plays the rest unmodulated.
- **Real time.** The control thread builds a plan (the modulators chain, rings of 256 frames of each output and each input heard, every target's links) and hands it over lock-free; the audio thread swaps it in at the next chunk and hands the old one back to be freed. A project update that keeps the same modulators, components and inputs keeps them running (phase, envelopes) and only sets values. Nothing on the audio thread allocates (`caw_rt_tests`: plan swaps, Plays, notes, knob and amount moves).
- **C API (version 19; 18 is the audio-engine branch's):** `caw_engine_set_modulator_param`, `caw_engine_set_modulator_bypass`, `caw_engine_set_modulation_amount` (a ring drag), `caw_engine_modulator_outputs` (each output at the last chunk, for a modulator's UI) and `caw_engine_modulation_offset` (a link's target's summed offset, for the knob's live dot); the readers never wait.
- **CPU** (wall time per second of audio at 48 kHz in 64-frame blocks, x86-64 GCC `-O2`, 2026-11-11, a scratch bench, two runs; two tracks of noise and saw with a filter each, about 7–9 ms alone): 1 modulator with 1 link adds about 1 ms; 4 modulators (LFO, random, follower) with 8 links into cutoff, resonance, volume and pan about 7–8 ms; 16 with 32 links about 11–13 ms; 64 with 128 links about 40 ms (4% of a core). Much of it is the targets themselves: a filter whose cutoff moves works its coefficients out per frame. [Assumption] a phone core is 3–5 times slower than this desktop core, so a handful of modulators costs a few percent of one core; measure on the S22+.

### Dynamics and drive: research and technique (fx-dynamics, 2026-11-11)

What the Dynamics and Drive effects are modelled on, and how. Kilohearts' current snapins are listed in its documentation ([kilohearts.com/docs/snapins](https://kilohearts.com/docs/snapins), read 2026-11-11: 3-Band EQ, Bitcrush, Channel Mixer, Chorus, Comb Filter, Compactor, Compressor, Delay, Distortion, Dynamics, Ensemble, Filter, Flanger, Formant Filter, Frequency Shifter, Gain, Gate, Haas, Ladder Filter, Limiter, Nonlinear Filter, Phase Distortion, Phaser, Pitch Shifter, Resonator, Reverb, Reverser, Ring Mod, Stereo, Shaper, Tape Stop, Trance Gate, Transient Shaper), with Faturator documented separately ([kilohearts.com/docs/faturator](https://kilohearts.com/docs/faturator), read 2026-11-11). Our code is original; the techniques below are textbook ones, in our own words.

- **Dynamics** (Kilohearts Dynamics: low and high thresholds and ratios dragged on the visualizer, attack, release, knee, in and out gain, mix; [Fact], their docs, 2026-11-11). What makes it good: one picture holds four processors (upward and downward compression, both expansions). Technique: a log-domain level detector and a static curve with a quadratic soft knee per threshold (Giannoulis, Massberg and Reiss, "Digital Dynamic Range Compressor Design — A Tutorial and Analysis", JAES 60(6), 2012; Zölzer (ed.), *DAFX*, 2nd ed., Wiley 2011, ch. 4). The instant-attack limit on the upward lift is our choice (a lifted transient otherwise spikes by the whole boost: +21 dB measured on a pluck before it, 2026-11-11).
- **Multiband with OTT** (OTT is Xfer Records' free plugin, after the "OTT" preset of Ableton's Multiband Dynamics, not a Kilohearts snapin; Kilohearts covers multiband through Multipass, a container). What makes it good: upward and downward compression per band at once makes quiet detail and loud parts meet, with a single depth knob. Technique: Linkwitz-Riley 4th-order crossovers (Linkwitz, "Active Crossover Networks for Noncoincident Drivers", JAES 24(1), 1976), whose low and high outputs sum to an all-pass, so the bands are phase-matched with all-passes; one detector and curve per band as above. OTT's per-band numbers are an [Assumption] (see the effect above).
- **De-esser** (no Kilohearts snapin). Technique: a compressor whose detector hears only the band above a frequency, applied to that band or to everything (Zölzer, *DAFX* ch. 4, de-essing as a sidechain-filtered compressor).
- **Clipper** (no Kilohearts snapin; Compactor covers clipping as a limiter and ducker, Limiter and Transient Shaper's Clip switch the rest). What makes one good: a transparent knee, oversampling so the harmonics don't fold back, and a guaranteed ceiling for mastering. Technique: a memoryless curve at 2^k times the rate between half-band filters (the Library's polyphase IIR half-band: Valenzuela and Constantinides, IEE Proc. G, 1983).
- **Phase distortion** (Kilohearts Phase Distortion: drive, normalize, tone, bias, spread, mix; "similar to feedback FM"; [Fact], their docs, 2026-11-11). Technique: a delay line read at a position the signal itself moves (self phase modulation), with fractional-delay interpolation (J. O. Smith III, *Physical Audio Signal Processing*, CCRMA online book, "Delay-Line Interpolation"). The fixed centre makes the latency constant and declarable. [Assumption] Kilohearts' exact mapping of drive to phase is not published; ours swings the delay up to ±46 frames.
- **Distortion types** (Kilohearts Distortion: drive, bias, spread, type overdrive / saturate / foldback / sine / hard clip / quantize, dynamics, mix; Bitcrush: rate, bits, ADC and DAC quality, dither, mix; Faturator: drive, fuzz, color, mix, stereo; Shaper: a drawn curve with drive, overflow and a DC filter; [Fact], their docs, 2026-11-11). Covered by the saturator's eleven modes, spread and dynamics; aliasing is held down by oversampling (2×, 4× at High) as Välimäki and others recommend for virtual-analog nonlinearities (e.g. Esqueda, Pöntynen, Parker and Bilbao, "Virtual Analog Models of the Lockhart and Serge Wavefolders", Applied Sciences 7(12), 2017, on folders' aliasing). Not covered yet (follow-ups): Bitcrush's ADC/DAC quality and dither, Faturator's color pre-emphasis and stereo turbo as their own knobs, and Shaper's drawn curve.
- **Transient or envelope follower to modulation** (no Kilohearts snapin; Phase Plant's envelope follower modulator). Not built: the graph executor has modulation outputs and links (F6.3), but projects and the app don't route them yet, so a follower's output would go nowhere. A follow-up once modulation links reach projects.

- **The overflow lane** (`kLaneRest` / `CAW_LANE_REST`, note id 0, last): `VoiceLanes::laneFor(noteId)` falls back to it, so every voice without a slot of its own goes through the overflow chain; the drums use it only for hits on their main output. It is never ENDED.
- **Slots:** chosen at each note-on's frame (lowest free; over the budget the oldest ended slot fades, else the oldest released note's slot fades while its sound crossfades into the overflow chain, and the new note takes a free chain; else overflow; held notes are never stolen). A slot's chain runs from its note's first frame; after ENDED it rings for max(its declared tail, 128 frames), at most 2 s, past its note's last nonzero sample, then fades out over 10 ms and frees (its chain is reset). - **Per-note sources (step 5, `modulation_links.*`):** a link's `source` may be `note.pitch` (pitch with bend / 127), `note.velocity`, `note.pressure`, `note.timbre`, `note.gate` (1 while held) or `note.age` (0 at the note-on to 1 after 2 s), `output` 0, target type `noteComponent` only; each slot works them out per frame from its own note's events and adds any modulator link into the same knob (`ModChainKind::NoteFx`, once per chunk). At most 64 note-source links a layer; the amounts move live with `caw_engine_set_modulation_amount`.
- **Budget:** `noteFxBudget(B, quality)`: Eco min(B, 4), Normal B, High min(B, 16), read at each note-on (so a quality change applies to the next notes). Slots are allocated for B; nothing changes on overload.
- **C API 22** (20 and 21 are left for parallel branches): `caw_engine_note_fx_stats(e, layer, CawNoteFxStats*)` (size-tagged: voices, budget, active, active_mask, overflowing, overflowed, stolen; never waits) and `CAW_NOTE_COMPONENT` (0x40000000) on a component index for `caw_engine_set_component_param`, `_bypass` and `caw_engine_component_display` (the newest note's slot). - **Refusals:** per-note FX on a layer without a native instrument, on an instrument that doesn't declare PerNote or PerVoice ("has no voice bus"), or with an effect that can't run per note ("can't run per note: …") fail the project update before anything changes.
- **Tests:** `engine/tests/note_fx_test.cpp` (each slot of two notes with different bends and pressure through a pitch- and pressure-driven filter equals a solo render of that note bit for bit; the mix is their sum; overflow, steals and a released note's crossfade, deterministic; tails ring then free; the quality caps; refusals; the project JSON; the host at uneven block splits and the Engine live at 64-frame and uneven buffers and offline, bit-identical; knobs fanning out, stats; the C API), `engine/tests/note_fx_rt_test.cpp` (no allocation on the audio thread through notes, steals, knob moves, quality changes, rack swaps, voice changes, per-note FX off and on).

### Modes, pads and the note map

- **4 banks (A..D) of 16 pads**, 64 in all; pad index 0..63 (A1 = 0, B1 = 16, D16 = 63). Every pad has the same parameters. `mode`: **Kit** (each pad answers its note) or **Single** (pad A1 answers every note: one sound per track).
- **Notes:** a pad's `note` is Auto (the default: `base_note` + its index, so bank A plays 36..51, B 52..67, C 68..83, D 84..99), Off, Any other (plays when no other pad took the note), or a MIDI note 0..127. Several pads may share a note (they layer). Default `base_note` 36 (C2, C4 = 60): **[Fact]** bank A then lands on the General MIDI percussion keys 36..51 (GM 1 Sound Set: 36 bass drum, 37 side stick, 38 snare, 39 clap, 40 electric snare, 41/43 floor toms, 42 closed hat, 44 pedal hat, 45/47/48/50 toms, 46 open hat, 49 crash, 51 ride), which is why the 808 kit's sounds sit where they do. **[Assumption, community reports read 2026-11-11 (mpc-forums.com): later MPCs default to a chromatic map from C1; the Akai MPD218 guide says it has 3 banks of 16 pads but its note map is in a separate document not checked]** 16 chromatic notes per bank from a configurable start is the common pad-controller layout, and Ableton's Drum Rack uses the same 36-upward chromatic layout; banks of 16 consecutive notes follow it.
- **Channels:** `channel` (Any, 1..16) filters the notes the instrument takes; a pad's `chan` is Kit (follows `channel`), Any, or 1..16 (e.g. 10, the GM drum channel). **[Assumption]** the app passes a hardware controller's channel in the note events (`NoteMessage::channel`); today's previews send channel 1.
- **Pitch tracking:** `track` Off plays the pad at its fixed pitch; On plays it `note − root` semitones from its tuning (`root`, default 60). In Single mode every note is tracked; in Kit mode a tracking pad on its own channel (`chan` 1..16) takes every note on that channel (an 808 bass on channel 2 beside the kit), and on Kit/Any only its own note. `mono` On: one voice; with tracking, a note played while another is held glides there (`glide`) without a new attack (an 808 slide), and releasing it glides back to the newest held note.
- **Triggering:** `trig` One-shot (note-offs ignored) or Gate (a note-off fades the voice over `release`). `poly` 1..4 voices per pad (a new hit past it fades the oldest over 5 ms; `mono` is 1); a pool of 64 voices serves all pads (when it is full the oldest fading voice, else the oldest, is taken). `choke` 1..8: a hit fades every other pad's voices in its group over 5 ms (to −80 dB), so an open hat is cut without a click.
- **Hardware pads:** a pad's `note` and `chan` are its note map; **note learn** is the app's: it watches the display's last-note fields (key, channel, velocity and a count that changes with every note, [display data](#display-data-of-the-drums)), then writes the key into the pad's `note` (`kNoteFirst` + key). **Pressure** (polyphonic aftertouch, per note) is a modulation source with one amount per destination (the `press` layer): `press_damp` 0..1 (the voice fades over 30 ms / (pressure × amount): squeezing a cymbal), `press_choke` (past half pressure the voice fades out in 5 ms), `press_tone` ±1 (±4 octaves on every filter and the resonator's brightness), `press_pitch` ±12 st, `press_level` ±1 (±12 dB), `press_drive` 0..1 (the drive × 2^(3 × pressure × amount), when the drive is on). It is read once per control period (16 frames).

Every parameter has a `group` (`ParameterDescriptor::group`, `"group"` in `caw_engine_components`): `kit/main`, `kit/glue`, `kit/drive`, `kit/room`, `kit/eq`, `kit/clip`, or `<pad>/<layer>` with the layer one of `pad`, `press`, `body`, `penv`, `sub`, `click`, `noise`, `metal`, `res`, `smp`, `drive`, `filter`, `eq`, `dyn`, `space`, `macro`, `var` (in that order; `caw_drums_info` lists each layer's suffixes and display name). Bank A's defaults are the 808 kit's sounds (a fresh instance plays); banks B..D default to empty pads (every layer off). **Why flat ids (to confirm with the owner, [decisions](decisions.md#2026-11-11-one-drum-instrument-built-choices-to-confirm)):** the component model has no parameter arrays or "selected pad", and every C.A.W. feature that moves a knob (automation lanes, modulation, MIDI learn, presets, undo, the app's knob widgets) addresses a parameter by id. Flat ids keep every pad's every knob automatable with no new machinery. The cost: a 2.9 MB descriptor in `caw_engine_components` (2.6 MB without spaces), and about 6 MB of parameter state per instance. The engine was made to handle it: duplicate ids are checked by sorting above 256 parameters (`module.cpp`), a component chain looks ids up in a map above 64 (`component_chain.cpp`), and the processor reads a pad's knobs only while it sounds, once a block when they hold still.

### How a voice sounds

A hit on a pad reads its knobs at the hit's frame, applies the macros and the hit's variation, and starts a voice. Layers sum: body + click + noise + metal + sample (+ the sub when it runs Through effects), then the resonator (struck by its exciter, driven by `res_input` × that sum) is added. Then drive (with its low cut, high cut and mix; pre or post the filter), the filter, the EQ, the transient shaper, the compressor, the clipper (a Clean sub joins its input), the fades (choke, gate release, pressure damp), then level and pan (a balance: the centre at full level on both sides, the far side falling along a quarter cosine). A Clean sub is added to both sides whole, after the pan. Width adds a side signal (the voice 0.4 ms later through a 4th-order high-pass at `width_hz`, × width) to the left and takes it from the right, so the sum to mono is unchanged and the low end stays mono. The room hears each voice × `room_send` (not its Clean sub). Voices go to their output's bus; the main bus runs the kit effects (glue, drive, EQ, the room's return at `room`, the clipper, in that order), then the volume.

- **Body pitch, Curve mode:** f(t) = f_end + (f_start − f_end) × e(t), f_end = `body_freq` × 2^(tune / 12), f_start = f_end × 2^(`body_pitch` / 12), with e(t) the pitch envelope (60 dB in `body_ptime`). This is the analog swept sine of the 808 and 909 kicks (the pitch moving in Hz along an exponential), so `body_pcurve` 0 matches them; + bends toward a fast drop with a tail, − toward a straight line.
- **Body pitch, Points mode (the shape editor):** the pitch in semitones over f_end runs from `body_pitch` at the hit through four points: segment N lasts `penv_tN` and ends at `penv_pN`; after the last, it holds `penv_p4` (so p4 0 settles on `body_freq`; a non-zero p4 is a held offset). A segment's curve c: 0 straight; c > 0 fast then slow, 1 − (1 − u)^k; c < 0 slow then fast, u^k; k = 1 + 7|c|, u the segment's progress. Semitones move linearly in pitch, so a straight segment is an even glide in octaves. Punch scales the times (× 2^(−0.7 punch)), as it does `body_ptime`.
- **Envelope curves** (`*_dcurve`, `body_pcurve`): 0 is the analog exponential (60 dB in the time); +c blends in an exponential 6 times as fast (a sharp drop with a long tail); −c blends in a straight line (a held, gated sound). Envelopes end below about −94 dB.
- **Sub:** a sine (or triangle, or warm sine) at f_end × 2^(−oct + fine / 12), with its own attack, hold, decay and curve, a tanh drive and a one-pole low-pass; `sub_follow` f multiplies its frequency by (body pitch / f_end)^f, so 1 rides the body's drop and 0 holds still. It sounds with the body off too (it takes `body_freq` and the pad's tuning).
- **Character macros** (fixed curves; each is a real, automatable parameter and moves the voice's working values, never the knobs themselves): **Punch** m: `body_pitch` + 12m st, `body_ptime` and the shape's times × 2^(−0.7m), click level × 2^(1.5m), transient attack + 0.5m. **Tone** m: `cutoff` × 2^(2m), noise frequency and click tone × 2^(1.5m), metal filters × 2^m, resonator brightness + 0.35m, `eq_high` + 6m dB. **Snap** m: click level × 2^m, noise level × 2^(0.8m), transient attack + 0.4m. **Length** m: every decay × 2^(2m) (the holds and the filter decay × 2^m). **Dirt** m > 0: drive × 2^(2m) (a pad with drive off gets Soft at 1 + 6m), `comp` + 0.3m; m < 0 pulls the drive toward 1. **Pitch** m: + 12m st on every pitched layer.
- **Variation** (from a hit at velocity v; x = v − 1): level × (1 + `vel_level` x), pitch + `vel_pitch` x st, the pitch drop's depth × (1 + `vel_punch` x), every decay × 2^(`vel_decay` x), the filters, the resonator's brightness and the click's tone (+ half as much) + 2 `vel_tone` x octaves, the mallet's strike × 2^(−toneOct / 2) longer (so a soft hit excites fewer high modes: velocity changes the spectrum, not just the level), click level × (1 + `vel_click` x). Per hit, deterministic: u = a hash of (`seed`, the pad, its hit count, which value) in −1..1; pitch + `rnd_pitch` u cents, decays × 2^(0.5 `rnd_decay` u), tone + `rnd_tone` u octaves, pan + `rnd_pan` u, level + 6 `rnd_level` u dB, strike position + 0.3 `rnd_pos` u. The hit counts restart at a reset and when the transport starts playing, so a render repeats.

### Quality

Eco: no oversampling (drives, clippers, kit drive), the metal's squares naive (no band-limiting), 8 resonator modes, the room light (`lib::Reverb::setLight`), display 30 times a second. Normal: drives and clippers 2× oversampled (`lib::Oversampler2x`), band-limited squares (polyBLEP), 16 modes. High: drives and clippers 4× (two half-band stages), the metal bank run at 2× and decimated, 32 modes. Crush and Decimate are never oversampled (their aliasing is the sound).

### Samples

- **Where they come from:** a component entry's `"samples"` ([project file](#project-file-json)): `{"slot": n, "path": file}` for the user's WAV files, or `{"slot": n, "builtin": name}` for the **built-in pack**: every sound of the library (the `sounds` names in `caw_drums_info`, e.g. "808 Kick", "Crash") rendered by the engine itself (a full-velocity hit on pad A1, until silent, at most 6 s, mono at the engine's rate), so there is nothing to license. Slot n is pad n (A1 = 0).
- **Loading:** on the control thread when the project's chain is built or updated (`applyComponentSamples`); a slot whose source is unchanged is kept. The new buffer is handed to the audio thread through a one-slot lock-free exchange (`SampleHandover`): the audio thread takes it at its next block, a voice still playing the old one stops its sample layer, and the old buffer is freed later on the control thread. The audio thread never allocates or frees.
- **Untrusted files** (`decodeWavBytes`): RIFF/WAVE only; PCM 8/16/24/32-bit and IEEE float 32/64, 1..8 channels (mixed to mono), 8..384 kHz, the extensible format's sub-format; every chunk size is checked against what is left (a lying header is refused, a truncated data chunk yields what is there), non-finite floats read as 0 and values are held to ±4. Limits: a file over 256 MB is refused unread; 30 s per slot (the start is kept); 64 MB of samples per instance. Resampling to the engine's rate is cubic (Catmull-Rom) after a two-pole low-pass when it goes down. **[Assumption]** good enough for one-shots; a windowed-sinc resampler would be cleaner. A file that fails empties its slot and the project still loads.
- **Not yet:** samples are mono (a stereo file is mixed down); no loop points.

### Outputs and exploding to tracks

- `out` (Main, Out 2..9) is stored per pad and the processor keeps nine buses, but **the instrument chain has one stereo output** (`ComponentChain::isInstrument`: one event input, one stereo audio output), so today Out 2..9 are summed into the one output after the kit effects (a pad sent there skips glue, drive and room). Multi-output instruments routed into child tracks need the chain, the mixer graph and the project's routing to carry a component's extra outputs: **a follow-up**, not built.
- **Explode (chosen for the "one track per pad" workflow):** `caw_drums_explode(entry)` returns one track per used pad, each a Single-mode Drums carrying that pad's sound on A1 (and its sample in slot 0), the notes it answers (`[key]`, `"other"`, `"all"` or `{"channel": n}`) and its choke group; the app creates the tracks and moves those notes into them. Choke groups across tracks and the kit effects (returned as `"kit"`) don't follow; the app can put the kit's effects on a bus.

### Randomize and mutate

`caw_drums_randomize(type, seed, amount, pad, current)`: pure and deterministic. Each drum type has a rule: the layers that must be on and, for its defining knobs, the range a random sound draws from (a kick: `body_freq` 38..80 Hz, `body_pitch` 4..40 st, `body_ptime` 10..120 ms, `body_decay` 0.15..1.8 s, the click's level, tone and length, the wave and click type, the sub (on a third of the time; its octave, decay and level) and `vel_punch`; a snare: body 150..280 Hz, noise 0.8..5 kHz and 0.08..0.4 s; hats: metal 300..700 Hz, high-pass 5..11 kHz, decay 20..80 ms (open: 35..80 ms with openness 0.4..0.8); toms 60..300 Hz; cymbals; rim; cowbell; shaker; perc; 808 bass; FX), plus every type's effects and variation within mild ranges (the drive now may draw Asymmetric, and a quarter of draws turn the Soft clipper on). The pitch shape's mode is never drawn, so a random kick settles where its `body_freq` says. With no current sound (or another type), it starts from a seeded pick among the library's sounds of that type and moves fully (amount 1); with one, it mutates: each knob moves `amount` of the way toward its random target in the knob's own taper, each listed choice switches with probability amount / 3, and every drawn knob is clamped into the type's range. The result is level-matched: the engine renders 0.4 s of it and sets `level` so a hit peaks near −1 dBFS. The pad's note, channel, level, pan, choke group and output stay where they were.

### Migration of the old drums

`org.caw.drum.kick`, `.snare`, `.hats` and `.kit` (removed from the registry) migrate in `migrateLegacyDrum` (`builtin_drums_sounds.cpp`), reached through `migrateLegacyInstrument` (project loading, sample packs, `caw_migrate_instrument`; the app's `ProjectDoc.resolveInstruments` lists them in `ComponentUseDoc.retiredInstruments`). ### Research (2026-11-11; sources read on that date)

- **[Fact]** The TR-808 bass drum is a bridged-T network (a band-pass) rung by a 1 ms pulse, with an envelope that moves its centre frequency for the first few milliseconds (Werner, Abel and Smith, "A Physically-Informed, Circuit-Bendable, Digital Model of the Roland TR-808 Bass Drum Circuit", DAFx-14). Here: a swept sine (the body) with a short pitch envelope, rather than a circuit model.
- **[Fact]** The 808's cymbal and hi-hats share a bank of six square oscillators (one hex Schmitt-trigger chip), nominally 205.3, 304.4, 369.6 and 522.7 Hz, two trimmed to 540 and 800 Hz, summed and filtered by band-passes (Werner, Abel and Smith, ICMC-SMC 2014, "The TR-808 cymbal: a physically-informed, circuit-bendable, digital model"). Here: the 808 metal set. **[Assumption, a 2015 Web Audio recreation, outputchannel.com]** the cowbell uses the 540 and 800 Hz pair through a band-pass; the AES 137 paper ("More Cowbell", 2014) was not read in full.
- **[Fact]** Roland describes the TR-909 kick as separate circuits for the attack and the resonant body (an interview quoted by Computer Music); clones list attack, decay, tune decay and level controls (Tiptop BD909). Here: the body's pitch envelope and a separate click layer. **[Assumption]** the 909 kick's wave is a shaped triangle (common knowledge, not checked against a schematic): the 909 Kick preset uses a triangle with `body_shape`. **[Assumption]** the 909's hats were 6-bit samples (widely reported, not checked): the 909 hats are crushed.
- **[Fact]** An ideal circular membrane's modes sit at the zeros of Bessel functions over the lowest (1, 1.593, 2.136, 2.296, 2.653, ...; computed here by bisection, and checked against Sound On Sound's "Synthesizing percussion" and Wikipedia's "Vibration of a circular membrane"); air loading pulls a real drum's toward harmonic. Here: the Membrane model, its strike weights |J_m(j_mn r)|. The plate, bar and tube ratios are textbook (a simply supported rectangular plate, a free-free bar's (β_k / β_1)², a closed pipe's odd harmonics); the bell's are **[Assumption]** typical tuned-bell partials; the cymbal model's spread is made up.
- **[Fact, reviews and tutorials, MusicRadar and Audiotent]** Sonic Academy Kick 2: a sub with a pitch envelope drawn as a Bezier curve with snap-to-note, up to three click layers, key tracking to tune the kick to the song's key. Here: `body_pcurve`, the click layer, `track` with `root`. **[Fact, Microtonic 3.1 manual, manualsdir.com]** Microtonic: an oscillator and a noise section with a multimode filter and three envelope modes, an oscillator/noise mix and velocity to the noise. Here: the noise layer's modes and filters. Arturia DrumBrute/Spark, Ableton Drum Sampler/DS Kick, D16 Drumazon/Nepheton, Elektron's machines, AudioRealism ADM and Bazzism were not researched in detail this session: **[Assumption]** their common controls (tune, decay, pitch envelope amount and time, click, drive, tone, choke and open/closed hats) are covered above.
- **[Fact]** General MIDI's percussion map (keys 35..81 on channel 10) and the default pad layout: see the note map above.
- **Per type, what the controls are for (read 2026-11-11):**
  - **Kicks, layered.** **[Fact, production guides: soundbridge.io "How to layer kick drums", Ableton's "Make a perfect kick drum" (Lenny Kiser)]** a modern kick is built from a top layer (the attack: click and punch), a body layer (tone, around 130..170 Hz of "punch") and a sub layer (the low end), with a slight fade at the start of the sub so it doesn't fight the attack, and their phase kept aligned. **[Fact, Cymatics "How to make dubstep"]** a dubstep kick must cut through the bass: its weight sits at about 50..60 Hz. **[Assumption, common practice not checked against one source]** riddim and dubstep kicks are clipped hard (a low crest factor) with the distortion kept off the sub. Here: the body as the punch layer with a drawn pitch shape, the Clean sub with its own attack (5 ms default), the drive's low cut (the sub stays clean) and mix, and the clipper; the Dubstep Kick preset measures a 54 Hz fundamental and an 8.3 dB crest factor.
  - **808 long and short.** **[Fact, Werner, Abel and Smith, DAFx-14, above]** the 808 kick is one decaying swept tone whose decay knob sets its length; **[Assumption]** trap and drill use it decays of 2..4 s, electro and house under 0.4 s. Here: the same body, the decay apart (2.95 s against 0.23 s).
  - **Acoustic kick and snare.** **[Fact, Fletcher and Bassett's bass-drum study (JASA; physics.byu.edu abstract) and Rossing, "The acoustics of percussion instruments", Physics Today 45(3), 1992]** a bass drum is two membranes and the air between them, its spectrum changing with where and how hard it is struck; a snare's lowest modes are pairs of the (0,1) and (1,1) membrane modes coupled through the air, and the snare wires buzz against the lower head. **[Fact, mixing guides, gear4music "Kick drum EQ" and soundsheavy "Drum EQ frequencies"]** a kick's weight sits at 50..100 Hz, its boxiness at 200..400 Hz and the beater's click at 2..5 kHz (felt lower than plastic); a snare's body at 150..250 Hz. Here: the Membrane resonator (struck off centre, its position varied per hit), the head's short pitch drop, the Pop click, the boxiness cut at 400 Hz, Snappy wires that follow the head, velocity on brightness and decay, and the room send. **[Assumption]** a stick's contact lasts a few milliseconds (a thesis on snare drums gives 3..6 ms; KTH master's thesis, Wagner 2006): the mallet exciter lasts 0.5..2.5 ms, longer for a soft hit.
  - **Cymbals.** **[Fact, Sound On Sound "Analysing metallic percussion"; Rossing and coauthors on gongs and cymbals (Legge and Fletcher 1989, UNSW)]** cymbal modes are inharmonic; a hard hit spreads energy upward into a near-noise spectrum over the first few hundred milliseconds, the high modes die first and the last energy sits in the few-hundred-hertz modes; hi-hats are clamped, rides pivot and crashes swing freely. Here: FM-paired or square metal plus noise, the Cymbal resonator, decay curves for the fast-then-long fall, and pressure to damp or choke. **[Assumption]** the upward cascade itself (a slow build of high partials) isn't modelled; the noise share stands in for it.
- **Not found:** a measured beater contact time for bass drums, and published decay times for crash and ride; both are **[Assumption]** values tuned by measurement against the ranges above.

### Audio assets

- **Decoding:** WAV (PCM 8–32-bit, float, extensible), FLAC and MP3 through miniaudio 0.11.25's bundled dr_wav, dr_flac and dr_mp3 ([decisions](decisions.md#2026-11-11-audio-assets-clips-sampler-and-input-wp-j-choices-to-confirm)), compiled a second time inside the core with every function `static`, so it never meets the device copy. Files are untrusted: at most 1 GB on disk and 3 hours long, every read bounds-checked by the decoders, samples clamped to ±8 and non-finite ones made 0; a file that fails gives an error, never a crash. The decoder sets its limits from the file's real rate and channel count once it has read the header, keeps only the first two channels while decoding, and stops as soon as the kept samples (4 bytes × at most two channels) would pass what the store's budget has left (the budget less the assets in use) or 3 hours; the resampled planes are checked against the same before they are made (a fuzz test feeds random bytes behind a RIFF header).
- **Resampling:** once, at load, to the engine's rate: a Kaiser-windowed sinc (β 9, 32 zero crossings at the lower rate, cutoff 0.96 of its Nyquist), deterministic maths (`detSin`). A source at 4× the engine rate or more is first halved by 31-tap Kaiser halfband stages (β 11, passband to 0.12 and stopband from 0.38 of the stage's rate) until it is below 4×, so the final kernel stays at most about 133 taps a side (768 kHz to 48 kHz directly was about 1,070). More than two channels keep the first two; mono stays mono (heard in both sides).
- **The store** (`AssetStore::global()`, one per process): an asset is keyed by path and engine rate and reloaded when the file's size or time changes; clips and zones naming the same file share one copy (refcounted). The budget (1 GiB by default, `caw_asset_store_set_budget`) counts decoded bytes; when a load needs room the least recently used asset nothing plays is dropped, and a load that still doesn't fit is refused with a message. Decoding happens on whatever thread asks (the app's worker isolate for `caw_asset_load`, or the control thread during a project update): preload long files with `caw_asset_load` so the update finds them cached.
- **Peaks:** min/max per 256 frames per channel, then levels of 512, 1,024, … frames; `caw_asset_peaks` answers any range and bucket count from the coarsest level no wider than a bucket (or from the samples when zoomed further in).

### Audio clips

A layer with `"audio_clips"` (and/or `"input"`) is an audio track: the engine plays it with the built-in instrument `org.caw.audio-track` (internal: `caw_engine_components` never lists it; it can't also name an `instrument`; a folder can't have clips), so a clip goes through the track's inserts, volume, pan, sends, folder buses, sidechain keys and latency compensation like any instrument, live and in every render (song renders, stems, exports).

```json
"assets": [ { "id": "a1", "path": "/abs/loop.wav", "bpm": 120 } ],
"layers": [ { "id": "t1", "name": "Vox", "volume": 0.8,
  "input": { "channel": 0, "channels": 1, "monitor": "auto", "armed": true },
  "audio_clips": [ { "id": "c1", "asset": "a1", "start_steps": 16, "length_steps": 32, "offset_seconds": 0.25,
    "gain": 1, "fade_in_seconds": 0.01, "fade_in_curve": "linear", "fade_out_seconds": 0.5, "fade_out_curve": "equal_power",
    "reverse": false, "loop": false, "loop_start_seconds": 0, "loop_end_seconds": 0, "pitch": 0,
    "mode": "fixed", "stretch": "wsola", "source_bpm": 120, "mute": false } ] } ]
```

- `"assets"` (project level, optional) names files once: `id`, absolute `path`, optional `bpm` (the source tempo musical clips default to). A clip names `"asset"` or a `"path"` directly. An unknown asset id refuses the project; a file that fails to load leaves its clip silent (the rest plays).
- **Placement:** `start_steps` and `length_steps` are sixteenths and may be fractional (a recorded take lands off the grid); the sample is `floor(steps × samples per step + 0.5)`, as notes. The song lengthens to reach the last clip's end. At most 4,096 clips a track and 16 sounding at once (more overlapping are skipped).
- **Source:** `offset_seconds` into the file at its own speed; `reverse` reads the file backwards (offset and loop points then count from its end); `loop` repeats `[loop_start_seconds, loop_end_seconds)` (0 end: the file's end) to fill the clip; past the file's end without a loop is silence.
- **Level:** `gain` linear 0..3.98 (+12 dB); fades in seconds of output with curves `linear`, `equal_power` (sine), `s_curve` (raised cosine), `fast` (1 − (1 − u)²), `slow` (u²).
- **Speed and pitch:** `mode` `"fixed"` plays at the file's speed (a tempo change moves where it starts, never how fast it plays, and a fixed clip already sounding carries on from the source position it is at; the app sets `length_steps` from the file's length at the current tempo); `"musical"` follows the tempo: the source moves `bpm / source_bpm` times real time, so it stays locked to the bars (needs `source_bpm` or the asset's `bpm`). `stretch` `"wsola"` keeps pitch at any speed and `pitch` (semitones −48..48) transposes without changing length; `"varispeed"` resamples, so pitch moves with speed (a musical varispeed clip at another tempo is transposed by it; in a fixed clip `pitch` changes the speed too, and the app should change its length). A clip at its file's speed with pitch 0 copies samples exactly.
- **The readers** (`time_stretch.*`): exact copies; cubic Hermite (Catmull-Rom) for varispeed, with no anti-alias filter when reading faster than real time; WSOLA (Verhelst and Roelands 1993, as reviewed by Driedger and Müller 2016): 30 ms periodic-Hann frames at 50% overlap whose analysis positions follow the arrangement, each moved by up to half a hop to best continue the last (cross-correlation of the mono sum, every 4th lag on every 4th sample, then refined to the sample), then a Hermite pitch stage. Direct and varispeed reading hold no state, so playback from anywhere sounds as passing through; a WSOLA voice starts afresh at a seek or a loop wrap (deterministic from that point). Everything is the same at every block size (tested at 37, 64 and 512).
- **Declick:** a clip voice cut by a seek, a loop wrap, stop, a mode change, a mute or an edit fades out over 4 ms, reading on where it was (the player keeps its own continuous time), while a voice that starts mid-clip fades in over 4 ms; a voice starting at its clip's start is left as authored. A clip's `loop` seam crossfades over 4 ms (at most half the loop) and keeps the loop's period: into the audio before `loop_start` when there is some, else from the audio after `loop_end`, else (the whole file looped) a dip of 2 ms out and 2 ms in. On a tempo change, musical clips follow the new grid, declicked. The 4 ms is to confirm ([decisions](decisions.md#2026-11-11-audio-review-fixes-declick-lengths-to-confirm)).
- **Edits** from roadmap 3.4 (trim, split, move, duplicate, offset, loop, fade, gain, reverse) are these fields: the original file is never changed (3.5). Selection, snapping, grouping and undo are the app's.

### Sampler (`org.caw.sampler`)

An instrument (one note input, stereo out) that plays zones over the asset store. Its state (`"state"` base64 in the instrument entry, `caw_engine_set_component_state` while it plays, version 1) is JSON `{"zones": [zone, ...]}` (at most 4,096 zones, 4 MB). A project update with a changed state reloads the zones of a kept sampler; voices of the old zones fade out over 5 ms on them (the sampler keeps the old zones until they are done).

Zone keys mirror SFZ opcodes; positions are frames of the sample file at its own rate:

| Key | Meaning (default) |
|---|---|
| `path` | the sample file (required) |
| `lokey`, `hikey`, `pitch_keycenter` | key range 0..127 (0, 127) and root (60) |
| `lovel`, `hivel` | velocity range 1..127 |
| `tune`, `transpose`, `pitch_keytrack` | cents, semitones, cents per key (100) |
| `volume`, `pan`, `amp_veltrack` | dB, −100..100 (balance), velocity sensitivity in % (100) |
| `offset`, `end` | first and last frame played (end 0: the file's end) |
| `loop_mode` | `no_loop`, `one_shot` (note-off ignored), `loop_continuous`, `loop_sustain` (loops while held, then plays on); loop points without a mode loop continuously |
| `loop_start`, `loop_end`, `loop_crossfade` | the loop's first and last frame; crossfade seconds (equal power, into the audio before the loop start) |
| `seq_length`, `seq_position` | round robins: a zone plays on hit `seq_position` of every `seq_length` matching ones (each zone counts its own hits) |
| `lorand`, `hirand` | random round robin: plays when a per-note random 0..1 (seeded, deterministic) falls in [lorand, hirand) |
| `group`, `off_by` | choke: a zone of group g cuts voices whose zone has off_by g (5 ms) |
| `ampeg_attack`, `ampeg_decay`, `ampeg_sustain` (%), `ampeg_release` | this zone's envelope instead of the instrument's |

Parameters: `gain` (dB −60..12), `attack`, `decay`, `sustain` (0..1), `release`, `velocity` (sensitivity 0..1), `tune` (cents ±100), `transpose` (±48), `filter` (Off, Low-pass, High-pass, Band-pass: the Library's SVF per voice), `cutoff` (20..20,000 Hz), `resonance` (Q 0.5..20), `filter_env` (octaves ±8), `filter_key` (key tracking 0..1), `filter_attack`/`decay`/`sustain`/`release`, `polyphony` (1..64; at the limit the oldest releasing voice is stolen, else the oldest, and it fades out over 5 ms in its slot while the new note starts in one of 8 spare slots; voices fading out do not count). A note that matches several zones layers them. Samples are read with cubic Hermite interpolation.

### SFZ support

`caw_sfz_import` reads a `.sfz` (at most 4 MB) into the state above: `<control>` (`default_path`), `<global>`, `<master>`, `<group>`, `<region>` with inheritance, `//` and `/* */` comments, `#define $NAME` (expanded in one pass: at each `$` the longest defined name, and a replacement is not expanded again; refused past 16 MB expanded), note names (`c4` = 60, `#` and `b`), sample paths with spaces and backslashes, relative to the file's folder. Opcodes read: `sample`, `key`, `lokey`, `hikey`, `pitch_keycenter`, `lovel`, `hivel`, `tune`, `transpose`, `volume`, `pan`, `pitch_keytrack`, `amp_veltrack`, `offset`, `end`, `loop_mode`/`loopmode`, `loop_start`/`loopstart`, `loop_end`/`loopend`, `loop_crossfade`, `seq_length`, `seq_position`, `lorand`, `hirand`, `group`, `off_by`, `ampeg_attack`, `ampeg_decay`, `ampeg_sustain`, `ampeg_release`, `trigger=attack`. Left out, each with a warning: regions with another `trigger` (release, first, legato), `#include`, `<curve>`/`<effect>`/`<midi>`/`<sample>` sections and every other opcode (named with its count: filters, LFOs, per-region EGs beyond ampeg, CC modulation, crossfades by key or velocity). Missing samples are warned about too. `caw_sfz_export` writes the same opcodes back (paths relative to the `.sfz` where inside its folder; `copy_samples` copies the files, unchanged, into `samples/`, named uniquely against what is already there without regard to case and never over an existing file, and only regular `.wav`/`.flac`/`.mp3` files whose first bytes say so, up to 1 GB, since a project's zone path could otherwise copy any readable file into a shared folder); frame opcodes are clamped to 9e15 (as are `caw_asset_peaks` times) before the integer cast; export then import gives the same state (tested).

### Audio input and recording

- **The device** (owner, 2026-11-12, [decisions](decisions.md#2026-11-12-audio-keeps-playing-when-the-microphone-is-busy-or-the-app-is-behind-owner)): the input is a capture device of its own beside the playback device (never miniaudio duplex), opened and closed alone by `caw_audio_configure_input` while the output plays on: any capture device the backend lists (AAudio: the default input, which Android routes), 1..32 channels, shared mode, the engine's rate. Its callback pushes into the input bridge (`engine/src/input_bridge.h`, a lock-free single-producer, single-consumer ring of 65,536 samples); the output callback pulls the input for each block it renders (`DeviceRender::render`), and whatever is missing (closed, starting, starved, silenced, disconnected) is silence, so the output's sound never depends on the input (`input_disconnect_while_playing_leaves_the_output_unchanged`, bit for bit). The output starts reading once two capture periods plus one output period, plus what the output's block FIFO renders ahead (up to 63 frames), are queued (in the engine's frames: the bridge runs at the engine's rate). The two devices' clocks drift by up to a few hundred ppm, so the output reads at a slightly changing rate (4-point Hermite interpolation), steered by a slow PI loop on the smoothed fill (poles near 0.3 rad/s, at most 2000 ppm), which holds the fill, and the input's delay, at that starting fill with no gaps, splices or creep (`input_bridge_follows_clock_drift_with_no_gaps_splices_or_creep`: ±100 and ±500 ppm for five minutes, the delay within one capture period). Only a real discontinuity is faded: a start or a refill after the input ran dry fades in and out over 64 frames, and a queue eight periods past the fill (the output stalled while capture ran on) jumps back through a 64-frame crossfade. NaN/Inf become 0. Device opens and closes run under an operation lock, the shared state under the device lock only for the swap, so `caw_audio_status` and `caw_audio_latency` never wait for a microphone to open; before any device is uninitialised, reroute jobs miniaudio queued for it are drained ([Fact] miniaudio 0.11.25 source, read 2026-11-12: a reroute job posted from the AAudio error callback could otherwise run after `ma_device_uninit` destroyed the device's reroute mutex). `missing_frames` counts output frames the input was missing since it first delivered, so a take's gaps can be told.
- **Behind the app (API 26):** `caw_audio_set_background(e, 1)` raises the AAudio output's buffer size to the stream's capacity with `AAudioStream_setBufferSizeInFrames` (no reopen; [Fact] developer.android.com NDK AAudio reference, read 2026-11-12: it adjusts the latency up to `getBufferCapacityInFrames`, API 26), and 0 restores the size it had; it returns the size now (0 off AAudio). The app calls it while playing behind the app with no take running (nothing monitors there) and refreshes the latency compensation either way. A reroute meanwhile opens a stream at its default size. If the input won't open (no permission, no microphone, another app holding it) the output plays on and `caw_audio_status`'s `"input"` says why. Its `"state"`: `off`, `open`, `stalled` (open, nothing arrived for 250 ms), `stopped` (the system stopped its device) or `failed`; with `underruns` and `dropped_frames`. Called again with the same arguments while the input is not `open`, it reopens the input alone. **Android needs the RECORD_AUDIO permission first** (the app asks).
- **Why not duplex** ([Fact], miniaudio 0.11.25 source, read 2026-11-12): in duplex mode on AAudio the playback side calls the data callback only with frames the capture side has delivered (`ma_device__handle_duplex_callback_playback`), so a late or silenced microphone made the output drop out, more the longer it played; and a reroute (`ma_device_reinit__aaudio`) closes both streams and, after failing to reopen, stops the device. `caw_audio_status`'s `"running"` now comes from `ma_device_get_state` (with `"stopped_by_system"`), and `caw_audio_start` reopens a device the system stopped.
- **A track's `"input"`:** `channel` (first device channel, from 0), `channels` 1 (heard in both sides) or 2, `monitor` `off`, `on` (always) or `auto` (while armed and stopped, or armed while recording), `armed`. Monitoring plays the input through the track's whole chain in the output callback that pulls it from the bridge (the bridge's starting fill added to the devices' own buffers); while stopped a monitoring track keeps running as a held preview does. Input meters: `caw_engine_input_peaks`.
- **Recording** (`caw_record_start` with the armed tracks): each chunk the transport plays, the audio thread copies the input into a lock-free ring (2 s of the channels used) with its song position, and a writer thread writes each track's take as WAV (32-bit float, or 24-bit PCM), `<layer>-take<n>.wav.part`, renamed to `.wav` when the take ends, with a `.wav.json` sidecar (layer, take, start). A full ring drops frames (counted in `dropped_frames`) and the writer fills them with silence at the song positions they had, carried by a sample-less header, so a take never slips or splits at a loop wrap or punch while the disk lags (`a_full_ring_across_loop_wraps_keeps_each_take_whole_and_in_place`; only when the 8,192-entry header queue is full too are positions assumed to run on); a failed write (full storage) ends that take with an error and keeps what was written. File positions are 64-bit, and a take goes on in a new file (the next take number, starting where the last ended) before its WAV sizes would pass 4 GB (`max_file_bytes` in the request lowers that limit, at least 1024). Paths are UTF-8 on every platform (`_wfopen` on Windows).
- **Takes:** a take ends where the song position jumps (a loop wrap) and the next starts there, so loop recording gives a take per pass, all placed at the same start (take lanes and comping are the app's); `punch_in_steps`/`punch_out_steps` record only that range, sample-accurately.
- **Latency:** recorded frame n is placed at the song frame heard n frames of round-trip latency earlier (the writer keeps the chunk positions), so a take lands where it was played; `start_frame`/`start_steps` may be before 0 (trim that much). The latency is an override (`caw_engine_set_input_latency`), else the last good ping, else the device's estimate (both sides' buffers, plus the input bridge's starting fill, shown as `duplex_buffer_frames` (the name kept for the app), plus the most the output's block FIFO holds; **[Assumption]** the estimate is close but not exact, since the fill drifts while running, so the ping is the reliable value). The ping (`caw_latency_ping_start`) plays a 4,096-sample noise burst at −12 dBFS after the limiter and cross-correlates it (by FFT, outside the control lock) with a second of input; the peak's lag is the round trip, accepted when it stands 8 times above the mean (tested with a simulated 733-frame loopback).
- **Device latency (API 23):** `caw_audio_latency` reports how late the running device is, per side, in engine frames: `"output"` from a sample leaving the engine to the speaker, `"input"` from the microphone to the engine reading it (the input bridge's starting fill included), each with its `"source"`, `"device_id"` and `"kind"`. On AAudio the figure is read from `AAudioStream_getTimestamp` (the time a frame was played or recorded) against `AAudioStream_getFramesWritten`/`getFramesRead`, the reckoning of Oboe's `calculateLatencyMillis`, under the device's reroute lock so a reroute cannot swap the stream mid-read (**[Fact, miniaudio 0.11.25 source, 2026-11-11]** `ma_job_process__device__aaudio_reroute` holds `aaudio.rerouteLock` while it closes and reopens the streams); `"device_id"` is `AAudioStream_getDeviceId`, the routed device's `AudioDeviceInfo.getId()`. Before the first timestamp, and on WASAPI, ALSA and PulseAudio, it is every queued period (`"buffers"`). `"kind"` (the app's `AudioDeviceKind` names) is read on WASAPI from the endpoint's property store, cached per endpoint id: the bus that enumerated it (`DEVPKEY_Device_EnumeratorName`; **[Assumption]** `BTHENUM` is classic Bluetooth, `BTHLE…` Bluetooth LE, `USB` USB audio, the bus names Windows uses in hardware ids, not read on a primary page), else its `PKEY_AudioEndpoint_FormFactor` (**[Fact, Microsoft Learn, read 2026-11-12]** VT_UI4 holding an `EndpointFormFactor`: RemoteNetworkDevice 0, Speakers, LineLevel, Headphones, Microphone, Headset, Handset, UnknownDigitalPassthrough, SPDIF, DigitalAudioDisplayDevice (HDMI or DisplayPort), UnknownFormFactor); ole32 is loaded at run time. Elsewhere `"unknown"` (Android's kind comes from `AudioManager` in the app). The Windows code is compiled by MinGW here and not yet run on Windows. **[Assumption]** whether a Bluetooth link's own delay is inside AAudio's timestamp is not documented (no primary source found, 2026-11-11), so the app adds a per-device offset on top only where its preset expects more than the platform reports. Without a device (`audio_none.cpp`) both sides read `"none"` (`latency_without_a_device_reports_none`).
- **Fixed engine blocks at the device (the owner's idea, 2026-11-12):** the output device (always playback only) renders the engine in whole 64-frame blocks (`kBlock`) whatever size its callback is, through `BlockFifo` (`engine/src/block_fifo.h`) inside `DeviceRender` (`engine/src/device_render.h`, which the callback and the tests share; no allocation, no lock). The callback first plays what the last one held, renders whole blocks straight into its output, and renders one more block for a tail, holding the rest (at most 63 frames) for the next callback. A callback that is whole blocks passes straight through and adds nothing; otherwise `caw_audio_latency`'s output adds the most it holds (63 frames, 1.3 ms at 48 kHz). A period that is not whole blocks and is under 4 blocks (256 frames; a phone's 96- or 240-frame low-latency burst) bypasses the FIFO and calls `Engine::process` with the callback's frames: through the FIFO a 96-frame callback would render 128 and 64 frames by turns, 1.33 times its budget at the peaks; from 4 blocks the most is 1.25 times (257 frames), 1.14 at 441. The FIFO is new at every open and reopen (a sample-rate or route change reopens) and is never flushed while running: a Play, Stop or seek keeps the frames it holds, since the engine has already rendered them and moved on (dropping them jumped the waveform: a click), and a Stop's fade covers the Stop. **[Fact, miniaudio 0.11.25 source, `ma_device_init` and `ma_device__on_data`, read 2026-11-12]** miniaudio already calls back with a fixed size by default (`noFixedSizedCallback` off: an intermediary buffer of `periodSizeInFrames`, or of the backend's own period when that is 0), so the device's own sizes (Bluetooth's 441 or 1920) do not reach the callback; the FIFO makes the engine's block the same on every route on top of that. Asking miniaudio for a whole-block period instead would not help where the backend's burst is not whole blocks: the intermediary buffer would then bridge the two sizes with the same uneven work. That intermediary buffer's own hold-back is not in the latency figure yet. The input does not change the path (switching while running would drop or repeat the held frames): `DeviceRender::render` pulls the input bridge's next frames for each block it renders, so monitoring and recording stay in step with the frames rendered, not the frames played. The bridge's starting fill adds what the FIFO renders ahead (a callback through it pulls up to 63 frames more than it plays), and the recording estimate (`setDeviceLatency`) adds the most it holds once, on the output side, like `caw_audio_latency`'s `"output"` (its `"input"` leaves it out: the app adds the two sides). Whether the FIFO is used goes by the period only (`DeviceRender::suits`, decided at open). Tests: `sample_timing_test.cpp` (bit-identical to fixed blocks for random and Bluetooth-like sizes, the most held, a Stop or re-Play mid-note playing exactly the engine's render), `odd_callback_sizes_through_the_device_fifo_shed_nothing_under_the_threshold` and `the_block_fifo_never_allocates_on_the_audio_thread`.
- **Long runs and callback sizes (2026-11-12, the owner's Bluetooth report):** `caw_bench SECONDS 600` plays a suite scenario for many minutes in device-like callbacks (fast-forwarded) and prints each minute's mean, p99 and worst time per millisecond of audio, with no app calls (as backgrounded) or with `--app` (the app's read-only polls at their rates in audio time on another thread); `caw_bench SECONDS 601` renders every track tapped in 64-frame and in given (`--frames`, `--random`) callbacks at a `--rate` and reports where they differ, for a suite scenario or a project file (`--only FILE.json`, the engine's project JSON). Measured on Linux x64 (Release, 2026-11-12): song8 15 minutes flat at about 101–112 µs per ms of audio with and without the polls, First loop 30 minutes at random 1–2048-frame callbacks flat at about 21–24; per-track output bit-identical to 64-frame callbacks for song8 (441 and 1023 frames, 5 min; random at 44.1 kHz, 4 min), 32 tracks with heavy effects (1920, 3 min), First loop (960, 5 min) and the default project eight times over (random, 4 min), except one difference the default project showed: its Track 3's ducker (Tempo, waking a frame after a beat) ducked at 441-frame callbacks and not at 64, fixed above. Tests: `every_track_plays_the_same_bits_for_odd_callback_sizes_over_a_long_render`, `the_engine_does_the_same_work_after_minutes_of_play_with_no_app_calls`, `the_ducker_in_tempo_mode_wakes_the_same_whatever_the_block_size`.
- **Audio threads (API 24 on its branch, in the library from 28; speed phase 5d, 2026-11-12):** `caw_audio_threads` returns JSON: the core the callback ran on (`"callback_cpu"`, sampled every 32 callbacks with `sched_getcpu` or `GetCurrentProcessorNumber`), its `"core_kind"` (`big`, `little`, `other` when every core is one kind, `unknown`), that core's clock now and its top (`"clock_khz"`, `"max_khz"`: sysfs `cpufreq/scaling_cur_freq` and `cpuinfo_max_freq` on Linux and Android, `CallNtPowerInformation` on Windows, read on the calling thread, never the audio thread; −1 where unreadable), `"hint"` (an Android performance hint session is open), `"mmcss"`, what the platform granted the callback and the workers (`"callback_tuning"`, `"worker_tuning"`: `priority`, `realtime`, `fast_cores`, `mmcss`, `no_power_throttling`), `"workers"`, `"active_workers"`, `"wait_share"` and the machine's `"cores"`, `"fast_cores"`, `"hybrid"` and `"core_source"`. The app reads it through `Engine.audioThreads()` in `app/lib/engine/engine.dart` (no UI yet). The platform parts are behind `src/thread_tuning.h`, loaded at run time with a silent fallback:
  - **Core kinds:** one number per core (Linux and Android `cpu_capacity`, else `cpuinfo_max_freq`; Windows the CPU sets' `EfficiencyClass`); cores within 15% of the slowest are little and the rest big when they differ more, else all `other` (`classifyCores`).

  - **macOS, iOS:** nothing yet (`thread_tuning_none.cpp`).
  - **Rule:** a worker's priority is never above the callback's: a spinning worker above the callback could take its core and starve it.
- **Recovery:** after a crash, `caw_record_recover(dir)` (refused while a recording in this process writes into `dir`; a `.wav.part` whose 44-byte header is not the recorder's own is left alone) fixes each `.wav.part`'s RIFF sizes to the whole frames written (the header is also brought up to date about every second while recording), renames it and lists it with its sidecar's placement and `"recovered": true`.

## Component testing

The testing suite for C++ effects and instruments (#163; `engine/src/component_test.*`, measurements in `engine/src/analysis.*`). It loads one component, activates it at a sample rate and block size, feeds it a test signal or notes block by block on the calling thread (no audio device, never the audio thread), and measures the output. Both the C API (`caw_component_test`) and the CLI (`caw test-component`) take the same JSON request and return the same JSON result.

**Ports (2026-11-11).** A plain stereo effect runs through `process`; anything else runs through `processPorts` with every port it declares. The first audio input takes `signal`; later audio inputs (a sidechain) take their signal from `inputs` by port id, or silence. The first event input takes `notes` (MIDI 2.0 note on and off events with note ids, frame-accurate in each block); later event inputs get none. Modulation inputs read 0 and control inputs their port's default; modulation, control and event outputs are given room (1,024 events a block) and the events counted. The first audio output is measured as `output`; later ones are summarised in `ports.other_outputs`. Audio ports may be mono or stereo: a mono input gets the mid of its signal, a mono output is measured on both sides. A component with no audio input (an instrument) is fed only `notes` (one C4 at velocity 100 for 1 s when the request has none); the notes' end is the signal's end, the tail is measured after the last note off against the output's own peak, and `thd`, `latency` and the frequency response, which need a known input, are `null`. A component needs an audio output and an audio or event input; ports of more than two channels are refused.

**Request** (JSON object; an unknown key is an error, so a typo doesn't silently change the test):

| Key | Default | Meaning |
| --- | --- | --- |
| `component` | required | an id (`"org.caw.distortion"`) or `{"id", "library", "trust", "params": {id: value}}`. A built-in needs only its id. A built library needs `library` (the .so/.dll path) and `trust`: `"trusted"` loads it in-process, `"blocked"` and `"isolated"` are refused as in the Engine; there is no default. Unnamed parameters keep their defaults; values are clamped and stepped as in playback. |
| `signal` | sine | a type name or `{"type", ...}`. Types: `impulse` (one frame), `sine` (`frequency`, default 1000 Hz), `sweep` (exponential, `start_frequency` 20 to `end_frequency` 20000 Hz, held below 0.95 x Nyquist), `white`, `pink` (`seed`, default 1; `decorrelated`: independent left and right), `silence`, `dc`, `wav` (`path`: 16/24/32-bit PCM or 32-bit float, mono or stereo) and `buffer` (`left`, `right` arrays). `seconds` (default 1, at most 120) and `level_db` (dBFS: peak for impulse, sine, sweep and DC, RMS for noise; default 0 for an impulse, -6 otherwise). Signals other than `wav` and `buffer` are the same in both channels unless decorrelated, and are generated with the deterministic maths, so they are the same bits on every device. |
| `sample_rate` | 48000 | 8000 to 192000; a `wav` signal's own rate when left out (a mismatch is an error) |
| `block_size` | 64 | 1 to 8192: the `max_frames` passed to activate and the frames per process call (the last block may be shorter) |
| `tail_seconds` | from the descriptor | silence rendered after the signal: the declared tail and latency plus 0.25 s, or 5 s for an infinite tail; signal and tail together at most 120 s |
| `tempo` | 120 | the transport every block carries (playing, from beat 0) |
| `cpu` | true | time each process call |
| `fft_size` | 8192 | 256 to 65536, power of two, for the spectrum |
| `bands_per_octave` | 6 | resolution of the spectrum and frequency response |
| `compare` | none | a second component (same form as `component`) for a null test. It is loaded in its own registry, so the same id from another library file (another build) works |
| `bypass` | false | also null-test the output against the dry input (A/B against bypass) |
| `align` | `declared` | null-test alignment: `none`, `declared` (each side shifted by its declared latency) or `measured` (by cross-correlation, either side may be later) |
| `sweep` | none | `{"param", "steps", "from", "to"}`: render once more per value, `steps` (1 to 64; default 5, or one per choice of a choice parameter) evenly from `from` to `to` (default: the parameter's range) |
| `write_wav`, `write_input_wav` | none | write the output or the test signal as a 32-bit float stereo WAV, for listening |
| `notes` | none | for the first event input: up to 4,096 `{"pitch", "velocity", "start", "length"}` (MIDI pitch 0 to 127, fractions allowed; velocity 1 to 127, default 100; start and length in seconds, defaults 0 and 0.5). Refused for a component without an event input |
| `inputs` | none | `{port id: signal}` for audio inputs after the first (same form as `signal`, but not a WAV file); an unknown port is an error |
| `checks` | none | pass/fail thresholds: up to 256 `{"path", "min", "max", "equals"}`. `path` names a value of the result by dotted keys and array indices (`output.channels.0.peak_db`, `output.thd.left.thd_percent`, `bypass.depth_db`, `cpu.worst_percent`, `sweep.points.2.channels.1.rms_db`); a number must lie within `min`..`max` (either may be left out) and `equals` compares a boolean or number exactly. A missing or `null` value fails |

**Result** (keys are stable; `schema` is 1). Every result has `ok` and `error`; on failure that is all. A dB value of minus infinity (digital silence) is written as `null`; so is a value that doesn't apply.
- `component`: `id`, `name`, `version`, `role`, `source` (`builtin` or `library`), `latency_frames`, `tail_frames` (a number or `"infinite"`) and `params` (every value used).
- `settings`: `sample_rate`, `block_size`, `tempo`, `signal` (`notes` for an instrument), its level and frequencies, `notes` (how many), `signal_frames` and `render_frames` (signal plus tail).
- `output`:
  - `channels` (left, right): `peak_db`, `rms_db` (dBFS by amplitude: a full-scale sine has RMS -3.01 dB), `dc_offset`, `crest_db` and `gain_db` (output RMS minus input RMS), over the signal's span shifted by the declared latency (an impulse: the whole render); `nan`, `inf` and `denormal` (non-zero subnormal floats) are counted over the whole raw render, before the suite treats non-finite samples as 0 for the other measurements. `failed_blocks` counts process calls that returned false (the input passes through, as in the app).
  - `stereo`: `correlation` (1 identical, 0 unrelated, -1 inverted) and `width` (rms(side) / (rms(mid) + rms(side)): 0 mono, 1 fully out of phase).
  - `thd` (sine only), per channel: `fundamental_db`, `thd_percent`/`thd_db` (harmonics 2 to 10 below Nyquist) and `thd_n_percent`/`thd_n_db` (everything but the fundamental and DC). Measured by a least-squares fit of the known frequency over whole cycles of the steady state (past the declared latency and the signal's first 100 ms or quarter).
  - `impulse_response` (impulse only): `length_frames` and `length_ms`, until the output stays below -90 dB of the input's peak, and `truncated` (still above it at the end of the render).
  - `latency`: `declared`, `measured` (the lag of the largest cross-correlation between input and output, within the first 2^17 frames; `null` for a sine, DC or silence, whose every period matches) and `matches`.
  - `tail`: `declared`, `measured` (frames after the signal ends until the output stays below -90 dB of the input's peak), `measured_ms`, `truncated` and `within_declared` (measured at most declared tail plus declared latency; always true for an infinite tail).
  - `spectrum` (not for silence): `fft_size`, `window` (`hann`), `channel` (`mid`, (L + R) / 2) and `bands`, `[hz, db]` pairs from 20 Hz at `bands_per_octave`, each band's loudest bin, scaled so a full-scale sine on a bin reads 0 dB.
  - `frequency_response` (impulse, sweep and noise): `channel` and `bands`, `[hz, db]` = output power over input power per band, from the FFT of the whole render (first 2^20 frames); bands where the input has less than -60 dB of its loudest band's power are left out. It describes linear, time-invariant effects; for others it is an average.
- `cpu` (with `cpu`): `blocks`, `median_us`, `worst_us`, and both as `median_percent`/`worst_percent` of the block's real-time duration. The only part of a result that varies between runs: with `cpu` off, the same request gives the same JSON byte for byte.
- `bypass` and `compare` (when asked): `align`, `offset_frames` (output frames skipped on the tested side minus the other), `frames` compared, `exact` (every sample equal), `difference_peak_db`, `difference_rms_db` and `depth_db` (difference RMS relative to the tested output's RMS). `compare` also names the other `id`, `source` and `latency_frames`.
- `sweep`: `param` and `points`, each with `value` and the same `output` measurements except spectrum and frequency response, plus its own `warnings`.
- `ports`: how many audio, event, modulation and control inputs and outputs it has, `events_out` (events it emitted), and `other_outputs`: per later audio output, `port`, `channels`, `peak_db`, `rms_db`, `nan` and `inf`.
- `checks` and `passed` (with `checks`): each check with its `path`, the `value` found (`null` when missing), its bounds and `pass`; `passed` is true when every check passed.
- `warnings`: `non_finite`, `denormals`, `clipping` (a sample above 1.0), `failed_blocks`, `latency_mismatch`, `tail_exceeds_declared` and `tail_truncated` (the render ended while a finite tail still sounded).

**CLI:** `caw test-component org.caw.distortion --param drive=8 --report text`, or for a built library `caw test-component ./build/my-echo.so --id local.my-echo --trust trusted --signal impulse`. Options map onto the request (`caw` with no arguments lists them); `--request FILE.json` sends a request file as it is. It prints the JSON result (`--report text`: a few readable lines). It exits 1 when the test fails or a check fails, and with `--strict` also when the result has warnings, so CI can gate a component on it.

## Sample packs

The sample-pack maker (#164; `engine/src/sample_pack.*`) renders one instrument, optionally followed by a chain of stereo effects, offline on the calling thread (no audio device, never the audio thread) over a grid of notes x velocities x parameter steps (x round robins), and writes each cell as a WAV file into one output directory, with a manifest and optionally SFZ files. Each cell gets fresh instances, activated at the request's sample rate and block size; the instrument gets a MIDI 2.0 note on at frame 0 (velocity / 127, note id 1), held for `hold_seconds`, then a note off; the render goes on until, after the off and the chain's declared latency, the output has stayed below `tail_threshold_db` for 0.25 s (or `max_seconds` is reached: `tail_truncated`). The file then ends at the last frame above that threshold. Parameters keep one value per file (no smoothing), and the transport is playing at `tempo` from beat 0. The same request gives the same files byte for byte (the manifest records an FNV-1a hash of each).

**Trust and files.** Trust is never read from the request: the caller passes it (`trust_level` in the C API, `--trust` in the CLI) and it applies to every `library` the request names; only `CAW_NATIVE_TRUST_TRUSTED` loads one (blocked and isolated are refused, as in the Engine), and a `"trust"` key anywhere in the request is an error. Built-ins need no trust. Every file is written directly inside `output_dir` (created if missing, then made canonical): names are sanitised to letters, digits and `. _ - # +` (anything else becomes `_`, no `..`, no leading dot, at most 150 characters, Windows device names prefixed with `_`), a target that is a symbolic link or not a regular file is refused, and an existing file is refused unless `overwrite` is true. All names are checked (and must be unique, ignoring case) before anything renders. Each file is written to `NAME.part` and renamed, so a failure never leaves a half-written file; a cancelled or failed pack keeps the files finished before it and writes no manifest. The engine reads no WAV files here.

**Request** (JSON object; an unknown key is an error):

| Key | Default | Meaning |
| --- | --- | --- |
| `instrument` | required | an id (`"org.caw.synth.flagship"`) or `{"id", "library", "params": {id: value}}`; it must be an instrument (one event input, one stereo audio output) |
| `effects` | none | up to 16 stereo effects in order, each in the same form |
| `output_dir` | required | the directory every file goes into |
| `name` | `sample` | the pack's name (sanitised): `{name}`, and the manifest `NAME.json` and SFZ `NAME.sfz` |
| `name_pattern` | `{name}_{note}_{vel}_{param}` | tokens `{name}`, `{note}` (C4 = 60, sharps: `F#4`, `C-1`), `{midi}`, `{vel}`, `{param}`, `{index}`, `{rr}` (the round robin take from 1; empty without round robins, and `_rr{rr}` is added at the end when there are takes and the pattern has neither `{rr}` nor `{index}`); the result is sanitised, repeated underscores collapse and trailing `_`/`-` are dropped (so an empty `{param}` leaves no trace); `.wav` is added |
| `notes` | `[60]` | up to 128 notes, MIDI numbers or names (`"C3"`, `"Bb2"`), or `{"from", "to", "step"}` |
| `velocities` | `[100]` | 1..127, a list or `{"from", "to", "steps"}` (rounded) |
| `params` | none | up to 8 axes: `{"id", "values": [...]}` or `{"id", "from", "to", "steps"}` (at most 128 values), with `"effect": n` for `effects[n]`'s parameter (default: the instrument's). Values are clamped and stepped as in playback. The first axis changes slowest, then notes, then velocities |
| `hold_seconds` | 1 | 0.001..60 |
| `max_seconds` | the larger of 10 and hold + 5 (at most 60) | the longest a file may be |
| `tail_threshold_db` | -80 | where the tail ends |
| `sample_rate`, `block_size`, `tempo` | 48000, 64, 120 | 8000..192000, 1..8192, 20..999 |
| `bit_depth` | 24 | 16 or 24 (PCM, rounded and clipped to full scale) or 32 (float) |
| `dither` | `none` | `"tpdf"`: before rounding to 16 or 24 bits, add triangular noise of +-1 LSB, the difference of two uniform values (Lipshitz, Wannamaker and Vanderkooy, "Quantization and Dither: A Theoretical Survey", JAES 40(5), 1992), so the rounding error no longer depends on the signal: a fade or a quiet tail turns into steady noise instead of distortion. Seeded per file (the same request, the same bytes); samples that are exactly 0 stay 0; float files are never dithered |
| `round_robins` | 1 | 1..16 takes of every cell, or `{"count", "preroll_ms": 7, "vary": [{"id", "effect", "amount"}]}`. Take k (from 0) first runs the fresh chain on silence for k x `preroll_ms` (its free-running state moves on; the pre-roll is dropped), and each `vary` parameter (the instrument's, or `effects[effect]`'s) moves by up to +-`amount` from its value, by a deterministic amount per take. The first take is exactly the cell without round robins |
| `channels` | 2 | 1 writes the mid, (L + R) / 2 |
| `trim` | `{"start": true, "end": true, "threshold_db": -80}` | removes leading and trailing frames where every channel is below the threshold; `false` turns both off |
| `fade_in_ms`, `fade_out_ms` | 0 | linear fades after trimming, kept outside a loop |
| `normalize` | `none` | `"peak"`, `"rms"` or `{"mode", "target_db", "scope"}`: target -1 dBFS for peak, -18 dBFS for RMS (over all samples of all channels); scope `file` (each file its own gain) or `group` (one gain for the pack, set by its loudest file, keeping the files' relative levels; costs a measuring pass). For 16/24-bit the gain is held so the peak stays at or below 0 dBFS (`normalize_limited_by_peak`) |
| `loop` | false | `true` or `{"enabled", "min_seconds": 0.05, "max_seconds": half the hold, "crossfade_ms": 0, "crossfade": "equal_power"}`: a forward loop in the held part, as heard after the chain's latency. Its end is the frame before the last rising zero crossing (of the mid) at or before 20 ms (or a tenth of the hold, if less) before the note off; its start is the rising zero crossing, from `max_seconds` before the end to `min_seconds` before it, whose surrounding 64 frames either side best match the end's (both channels; ties keep the longer loop). Written to the `smpl` chunk; `no_loop_found` when there is none. With `crossfade_ms`, the loop's last frames are crossfaded with the frames just before its start (`equal_power`, sin/cos gains for unrelated material, or `linear`), so the wrap continues the sound as it first ran whatever the seam's match; held to the loop's length and to the frames before its start (`loop_crossfade_shortened`) |
| `sfz` | false | also write SFZ: one file per parameter combination (`NAME.sfz`, or `NAME_PARAMS.sfz` with axes) |
| `manifest` | true | write `NAME.json` |
| `max_files` | 256 | the grid may be at most this (at most 4096); a larger grid is refused before rendering |
| `overwrite` | false | replace existing files of the same names |

**Each WAV** has `fmt `, `fact` (float), a `smpl` chunk (MIDI unity note = the rendered note, the sample period, and the loop, if any, as start and inclusive end frames) and `data`.

**SFZ** (plain text, basic opcodes only): one `<region>` per file with `sample=` (the file name, in the same directory), `lokey`/`hikey` (each sampled note covers the keys halfway to its neighbours; the lowest from 0, the highest to 127), `pitch_keycenter`, `lovel`/`hivel` (each velocity layer from the one below it, exclusive, up to its own velocity; the lowest from 1, the highest to 127), `seq_length`/`seq_position` for round robins (the sampler plays the takes in turn), and `loop_mode=loop_continuous loop_start= loop_end=` or `loop_mode=no_loop`.

**Result and manifest.** The result has `ok` and `error` (on failure that is all), `output_dir` (canonical) and everything the manifest holds; the manifest has no absolute paths, so a pack can be moved: `schema` (1), `name`, `instrument` and `effects` (`id`, `source` builtin or library), `settings`, `file_count`, `files` (each: `file`, `note`, `note_name`, `velocity`, `round_robin` (with takes), `params` {id: value used}, `param_effects` (`"instrument"` or an effect index, per axis), `frames`, `seconds`, `trimmed_start_frames`, `peak_db`, `rms_db`, `gain_db`, `loop` (`start`, `end`, `match_db`: the seam's difference energy relative to the signal before any crossfade, lower is better; `crossfade_frames`) or null, `tail_truncated`, `hash` and `warnings`), `sfz` (file names), `manifest` and `warnings` (`tail_truncated`, `failed_blocks`, `no_loop_found`, `silent`, `normalize_limited_by_peak`, `clipped`, `over_full_scale`, `loop_crossfade_shortened`); `settings` also has `round_robins`, `dither` and, with a crossfade, `loop_crossfade_ms` and `loop_crossfade`. A dB of digital silence is `null`.

**CLI:** `caw sample-pack org.caw.synth.flagship --out pack --name lead --notes C2:C5:12 --vel 64,127 --step flt1_cutoff=600,3000 --set env1_release=0.4 --loop --sfz --normalize peak --group --bits 16`. `--request FILE.json` reads a request; the options override its keys. `--library PATH` takes the instrument from a built library and `--trust trusted|isolated|blocked` (default blocked) is the trust passed for every library; `--effect ID` (repeatable) adds built-in effects (library effects go in a request file). `--loop-xfade MS` loops with a crossfaded seam, `--rr N` renders N round robins and `--dither tpdf` dithers 16/24-bit files. `caw` with no arguments lists every option. It prints the result JSON and exits 1 when the pack fails.

**[Fact] Limits, as built:** a loop is found only where the held sound repeats: a detuned two-oscillator patch that beats slower than the hold gets a loop whose seam does not match well (`match_db` about -25 to -28 dB for `org.caw.synth.basic` at its default 7-cent detune, against below -80 dB with one sine oscillator); `loop.crossfade_ms` smooths such a seam. Notes are whole MIDI numbers. Round robins vary only by pre-roll and parameter offsets: an instrument whose state does not run free, given no `vary`, renders the same take each time.

## The Benchmark

The app's built-in stress test (beta plan C; the app calls it **Benchmark**). `src/stress_scenarios.cpp` holds the projects caw_bench's suite plays (moved there unchanged: caw_bench's output is the same, and `stress_test.cpp` checks each builder's project hash against caw_bench's own code at `d932771` and 1 s of each against `references/stress.cawref`), their tiers and two ramp builders; `src/stress_run.cpp` times them; `src/capi_stress.cpp` is the C API. **[Fact]** (`engine/tests/stress_test.cpp`, `stress_rt_test.cpp`, 2026-11-13).

- **Scenarios** (`benchmarkScenarios()`, the ten ids section H2 names): Normal `first_loop`, `three_tracks`, `song8`, `song8_extras`; Heavy `song16`, `drums_kit`, `flagship_heavy16`; Extreme `flagship_heavy`, `song32_heavy`; Idle `tail_floor`. caw_bench's `tail` (three phases) is the suite's only. Each carries `memory_mib`, its peak RSS growth set up and playing on Linux x64 (2026-11-13) with about a third on top, for the app's budget check. `typicalSong(extras, dir, &error)` writes song8_extras' two WAVs into the caller's folder (Android has no usable temporary folder) and reports a failed write.
- **A run** has its own `Engine` (48 kHz, the quality asked) and project, never the caller's; overload shedding is off on it (`Engine::setShedding(false)`: one check where a layer would be shed, and a change resets shedding, so layers already shed come back and the load history is forgotten), so the whole project is measured. Like caw_bench's suite: set up, 0.25 s stopped to apply, Play, then `seconds` of `frames`-frame callbacks (256 by default: the CI bench's) timed one by one. Mean, p99 and worst (a percentage of the callback's budget), callbacks over budget, the worst's time, the first and last tenth's means.
  - **Plain** and **sustained** (the same, long: a rise from the first tenth to the last shows heat).
  - **Ramps:** tracks (`bigSong(n)`, the typical song's tracks with its buses, master and LFOs; 1 to 128), Flagship voices (`flagshipVoices(n)`, its default patch holding n notes; 1 to 64, its polyphony) and effects on one track (`effectsChain(n)`, a Flagship chord track through EQ, compressor, saturator, chorus, delay, filter, phaser and reverb in turn; 1 to 64). Each step is a fresh engine timed for `seconds`; a step holds when its p99 callback is within the budget (`kHoldP99`). The counts go up until the first that doesn't hold, then halve the gap below it (never above the failed count), so the limit is the last count that held.
  - **Profile:** 1 s warm-up, then each component's own time (`ChainProfile`, nested chains taken off their parents) and the host's share (all `Engine::process` does outside components), summed per component id. The profile is per Engine (`Engine::setProfile`): `process()` reads it once and hands it to every chain and modulator in its `ChainTime`, so it travels with the work, an engine without one adds nothing to another's on the same thread, and the audio path uses no thread-local storage (Android's emulated TLS can allocate on a thread's first use). A profile is filled by one thread at a time, so a profiling engine's mix stays serial: the pool runs a callback only when `wantsMixPool() && !profiling()`.
  - **Live** (plain and sustained only): a `CawEngine` of its own through the default output device (low-latency buffer, the size asked or the device's smallest), output muted (`CawEngine::muteOutput`, zeroed after `process()`), the callback recording each callback's time, load and size into preallocated `CawStressStats` after its timed span. The budget is the mean of the callbacks' own and the audio the sum of their frames, so varying callback sizes are measured right. Dropouts: AAudio's `AAudioStream_getXRunCount` over the run where it exists (**[Fact]** NDK r30 `AAudio.h`: underruns or overruns, API 26+), else the callbacks over budget; the callback's core (`sched_getcpu`, Windows `GetCurrentProcessorNumber`), read on the first callback and every 64th, since it can be a system call. Muted output is written as zeros, not scaled. One output per process: the caller stops its own engine's audio first; while a live run has the device, `caw_audio_start` on any other engine is refused, and a run whose device stops calling back for a second fails with that reason.
  - **Cancel** is read at every callback (DSP) or every 100 ms (live), so a run stops within a step. The timed loop allocates nothing (`caw_rt_tests`); the load history is a fixed ring of 8192 points, one per 100 ms of audio.
- **C API:** `caw_stress_scenarios()` (JSON: scenarios with tier and memory, the ramps' counts, `hold_p99`); `caw_worker_pool_submit_stress(pool, CawStressRequest*, priority)` returns a `CawJob` (status, cancel, wait and release as for every job; `caw_job_result` the run's JSON, `caw_job_error` the reason, "cancelled"); `caw_stress_progress` (atomics: permille, ramp step, count, held, load, callbacks, over budget), `caw_stress_history` (the 100 ms load points from an index on), `caw_stress_result` and `caw_stress_costs` once it finished. `threads` must be 0 until a parallel mix lands.
