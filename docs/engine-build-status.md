# Modular engine implementation status

This is the implementation ledger for the unified modular engine. A documented contract is not the same thing as a running feature. Status below separates code that exists from code that still needs integration or verification.

## Implemented in the current repository snapshot

- Portable deterministic workload policy for audition, preview, background generation, offline render and idle workloads.
- App-side native job integration: the Flutter host binds the native hardware probe and workload planner, then submits project compilation, async source checks and offline WAV renders to the C++ `AdaptiveWorkerPool`. Dart owns job handles, polls status/progress and reads results; native workers never call Dart. Project jobs retain their engine handle until completion. Android thermal status and battery-saver changes are supplied by the app host; app lifecycle and audio-playing transitions refresh the native worker budget. Other platform adapters remain explicitly unknown.
- Hardware profile input and C ABI adapter for workload planning, plus a native best-effort probe for active/online cores, process CPU affinity and Linux/Android cgroup CPU and memory limits, conservative available-memory budgets and CPU SIMD support on Windows, macOS, Linux and Android. Linux/Android preserve exhausted finite cgroup limits as a minimal budget; positive budgets are quartered with a 1 MiB minimum and an 8192 MiB cap. macOS/iOS still use half of physical memory as a fallback, not live available memory. Missing CPU/memory signals remain unknown and policy falls back conservatively to one worker. Android thermal status (Android 10+) and battery-saver changes are supplied by the app host; unsupported platforms remain explicitly unknown. GPU compute is unavailable until a real kernel backend exists.
- Public C++ module descriptors with stable IDs, typed ports, parameter metadata and validation, plus framework-neutral generated UI controls and custom-view identifiers. The `CAW::SDK` target is installable as a versioned CMake package for standalone engine builds; the manifest-driven CMake helper builds shared components and emits a configuration-specific artifact-path file. The app now persists component sources and exact dependency pins, materializes them into an app-private workspace, invokes a local CMake runner, reuses a separate build directory and returns a verified artifact path. A Linux integration test builds a manifest-driven module with the repository's actual CMake helper and rebuilds it after a source edit. `ModuleRegistry` is now owned by `Engine`: Windows uses `LoadLibraryW`, POSIX uses `dlopen`, descriptor and stable ID are validated, and a processor wrapper retains the library and calls the component's own destroy export. Loading requires an explicit trust value through the Engine C API: Blocked refuses to open, Isolated is rejected until process isolation exists, and Trusted loads in-process. Build success does not load or authorize code. The Dart FFI load/unload wrapper now runs on a background isolate, and native stereo effects run with their parameters on tracks (`LayerDoc.components`, after the track's chain and before volume and pan) and on the master (`ProjectDoc.masterComponents`, before the safety limiter); the per-component trust UI/store remains missing; Android-hosted compiler provisioning is also outstanding. Repository CI (not a user build service) builds the component fixture for Linux x64, Windows x64 and Android ARM64.
- N-channel borrowed-buffer processor contract (`engine/include/caw/module.hpp`): channel layouts Mono, Stereo, Quad, 5.1, 7.1 and Discrete, a hard ceiling of 64 channels per port (`kMaxPortChannels`; descriptors above it fail with `TooManyChannels`), planar channel views and the generic `process(AudioProcessBlock)`. Frames rule: the block's `frames` is the work size and each view's `frames` is its capacity, which must be at least that. The default generic `process` adapts a block whose input and output each have 0 or 2 channels to the legacy stereo overload, passing null pointers for a side with no channels (stereo generators and sinks keep working); a processor that implements neither overload returns `false` on every call instead of silently leaving its output untouched. The generic executor is exercised by graph tests, but externally loaded C++ components are not yet inserted into the live Engine VM/mixer chain.
- Component descriptor (CP.2, `engine/include/caw/module.hpp`): display name, component version (at least 1), role (instrument, generator, effect, utility, event processor, analyzer), latency and tail frames (`kInfiniteTail`), maximum state bytes; per parameter a display name, choice labels (whole-number ranges only) and `modulatable`/`midiMappable` beside `automatable`. `GraphExecutor` refuses a modulation link, automation lane or CC mapping the parameter does not allow (`ParameterNotModulatable`, `ParameterNotAutomatable`, `ParameterNotMidiMappable`). `stereoInput`/`stereoOutput`/`audioPort` build ports with stereo as the default layout; a layout mismatch between connected ports is still refused (`ChannelLayoutMismatch`), never converted. Components cross the plain-C interface v3 (`engine/include/caw_component.h`): one export, `caw_get_component_v3`, with a size-tagged descriptor, `activate`/`deactivate`, the full typed-port `process` and extension hooks; `ModuleRegistry` copies the descriptor into engine-owned storage and wraps instances without allocating on the audio thread. The Engine's master chain activates each instance before it plays. A library may be a bundle (`caw_get_component_v3(index)`, `CAW_EXPORT_COMPONENTS`); the registry loads the component with the expected id. `caw_engine_components` lists loaded descriptors as JSON for the app (`NativeComponentInfo` in `app/lib/engine/component_info.dart`); no screen shows them yet. Choice parameters are linear, at most 4,096 labels, values within ±2^31.
- Live playback and offline render run through one mix graph (F4.3, F4.4): `Engine` owns a `GraphExecutor` (`prepareRouted`) with, per slot, 32 module nodes, a track node and a bus node, plus a master node (gain, DC blocker, limiter, stop fade). A track runs one module node per module of its chain (the generator or voice pool, then each effect), joined by 3-lane float edges: lane 0 the current chain, lane 1 the shadow instances finishing the previous pass across a loop seam, lane 2 the replaced chain fading out after a code swap. Its track node does those crossfades, gain, pan and meters; a track's and a folder bus's meter is the sample peak of what it sends on (after volume and pan, the louder channel). Before the graph runs, `planChunk` applies each playing track's loop restarts and code swaps at the chunk start and ends the chunk at the next one, so every node runs one whole segment. After a command batch, a swap, a retirement or a slot (de)activation, the audio thread re-derives the routing with `GraphExecutor::setRouting`, without allocation: a track goes to its parent when that is an active folder bus and to master at the root, in dependency order (exporters before readers) with each bus after its children; idle slots and unused module nodes are left out and cost nothing. A chain over 32 modules is refused with a layer error (`kMaxTrackModules`). Within a layer, a module reads exports only from modules before it in its chain; a later one is refused with a warning and reads 0. Track-to-track exports remain a 64-bit side channel. F4.4 re-recorded 9 template and 8 mixer golden hashes (each module's output now rounds to float); the old engine with that rounding added renders the same bits for all of them and for new effect-chain, seam, pattern and code-swap goldens; 24-bit renders differ by at most 1 LSB. `Engine::process` is tested allocation-free through seams and swaps. Callgrind, 192-frame callbacks, before → after F4.4: 1 layer 152,390 → 132,831 instructions; 4 layers 589,489 → 577,970; 16 layers 2,072,610 → 2,070,932; 4 layers each with delay and reverb 974,775 → 999,238 (+2.5%, the extra effect nodes).
- Play from a position (2026-11-05): `caw_engine_play_at(step)` starts the transport that many sixteenth steps into the project loop, converted with the tempo then in effect, with a 10 ms fade in (also used when a play cuts a stop's fade short). Tracks work out their loop pass from it; a note that began earlier isn't heard and a trig waits for the module's next pass. The app's Space pause uses it. Tests: the `play_from_a_position_*` and `play_during_a_stop_fade_fades_back_in` engine tests.
- Native C++ instruments (#156, 2026-11-10): a component with one event input and one stereo output plays a layer's notes in place of a .caw generator (`instrument` in the project JSON; `ComponentChain::buildInstrument`, `engine/src/note_events.h`). Pattern and clip notes, previews and Stop reach it as frame-accurate MIDI 2.0 UMP note events with host note ids, from per-block storage set aside at setup (no practical polyphony cap: 1,024 notes, 4,096 events a block, 360 KB a track, a full block never drops an off); values, bypass, lanes, state, rebuilds (held notes carried over), latency and release tails work as for effects; export renders it on the same path. A component that has fallen silent sleeps until an event or input (`ModuleProcessor::quiet()`, C extension `caw.quiet.v1`; a declared tail alone does not, so the output doesn't depend on the buffer size). SDK helpers in `caw/instrument.hpp`, the built-in `org.caw.synth.basic` (golden render) and `examples/cpp/poly-synth/`. The app sets it from the track menu and shows its knobs in the FX tab. Not done: .caw effects after an instrument are mono (its mid); the Builder's audition doesn't play C++ instruments yet. Notes in arrangement clips keep their expression (bend, vibrato, pressure, timbre) when the clips are laid out into the song; before 2026-11-10 that copy dropped it, so a clip's bent note played without its bend (owner report, #170; test `a_clips_note_keeps_its_bend_when_the_clips_are_laid_out`).
- The flagship synth (#171, 2026-11-10, `engine/src/builtin_flagship.cpp`, `org.caw.synth.flagship`): three wavetable oscillators (four code-generated tables, five warps, unison up to 16 copies with detune power, spread, blend, random phase and stack modes), two filters per voice (ladder LP/HP/BP, SVF LP/HP/BP/notch, comb, formant; series or parallel; per-oscillator routing), three envelopes, three LFOs (free, synced or retriggered), a random source, a 16-slot mod matrix stored as parameters (applied every 16 frames per voice), and distortion, EQ, chorus, ping-pong delay and reverb; 64 voices, deterministic, the same bits at any block size, allocation-free while playing, quiet when silent. Parameters in [engine](engine.md); cost in [performance](performance.md#flagship-synth-2026-11-10).
- Note previews (#103): `caw_engine_note_on(layer, id, pitch, velocity)`, `note_pitch` (a 5 ms glide on the held voice), `note_off` and `notes_off` hold a voice on a voiced layer's instrument through the command queue, with no expression, outside the pattern (pattern restarts and swaps don't release it). Stopped, `Engine::process` runs preview chunks: only the previewing tracks play, through their effects, folder buses and master, with no pattern events and the transport left where it is; a track's time runs on from where it stopped, other tracks export silence, and a track keeps running after its last preview until its output has stayed below -80 dB for 0.25 s (30 s at most). When a stop fade ends, pattern voices end and effects reset, and held previews fade back in over 10 ms. A preview on a muted or soloed-out track ends. Renders and exports never get previews. Tested in `engine_test.cpp` and allocation-free in `engine_rt_test.cpp`.
- Routing carries 32-bit float since F4.2: each track or bus output is rounded to float where it enters its folder bus or the master and summed in float in processing order from +0.0, exactly as graph summing inputs do, saturating at ±FLT_MAX with NaN as 0 (`engine/src/route_math.h`, shared by both), so F4.3 could move it into the graph bit-for-bit. Processing inside tracks, buses and the master stays 64-bit.
- Parameter resolver (Foundation F6.1, `engine/src/params.*`): `ParameterDescriptor` has a curve (linear, or exponential via `detLog`/`detExp`), step, smoothing frames and a display unit. `ParameterResolver` gives one parameter's value per block:
  - **Base:** the manual or MIDI value, smoothed; automation replaces it unless a touch overrides it until playback restarts.
  - **Modulation:** up to 8 links in link-id order on the normalized range (add, multiply, min, max, replace, depth −1..1).
  - **Result:** clamped and stepped like the Engine's automation path, and one constant when nothing varies.
  - **In the graph executor (F6.2):** every node's descriptor parameters get a resolver at `prepare()` (counted in the budget). Each block resolves them before the node runs and passes them in descriptor order (`AudioProcessBlock`/`ProcessBlock::parameters`). The control thread sets values with `queueParameter()` and ends touches with `queueClearTouch()`, through a bounded lock-free queue (256 commands) drained at the next accepted block; a full queue refuses the command, so the caller resends the latest value. Touch resets cost O(1) (an epoch). After a rebuild, `setInitialParameter()` restores values directly: no ramp, no touch.
  - **Modulation links (F6.3):** `setModulationLinks()` connects modulation outputs to node parameters. It runs while audio is stopped and validates the whole list first. A source must be a modulation output that runs before its destination. Each parameter takes at most 8 links, applied in link-id order. Links and dynamic routing exclude each other either way round, since routing could run a source late or not at all.
  - **Automation lanes (F6.4):** `setAutomationLanes()` (while audio is stopped; at most one lane per parameter, points borrowed, sorted by step, finite, validated as a whole) gives parameters a lane. `setTransport()` on the audio thread sets the song position, samples per step and play state; the position then advances by each block's frames. While playing, each frame reads the lane at `(position + frame) / samplesPerStep` with `automationLaneValue()`, the function the Engine's own automation uses, so values match it bit for bit, seeks included. A touch overrides the lane until `queueClearTouch()`; when playback stops the parameter holds the last played value. The graph knows no loop: the host splits blocks at a loop point and sets the transport again, like `Engine::process`. Positions are refused at 2^53 samples or beyond (where doubles stop being exact), and a block that would cross that stops the lanes. `prepare()` clears lanes and stops the transport.
  - **MIDI CC mappings (F6.5):** `setCcMappings()` (while audio is stopped; one CC per parameter, one CC may drive several) maps a (group, channel, controller) Control Change in the host events passed to `process()` onto a parameter. MIDI 1.0 (7-bit) and MIDI 2.0 (32-bit) UMP Control Changes both apply (`decodeControlChange` in `midi2.h`). The CC's 0..1 value spans the range on the parameter's curve and sets its base at the event's frame, like a knob: smoothed, and a touch over automation. The block's host CCs are decoded once into a prepared list (at most `maxEventsPerPort`, counted in the budget), and each mapped parameter scans only those. Host events are now accepted (bounded the same way) by graphs without event ports too.
  - **The Engine's .caw params (F6.6):** every param and global of every chain module has a resolver (built with the chain on the control thread). Each chunk, on the audio thread, the held value is the manual base and the param's automation lane (if any) the automated base. Only a knob move (`setParam`/`setGlobal`, which give the param an engine-wide touch stamp after storing the value) is a touch over a lane, until the next Play; a move stamped after `play()` (even before the audio thread handles the Play) stays a touch; any other change of the held value (a project update) is a restore with no touch. Knob moves made while stopped are taken as plain values at Play, and a chain rebuilt by a code edit keeps the touches the control thread recorded since the last Play. An untouched lane resolves exactly as the old inline path did (clamp, then step), so golden hashes are unchanged; a held value is now stepped like any base. A param with no lane whose held value is already exact skips the resolver (callgrind: +0.3% per callback). The compiler refuses a param whose default, range or step is not finite (`param numbers must be finite`), so every param gets a resolver..
  - **Not connected yet:** nothing feeds the graph's host events from MIDI devices, and projects do not yet declare modulation links or CC mappings for the Engine's graph (which also uses dynamic routing, so links there will need routing-aware ordering).
- Typed DSP graph validation, deterministic topological ordering and a prepared planar N-channel executor (roadmap F3). The compiler no longer imposes arbitrary 1024-node/8192-connection caps; node references retain a uint32 representational boundary and connection indices use size_t. Duplicate-ID validation uses deterministic sorting. GraphResourceBudget requires explicit maxWorkingBytes; optional count ceilings default to unlimited. Compilation and executor preparation estimate internal working memory before allocation and distinguish invalid budget, budget exhaustion, size overflow and actual OutOfMemory. The executor accepts host-selected nonzero block sizes without the old 8192-frame cap, allocates only during prepare and processes with preallocated buffers and no graph traversal or locks. Since F3 the executor stores one planar buffer per node output channel plus per-node input/output pointer tables, all allocated in `prepare()`, sized from the validated port descriptors and counted in the working-memory budget. It calls processors only through `process(AudioProcessBlock)`, runs any layout up to the budget's `maxChannelsPerPort` (default 64), and rejects incompatible routing (including Discrete count mismatches such as Discrete(3) to Discrete(5)) instead of truncating or padding. A `false` from any processor fails the block: the host output is zeroed and the failing node and a failure count are recorded. Unconnected inputs read the host input, so they must share one channel count; a graph with no host-fed inputs ignores any host input. An executor rebinds host channels on each call, so it must never be processed by two threads at once (playback and export need separate instances). The old left/right `process()` stays as a thin wrapper over the planar path. Since F4.1 an input marked `summing` (a mix bus) takes any number of connections, summed into prepared per-channel buffers in connection order from +0.0f in float; any other input takes one. Since F5.1 a node may have any number of audio, modulation and control ports (sidechains, modulators, block-rate controls), and since F5.2 event ports: timed `Event`s (frame, kind, note id, raw MIDI 2.0 UMP words) in prepared buffers of `maxEventsPerPort` (default 1024), merged by frame on summing inputs (overflow dropped and counted), checked for order after each node (a bad list fails the block), with host events into each node's first unconnected event input; nodes with more than one audio port or any other port are called through `processPorts` and must opt in, checked at prepare. Nothing feeds the graph events from MIDI devices or patterns yet; the active Engine does not yet derive or pass a hardware-based budget.
- A graph runtime publication helper that adopts prepared graphs on the audio thread and defers old-graph reclamation to the control thread. The Engine's mix graph doesn't use it: its topology is fixed (one node per slot), and routing changes go through `setRouting` instead.
- Bounded, fixed-capacity non-real-time worker pool with priority scheduling, worker-budget controls, queue rejection and pending-job cancellation, plus an `AdaptiveWorkerPool` wrapper that applies the deterministic workload plan to actual worker concurrency. An additive public C ABI now exposes pool creation, plan application, prioritized source-check/project-compile/offline-render jobs, status/progress, cancellation and owned result/error handles. Native job inputs are copied, engine handles are retained across project jobs, and pool shutdown drains accepted work. Workers are created on demand, sleep on a condition variable and retire after a configurable idle timeout; completed thread slots are joined and reused when demand returns. Retirement never runs on the audio callback.
- Exact, scope-aware dependency resolver for project-local, user-global, factory and add-on assets, including pinned version, content hash, interface version, optional references and ambiguity detection. Project JSON now parses and stores these dependency references; matching them against the installed library and surfacing repair actions remain unimplemented.
- Native module registry with stable-ID lookup, factory creation, descriptor verification and reset/versioned state hooks. The registry is static/in-process only; dynamic loading, host adapter, state migration/serialization policy and package signing remain unimplemented.
- MIDI 2.0 Channel Voice UMP decoder for note, per-note pitch, pressure, CC and channel pitch events, plus a bounded lock-free SPSC input queue. This is a host bridge primitive, not live device I/O or Engine voice routing.
- Existing note model already supports fractional MIDI pitches and per-note bend, pressure, timbre and vibrato curves. Existing MIDI import/export handles Standard MIDI Files and MIDI 2.0 Clip Files.
- Synth patch compiler now supports three oscillators, sub/noise, unison, two filters, three ADSR envelopes, four tempo-synced LFOs, four macros, modulation routing to oscillator position/level/pitch, filter cutoff/resonance and master volume, plus effect chains. A deterministic phase-distortion amount is now available per wavetable oscillator. The Builder includes a synth modulation-matrix editor and a general numeric parameter/global modulation editor using `mod name = expression` and `util.mod`; dedicated sidechain ducking effects can be created, routed from active exports, retargeted and removed. Missing exports warn and read zero; dependency cycles remain bounded with one-block feedback and diagnostics. Drawn LFO curves, additional warp modes (hard sync/FM/fold), and custom/imported wavetable authoring remain unimplemented.

- Component testing suite (#163, `engine/src/component_test.*`, `engine/src/analysis.*`): renders one C++ component (a built-in or a library loaded with an explicit trust choice) offline: an effect, a keyed effect (its sidechain and key notes fed from the request) or an instrument played a note list, with every port of any kind given a buffer (2026-11-11), at a chosen sample rate and block size with an impulse, sine, log sweep, seeded white/pink noise, silence, DC, WAV or buffer; measures levels, DC, crest, denormal/NaN/Inf counts, stereo correlation and width, THD and THD+N, impulse-response length, frequency response, a windowed spectrum (own radix-2 FFT), latency and tail against the declared values, and CPU per block; null tests against another component or build and against bypass, parameter sweeps, and pass/fail thresholds on any value of the result (`checks`, with `passed`; the CLI exits 1 on a failed check). JSON in and out through `caw_component_test` and `caw test-component` ([engine](engine.md#component-testing)). Deterministic without CPU timing. Not yet: ports of more than two channels, and an app UI.
- Live loudness and correlation meters (roadmap 2.6, 2026-11-11, `engine/src/meters.*`): the master's momentary, short-term and integrated loudness (ITU-R BS.1770-5, EBU Tech 3341 V4), true peak (BS.1770-5 Annex 2, 4x) and correlation, and each track's and folder's correlation, through `caw_engine_loudness`, `caw_engine_loudness_reset` and `caw_engine_layer_correlation` (API 12). Cheap per-sample accumulation on the audio thread, gating at read, no allocation. Not yet: Dart bindings and a meter UI.
- Library kernels (`engine/include/caw/library/`, header-only, public with `CAW::SDK`): pan, width, distortion, ping-pong delay, chorus, oscillators, filters, envelopes and drum voices (used by the built-in components and instruments), plus parameter smoothers, an LFO (seven shapes, Hz or tempo-synced), a mipmapped band-limited wavetable oscillator with frame morph, and an 8-line FDN stereo reverb, each with unit tests (`engine/tests/library_kernels_test.cpp`: rate and phase, aliasing below −60 dB, morph, RT60 within 5 %, no NaN or subnormals). The flagship synth uses the LFO, wavetable and reverb; it added `unison.hpp`, `comb.hpp`, `formant.hpp`, `eq.hpp`, `MultiLadder` and `Wavetable::levelData`, tested in `engine/tests/flagship_test.cpp`.
- Sample-pack maker (#164, `engine/src/sample_pack.*`): renders an instrument (a built-in or a library the caller trusts; trust is an argument, never part of the request) and an optional stereo effect chain offline over notes x velocities x parameter steps, each a held note then its tail until it is quiet, to 16/24-bit PCM or 32-bit float WAV with a `smpl` chunk (root note, and a loop found by zero-crossing match); trims, fades, peak or RMS normalisation per file or per pack, names from a pattern with a sanitiser, everything inside one output directory (symlinked targets refused), a manifest JSON and basic SFZ. `caw_sample_pack_render` (progress and cancel) and `caw sample-pack` ([engine](engine.md#sample-packs)). Crossfaded loop seams (equal power or linear), round robins (pre-roll and deterministic parameter variation per take, SFZ `seq_length`/`seq_position`) and TPDF dither for 16/24-bit (2026-11-11). Deterministic. Not yet: fractional notes, noise-shaped dither, an app action.

## Not yet implemented

- A project graph representation and bytecode/native processor interoperation: the mix graph runs each track module as a node, but only `.caw` programs; native modules are not graph nodes yet, and ModuleRegistry has no production references from Engine, VM, C API or Flutter. GraphResourceBudget is implemented at the lower-level API but is not yet connected to hardware-aware Engine policy.
- Universal state transfer, graph hot-swap integration and dependency-aware retirement for native module instances; the graph helper currently provides only prepared-graph pointer publication and deferred reclamation.
- Multichannel and multi-port runtime processing, multiple sources per input, multiple outputs, cross-domain control/modulation/event/MIDI execution, general sidechains, sends/returns and feedback networks. The current prepared executor runs any channel layout but is audio-only, one-in/one-out per node, and accepts only 8–192 kHz.
- Native routing for remaining generation and analysis work; the app currently uses the native worker pool for project compilation, source checks and offline WAV renders. Android thermal/battery signals and app lifecycle/audio transitions now update the active worker budget; other platform adapters remain unimplemented.
- A true adaptive quality ladder with measurable preview-quality modes and guaranteed unchanged offline exports.
- Drawn LFO curves, FM and fold warps, and the complete custom/imported table draw/render pipeline (the flagship synth has bend, sync, mirror and quantize warps on its code-generated tables).
- The flagship synth's app side: a device editor with OSC, FILTER, MOD and FX pages and a drag-a-source mod matrix ([app](app.md)); the flagship publishes no display data yet, so its envelope playhead is not built.
- MIDI 2.0 device input/output, Engine voice routing, output scheduling and full per-note controller/attribute mapping. The decoder/queue do not by themselves provide device support.
- Project manifest writing/round-tripping, dependency snapshots, content-hash generation and library/app integration for the new resolver.
- App-side rendering/runtime for declarative and custom module interfaces.
- Dynamic native module loading, package verification, crash containment and optional out-of-process isolation.
- VST3 export, CLAP export of whole graphs, and macOS plug-in bundles (CLAP export of component libraries is built: [native module SDK](native-module-sdk.md#export-as-a-clap-plug-in)).

## Known project-size and reliability risks under active refactor

**[Fact, caps audit for F7, 2026-11-04, at `5f1c47b`]** The engine no longer has the old fixed caps on exports, imports, parameters, synth parameters, modules, clips, automation lanes or points, pattern notes, steps or note-curve points; project state is a budget (`EngineResourceBudget`), like graph working memory and export buffers. What remains, by kind:

- **The app keeps what the engine keeps (F7.1):** project loading (on launch the app opens the last project straight away, and an undo reloads a whole saved snapshot the same way) keeps every automation lane and point, and patterns hold any number of notes and curve points, with steps bounded only by the engine's signed 32-bit step representation (`app/lib/model/pattern_doc.dart`). Stretching a note's start (`PatternDoc.stretch`) never moves it before step 0. One generate step (random notes, arpeggiate) refuses more than 2^20 new notes whole instead of cutting them short. Still open: layer/folder adds are only guarded by the buttons, so a 65th layer makes the engine refuse the whole project (F7.3 makes layers dynamic).
- **More than 64 layers (F7.3 part B; merged 2026-11-04 with known problems, followed up in #94/PR #124 and #133):** `setProject` grows the Engine's slot table and mix graph off the audio thread (doubling, never shrinking) and swaps them in by command, so playing layers keep their slots and sound bit for bit; the old table is freed off the audio thread. The ceiling, `maxLayers()`, comes from the graph-working budget with a measured cost (the mix graph grows with the square of the capacity, and a grow holds the old and new graphs at once): 349 layers at the 128 MiB fallback budget, 2,154 at a 1 GiB device budget, 5,847 at 4 GiB, never below 64 [Fact: measured 2026-11-11, `maxLayers()` at 48 kHz]. A project with more is refused: "project has N layers; this device's memory budget allows at most M". `scope()` names the master and the audition by id (C API `CAW_SCOPE_MASTER`/`CAW_SCOPE_AUDITION`), since the audition's slot moves on a grow; `CAW_API_VERSION` is 2 for that change. Exports: offline installs no longer drop layers above the command queue (PR #124). The export buffers and the slots' export pointer tables a project allocates are held, in bytes, to `exportBufferBudget()` buffers' worth (a 65-slot share of the graph-working budget, each buffer with one table entry), so many layers spread it instead of multiplying it; a layer past it is refused with a layer error before anything is allocated for it (#133). Each slot's pointer table is exactly as large as the largest chain it has held exports; a chain that exports more gets a new table by command (the audio thread retires the old one), so the control and audio threads never share a field and creating export memory while layers play is not a data race (#133). The per-chunk loops (planning, solo, export clearing, previews, overload, routing) visit only the slots in use, kept in an ascending list on the audio thread, so callback cost follows the layers in use, not the capacity (#133; callgrind, 4 layers, 1,000 callbacks of 192 frames: 216.5M instructions at capacity 64 and at capacity 1,000, which cost 220.8M and 289.1M before). Still open: the app's own 64-layer caps on its add buttons (part C).
- **Runtime slot capacity (F7.3 part A):** the Engine's slots are held by pointer with a stored index, and the mix graph, process order and busy flags are sized from a runtime capacity (64 layers plus the audition at first, `layerCapacity()`/`auditionSlot()` in `engine/src/engine.h`). The layer-order command carries its list out of line and retires it off the audio thread. Sound is unchanged (goldens), and playback is slightly cheaper (callgrind 1 layer −1.0%). Parts B (growth by budget) and C (C API audition index, app caps) follow.
- **No 64-bar limit (F7.2):** loop length, clips, layer lengths, automation points and the audition run to the 32-bit step count (whole bars up to 2^31 − 1 steps) in the engine and the app. Out-of-range values are refused with a message naming the field (`engine/src/project.cpp`). Clip expansion is checked against the project-state budget before it is built, so a huge looping clip is refused, not expanded (`arrangementBytes` in `engine/src/engine.cpp`). The app's loop and free exports stream to the WAV file a chunk at a time (`renderExportToWav` in `engine/src/render.cpp`, `WavFileWriter` in `engine/src/wav.cpp`), so a long song needs no more engine memory than a short one; they write `path.part` and rename it at the end, so a cancelled export leaves an existing file untouched. A render longer than a WAV file holds is refused before anything is written. The app's save step copies the finished file to the picked place in chunks (Android: the system's create-document picker and a streamed copy in `MainActivity.kt`; desktop: a file copy to the picked path, `app/lib/platform/save_copy.dart`), so it never holds the whole file in memory (#91). The `caw` CLI keeps the in-memory path (it prints peak and RMS) and checks `--bars`/`--steps` the same way. The app pulls a project file's meter into the engine's 1..16 beats on load. In the app the song ends at its last clip or automation point (or the shortest length the project sets) and playback loops back there; the arranger timeline always reaches 64 bars past that end. The arranger ruler and grid paint only the visible span; clips past about 2^24 px (around 900,000 steps at the default zoom) may draw imprecisely, because the renderer uses 32-bit floats ([Assumption], #90).
- **Silent clamps in the engine:** bpm 20..400, beats per bar 1..16 and voices 1..32 in the parser; render one-shots cut at 30 s and free exports clamped to 0.1..600 s; `wt` unison clamped to 16 and wavetable frames to 256; note-timing splits per 64-sample block (16, later notes start together); hot-swap state take-over (2 MB, the rest restarts fresh).
- **Fixed structure that should become dynamic or a budget:** 64 layers (`kMaxLayers`, fixed slot arrays and the mix graph sized from them), 32 voices, 32 modules per track, 8 modulation links per parameter, 64 dropdown choices, ratchet 8.
- **Safety bounds to make configurable within host policy:** module source 64 KiB, nesting 128, registers 1,024, state 8 MiB per module, `fn` depth 32 and 4,096 calls; JSON 16 MiB and depth 64, project JSON 8 MiB, 4,096 dependencies; MIDI files 16 MiB and 65,536 events; queues (commands 1,024 with a 2 s retry that can drop a payload, retirement 1,024 plus 256 pending whose overflow leaks, MIDI 2.0 input 1,024 with an unsurfaced drop count, graph events 1,024 per port, parameter commands 256); 16 workers and 256 queued jobs; 64 channels per port.
- **Real format limits (stay):** MIDI 7-bit fields and 0..15 channels, UMP group/channel/controller, the 2^53-sample transport, sample rates 8 kHz..192 kHz, uint16 register indexes, built-in arity 6.
